# 관제자 사용성 재점검 — #100

검토일: 2026-10-03 · 기준: main `e85843c` · 수정: `fix/100-operator-ux`

**후속 개발 안내:** 아래 평가는 #100 당시 판의 기록이다. 같은 날 #103~#113에서 TLS·로그인 제한·웹훅 DNS 검증, 담당 배정·동시 작업 충돌 처리, 로고·조치 의미, data01 자원 감시, Mac 백업 감시를 추가했다. 이 문서에 당시 미구현으로 적힌 기능을 현재 상태로 인용하지 않는다. 실제 배포와 후속 검증은 [최종 HTTPS 배포 기록](evidence/2026-10-03-final-tls-deployment/README.md)을 기준으로 확인한다. Loki 보존 삭제·상시 가동 조건 등 남은 한계는 그 기록에서도 구분한다.

## 1. 평가와 검토 범위

**보호 대상의 상태를 보고 사건의 근거·판정·차단 지점까지 확인하는 시연 흐름은 갖춰져 있다.**
현재의 주된 문제는 기능 수 부족보다 최신 상태의 신뢰도, 목록과 상세 사이의 작업 맥락, 좁은 화면에서 다음 동작을 찾는 비용이다.
초기 기획 전체가 구현됐거나 상시 운영 준비가 끝났다는 평가는 하지 않는다.

### 검증 방법

1. 배포 콘솔 `http://192.168.70.254:8443/`의 관리자 세션에서 모든 주 메뉴와 주요 상세를 읽기 점검했다. 목록 조건, 정렬, 펼치기, 보고서 조회, 편집 열기/취소를 확인했다.
2. 운영 사건 판정·차단·해제·계정 변경·노드 토큰 발급·외부 알림 발송은 이 점검에서 실행하지 않았다. 실제 방화벽 효력이나 새 복원 RTO를 측정한 회차도 아니다.
3. 수정 빌드는 `127.0.0.1:18765`의 고정 시험 표본과 분리된 서버에서 확인했다. 이 서버는 운영 API로 전달하지 않으며 쓰기 요청을 거절한다.
4. 1440×800, 1440×900, 1100×800, 390×844와 추가 320×740 폭을 확인했다. 캡처는 표본 화면이므로 운영 성과 증거로 쓰지 않는다.
5. 일시 조회 오류와 복구, 제출 차단, 목록 조건 보존은 단위시험과 브라우저 동작을 함께 확인했다. 쓰기 성공·권한 조건은 기존 API/화면 시험으로 검증했다.

## 4. 초기 기획과의 차이

### 현재 구현으로 설명할 수 있는 것

- 수집한 근거에서 사건을 만들고, 사람이 다섯 판정값과 사유를 남기며, 버전별 집계와 저장된 리플레이 결과를 비교하는 흐름
- 보호 대상 로그/상태와 보안 사건을 함께 확인하는 콘솔
- 차단 요청을 내부 방화벽·허니팟 관문에서 별도로 확인하는 구조
- 역할 구분, 외부 알림, 감사, 자산/공개 취약점 연계
- 문서·기존 증거가 있는 망 분리 구성, 장애 전환 시험, 백업·격리 복원 절차

### 초기 화면 설계에 있지만 현행 화면에 없는 것

담당 배정/맡기, 런북 체크리스트, 제안 10% 대조군, 운영자가 고른 근거 행 고정, 예외 제안 생성·승인,
발생 전후 배포/변경 타임라인, UI에서 규칙 변경과 새 리플레이 실행은 실제 화면에서 제공하지 않는다.
문서의 초기 구상 표를 완료 체크리스트처럼 읽어서는 안 된다. 해당 항목을 이번 핫픽스에서 새 DB·워크플로로 만들지 않았다.

- 다중 관제자를 전제로 한다면 다음 기능 우선순위는 담당·충돌 처리다. 두 사람이 같은 사건을 독립적으로 처리하는 비용이 커지기 때문이다.
- 규칙 개선을 제품의 중심 가치로 내세운다면 변경 제안→검토→실행 결과 비교의 연결이 다음 단계다. 현재의 저장 결과 조회와 구분한다.
- 계정 관리·보고서 등은 이후 승인된 범위 확장이다. 초기 기획에 없었다는 이유만으로 결함이라고 판단하지 않는다.

## 5. 디자인·미적 평가

현재 화면은 화려한 장식보다 밀도 높은 운영 표에 가까우며, **전체 디자인을 갈아엎을 단계는 아니다.**
일관된 여백·얇은 테두리·제한된 색상, 데스크톱 표/모바일 행 전환은 유지 가치가 있다.

'AI 티'라는 인상을 줄 만한 부분은 다음과 같다.

1. 비슷한 카드·접힌 줄·작은 회색 보조문구가 반복되어 서로 다른 중요도의 정보가 같은 무게로 보인다.
2. 하나의 상태에 요약 배지·설명·도움말이 겹쳐, 무엇을 읽고 다음에 어디로 갈지 잠깐 판단해야 한다.
3. 긴 내부 식별자와 기술 용어가 일부 표에서 업무 이름보다 먼저 보인다.
4. 정상과 확인 전까지 중립색으로 처리하면 시각적인 상태 구별이 약하다.

그래서 이번에는 초록 정상 신호, 짧은 다음 동작, 대상 키 접기, 모바일 스크롤을 손봤다. 그라데이션·큰 홍보형 카드·장식 애니메이션을 추가할 필요는 없다.
보조 글의 작은 크기와 옅은 대비는 회의실 투사 화면에서 추가 확인할 가치가 있다. 이번 검토가 WCAG 전체 적합성이나 색 대비 측정 완료를 뜻하지는 않는다.

우선순위가 다른 정보는 **사건/조치, 수집 상태, 참고 분석**의 순서로 구분하는 편이 낫다. 모든 상태를 초록/빨강으로 단순화하면 미수집·미확인이 사라지므로 피한다.
보호 대상 로그 10줄을 유지하자는 사용자 방향은 타당하다. 다만 실시간으로 도착하는 스트림이라는 설명 대신 1분 적재·화면 재조회 주기를 분명히 한다.

## 6. 시스템 엔지니어 관점과 운영 한계

강점은 대시보드 장식보다 **경계가 있는 네트워크, 수집 경로, 장애를 식별하는 상태 표시, 지점별 적용 확인, 복원된 서비스 사용 확인**이다.
발표는 구성→노드 편입과 첫 수신→탐지/판정/차단→장애 전환→복원→한계로 보여 주면 이 강점이 드러난다.
단순 토큰 발급이나 예쁜 차트보다 '무엇을 확인했고 어디까지 검증하지 않았는가'가 중요하다.

현행 코드·설정·README에서 다음 제한은 여전히 남는다. 이번 PR은 해결했다고 주장하지 않는다.

- TLS·Secure 쿠키와 로그인 시도 제한, 웹훅 DNS 목적지 검증: 상시 운영/다른 사용자 접속 전 선행 조건
- data01 자원·디스크 감시와 보존 정책: 현재 여유 공간이 있다는 사실과 별개의 운영 요건
- 같은 Mac 위 VM과 단일 DB/방화벽, 평시 콘솔 B 중지: 호스트 장애나 평시 완전 이중화를 해결하지 않음
- 8시간 백업이 한 번 빠지면 16시간: RPO 12시간 이내라고 보장할 수 없음. 실행 중 잠자기 방지와 예약 실행 보장은 다름
- 기존 연결은 허용하는 방화벽 순서: 새 연결 차단 범위이며 기존 연결 종료는 정책 결정·미시험
- 새 노드의 방화벽/설치 과정 수작업, 실제 장비 API 연동 미검증
- 장비 매핑은 조회 때 계산: 장기 감사에서 당시 장비 귀속을 불변 기록으로 제공하는 기능은 아님

이 제한은 단순 문구 미관보다 중요하다. 이번 결과는 제한된 시연/연구 환경의 화면 완성도를 높인 것이며, 상시 운영 준비 완료 판정이 아니다.

## 7. 코드 품질 평가

프런트엔드는 API 훅, 페이지, 공통 상태/입력/표시 컴포넌트가 나뉘어 있고, 실패·권한·악성 문자열 시험이 포함되어 있다.
`api/client.ts`의 공통 오류·취소·시간 초과 처리, `api/live.ts`의 WebSocket 재연결·조회 무효화,
`UntrustedText.tsx`의 외부 문자열 처리, `app/web.py`의 동일 출처 검사·CSP는 유지할 만한 구조다.
실시간 통보는 `/ws` WebSocket이며 통보를 받으면 해당 REST 조회를 갱신한다. 로그 원문을 WebSocket으로 계속 흘리는 구현은 아니다.

다만 상태의 의미는 여러 화면에 퍼져 있어 한 곳만 고치기 쉽다. 이번에는 정상/이전 자료 판별을 공통 훅으로,
목록 복귀 경로 검증을 공통 함수로 모았다. 공통 컴포넌트의 수보다 **같은 자료에 같은 뜻을 부여하는가**가 더 중요한 리팩토링 기준이다.

서버는 기능 모듈로 분리되어 있으나 `app/main.py`(약 1,150줄), `app/targets.py`(약 1,410줄)에 여전히 여러 책임이 모여 있다.
특히 대상 매핑·상태 집계·경고 판단·SQL을 함께 바꾸면 영향 범위를 파악하기 어렵다. 다음 구조 개선은 순수 매핑/상태 함수와
DB 조회 계층의 경계를 나누는 작업이 적절하다. 파일이 길다는 이유만으로 장애라고 단정하지 않았고, 이번에는 이 SQL·집행 경로를 재구성하지 않았다.

시험 수는 많지만 실제 DB 없이 건너뛴 시험과 브라우저 표본 시험이 있다. 전부 통과했다는 숫자가 운영 환경 전체의 보증은 아니다.
복원 도구 시험에는 파일을 닫지 않은 `ResourceWarning`도 남는다. 이번 화면 동작과 별개인 시험 코드 정리 과제다.

첫 실행의 로컬 포트/프로세스 조회 제한은 허용된 실행 환경에서 재시험해 통과했다. 앱 첫 실행의 선택적 DB 모듈 준비 오류는
시험 초기화를 수정한 뒤 전체 탐색으로 확인했다. 프런트엔드 시험의 중복 조치 ID 표본도 고유 ID를 부여하도록 정리했다.
초기 실패 기록은 최종 기록과 구분해 증거 폴더 `initial/`에 보존한다. 이는 실패를 숨기거나 제품 결함으로 합산하지 않기 위한 구분이다.

사용성 표본에서 1440×800·보호 대상 2개·로그 각 10줄일 때 판정 대기 첫 행이 첫 화면에 보였다.
다수 노드·모든 경고 조합에서도 항상 첫 화면에 들어온다는 보장은 아니다. 320px에서는 가로 넘침과 상단 동작 노출을 확인했다.

수정판은 기존 10/02의 탐지·차단·전환·복원 수치를 재측정한 판이 아니다. 기존 측정 증거는 당시 판의 결과로 유지한다.
운영 반영 뒤에는 사건 목록/상세 읽기, 모바일 새로고침, 판정 구역 이동, 정상·이전 자료 표시를 한 번 확인해야 한다.
