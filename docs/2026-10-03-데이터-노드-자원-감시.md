# 데이터 노드 자원 감시와 Loki 보존 설정 (#109)

이 문서는 구현과 반영 절차다. 10/03 콘솔 보안 #103, 사건 담당/충돌 #105, 화면 #107과 함께 운영 설치했다. 타이머·역할 권한·운영 화면의 실제 측정은 [배포 증거](evidence/2026-10-03-final-tls-deployment/README.md)를 따른다. 아래 Loki 보존 후보는 운영에 적용하지 않았다.

## 저장과 판정

`collector/data_node_health.py`를 data01의 systemd 타이머로 약 1분마다 실행한다. CPU는 1초간 `/proc/stat` 변화, 메모리는 `MemAvailable`, 디스크는 실제 저장소의 `statvfs`로 측정한다. 루트, PostgreSQL Docker 볼륨, Loki 마운트가 같은 파일시스템이면 한 줄로 묶는다. 디스크 사용률은 예약 블록을 제외한 `used / (used + available)`이며 여유는 일반 프로세스가 쓸 수 있는 바이트다.

| 기준 | 경고 |
|---|---|
| 사용률 ≥80%, 여유 ≤2 GiB, inode 사용률 ≥90% 중 하나 | 여유 감소 |
| 사용률 ≥90%, 여유 ≤1 GiB, inode 사용률 ≥95% 중 하나 | 용량 부족 |
| 측정 후 10분 초과, DB 기준보다 5분 넘게 미래 | 지표 오래됨 · 현재 용량 확인 불가 |
| 미설치·권한 없음·부분 측정 실패 | 자원 확인 불가; 읽을 수 있는 다른 디스크의 부족 경고는 유지 |

`data_node_health`에는 최신 한 행만 저장한다. 수집 역할 `opsloop_ingest`는 SELECT/INSERT/UPDATE, 콘솔은 SELECT만 받는다. 소유자 자격 증명으로 수집하지 않는다. DB 시각을 기록하므로 노드의 로컬 시계가 측정 시각을 위조하지 않는다. 쿼리 5초·잠금 2초·접속 5초, systemd 회차 전체 30초 제한을 둔다. 부분 측정 실패도 한 행에 남기고, DB 저장 실패는 다음 조회에서 오래됨으로 드러난다.

원문에서 재생성하는 `node_metrics`에는 넣지 않는다. 복원 목록은 28개 표로 늘지만 원장 재생성 대조 범위는 그대로다. 복원된 자원 한 행은 **백업 시점의 과거 상태**이며 복원 대상 호스트의 새 측정이 아니다.

카드와 관제 이상 띠는 `app/data_health.py`의 같은 판정을 사용한다. 펼친 데이터 노드의 시스템 구역에서 각 저장소의 사용률·여유·측정 시각을 읽는다. 접힌 줄에서도 부족·오래됨·확인 불가가 보인다. 경고 링크는 `/nodes?open=data-node`로 연결한다.

## 설치 · 확인 · 되돌리기

data01에 해당 커밋의 `collector/`, `infra/migrations/20261003_data_node_health.sql`을 전달한 뒤, 기존 수집기와 `opsloop_ingest`/`opsloop_console` 역할이 있는 상태에서 실행한다.

```sh
sudo bash collector/install-data-health.sh
```

설치기는 실제 `opsloop-db`·`opsloop-loki` 마운트를 조회해 `/etc/opsloop/data-health.json`에 기록하고, 마이그레이션·스크립트·unit을 설치한다. 기본 실행은 측정 결과만 출력하며 새 타이머를 켜지 않는다. 이미 켜진 타이머를 중지하는 명령은 아니다. 결과에 `error: true`나 `problems`가 있으면 경로와 권한을 먼저 확인한다.

반영을 결정하면 같은 명령에 `--enable`을 붙인다. 첫 저장 성공 후 타이머를 켠다. 이후 다음을 확인한다.

```sh
sudo systemctl status opsloop-data-health.timer --no-pager
sudo journalctl -u opsloop-data-health.service -n 10 --no-pager
sudo docker exec opsloop-db psql -U opsloop -d opsloop -c 'SELECT checked_at, cpu_pct, mem_used_pct, disks, problems FROM data_node_health'
```

콘솔 데이터 노드의 측정 시각이 새로 바뀌는지, 접힌 행과 펼친 카드가 같은 상태인지 확인한다. `verify-db-roles.sh`도 해당 스키마 전체 적용 후 실행한다. 되돌릴 때는 타이머를 `disable --now`하고 콘솔 버전을 되돌린다. 표를 삭제할 필요가 없다. 새 콘솔을 유지하면서 수집만 끄면 10분 뒤 오래됨 경고가 뜬다.

## Loki 보존: 운영 반영과 분리된 후보

기본 `infra/vmware/compose/loki.yaml`은 아직 무기한 보존이다. 보존 기간 결정과 원본 삭제 승인을 받기 전에 운영 설정을 바꾸지 않는다. 후보 생성기는 7일·30일 중 명시한 기간의 전체 설정 파일을 만들고 기존 파일은 덮어쓰지 않는다.

```sh
python3 infra/vmware/scripts/prepare-loki-retention.py --days 30 --output /tmp/opsloop-loki-30d.yaml
```

공식 [Loki 보존 문서](https://grafana.com/docs/loki/latest/operations/storage/retention/)에 따라 단일 Compactor, 지속 저장 경로 `/loki/compactor`, 24시간 인덱스, 2시간 삭제 지연을 사용한다. 이 프로젝트의 384MiB 제한을 고려해 삭제 작업자 수를 10으로 제한한다. 설정 검증은 Loki 3.7.8의 `-verify-config=true`로 수행한다. 이는 실제 삭제 동작이나 부하 시험을 대신하지 않는다.

**보존 적용은 원본 삭제를 유발한다.** 필요한 재생성 원장·시연 증거를 먼저 별도 보존하고 기존 설정과 마운트를 백업한 뒤, 후보 파일의 차이를 확인해 적용한다. 이미 삭제된 원문은 보존 기간을 늘리거나 설정을 되돌려도 돌아오지 않는다. 오래된 원장의 즉시 공간 회수를 약속하지 않는다. Compactor 실행·삭제는 비동기다.

범위는 Loki에 저장된 관제 대상 원본 로그뿐이다. PostgreSQL의 사건·판정·감사, S3 허니팟 원장, Mac 백업, 저장소 시험 증거의 삭제 정책을 바꾸지 않는다. Loki 이외의 저장소도 무한정 커질 수 있으므로 용량 경고에 대한 확인·확장·별도 보존 절차는 여전히 필요하다.

## 운영 한계

- 데이터 노드가 죽거나 DB가 가득 차면 새 상태를 저장할 수 없다. 이때 콘솔 `/health`와 Mac의 기존 진입점 감시가 DB 접근 실패를 감지한다.
- Mac이 잠들거나 꺼지면 그 Mac의 VM·진입점 감시도 함께 멈춘다. 호스트 밖의 독립 감시를 대신하지 않는다.
- CPU·메모리는 수치와 신선도만 제공한다. 순간 높은 사용률을 장애라고 단정하는 경고는 추가하지 않는다.
- Docker 볼륨이나 Loki 경로를 옮기면 설치기를 다시 실행해 경로를 갱신한다. 없는 경로는 루트 수치로 대신하지 않는다.
- 최신 상태 한 행으로 장기 추세·가득 찰 시점 예측은 제공하지 않는다.
