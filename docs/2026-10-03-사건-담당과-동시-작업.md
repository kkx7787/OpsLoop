# 사건 담당과 동시 작업 (#105)

## 화면에서 달라지는 점

사건 목록에서 전체·내 담당·미배정을 고른다. 담당 조건은 쪽 나누기 전에 적용하며 빠른 보기, 장비, 정렬과 함께 유지한다. 상세의 조치와 판정 구역에서 관제자는 미배정 사건을 인수하거나 본인 담당을 해제한다. 관리자는 다른 활성 관제사·관리자에게 배정할 수 있다. 조회자는 배정과 조치를 할 수 없다.

담당은 업무 분담이다. 다른 관제자의 기존 판정·차단 권한을 없애거나 사건을 독점 잠그지 않는다. 담당자의 계정이 비활성화되거나 조회자로 바뀌면 `담당 변경 필요`를 표시하고 다른 관제자가 인수할 수 있다. 담당 사건이 남아 있는 계정은 먼저 재배정·해제해야 삭제할 수 있다.

다른 사람이 판정·조치·담당을 바꾸면 입력한 메모와 판정 초안을 보존하고 저장을 멈춘다. 현재 상태와 이력을 읽고 `최신 이력 확인 후 계속`을 눌러야 새로운 기준으로 제출할 수 있다. 차단 목록의 해제 확인 창도 열었을 때의 기준을 유지한다. 조회 갱신 자체가 사용자의 확인을 대신하지 않는다.

## 저장 계약

- 상세와 차단 목록은 `workflow_version`을 보낸다. 사건별 마지막 조치 ID와 마지막 판정 ID를 조합한 불투명 토큰이며 클라이언트가 직접 만들어 쓰지 않는다.
- 판정·조치·담당 변경 POST에 `expected_version`을 반드시 넣는다. 사건 행을 `FOR UPDATE`로 잠근 다음 DB의 현재 토큰과 비교한다. 빠지면 428, 오래됐으면 409다. 거절된 요청은 판정·조치·차단·담당 이력을 추가하지 않는다.
- 같은 기준으로 온 동시 요청은 먼저 저장된 요청 하나만 성공한다. 성공 응답이 유실되어 같은 요청을 다시 보내도 이미 바뀐 토큰 때문에 중복 기록을 만들지 않는다. 변경 없는 담당 재지정은 새 이력을 만들지 않는다.
- 탐지 신호 증가와 집행기의 반영 보고만으로는 토큰이 바뀌지 않는다. 토큰은 관제자의 작업 이력 충돌을 막는 기준이며 사건의 모든 필드에 대한 스냅숏 잠금이 아니다.
- 상세 조회는 반복 읽기 트랜잭션으로 사건·판정·조치 이력을 함께 읽는다. 실시간 알림이 POST 응답보다 먼저 도착해도 같은 이력을 중복 추가하거나 더 최근 상태를 옛 응답으로 덮지 않는다.
- 명령줄 `triage.py`도 표시 전 토큰을 읽고 저장할 때 사건을 잠가 대조한다. 충돌은 저장 없이 건너뛴 것으로 남긴다. CLI 판정도 콘솔처럼 사건을 종결하고 실시간 변경 알림을 낸다.

배정 이력은 기존 `actions`에 `assign`으로 남긴다. 기록에는 실행자·시각·이전 담당·새 담당이 포함된다. DB에 새 테이블이나 별도의 버전 카운터는 추가하지 않는다. 사건의 `assigned_to`와 계정 사이에는 삭제 제한 FK를 두며 복원 대조에도 담당 상태를 포함한다.

## 적용과 되돌리기

1. 운영 백업을 확인하고 `infra/migrations/20261003_incident_workflow.sql`을 새 앱보다 먼저 적용한다. 반복 적용해도 담당과 이력을 초기화하지 않는다. #103 로그인 제한 마이그레이션도 필요하다.
2. 콘솔 A/B와 명령줄 triage를 같은 새 판으로 맞춘다. **옛 앱은 토큰을 검사하지 않으므로 옛 앱과 새 앱을 동시에 서비스하면 충돌 방지를 보장할 수 없다.** 점검 창에서 옛 B를 분배에서 빼고 A를 바꾼 후 같은 판의 B만 합류시킨다. CLI 판정도 이 사이에는 실행하지 않는다.
3. 기존 브라우저를 새로고침한다. 옛 화면의 변경 요청은 새 서버에서 428로 거부된다. 최신 화면인데 토큰이 없으면 저장을 비활성화하고 배포 상태 확인을 안내한다.
4. 두 관제자/두 탭에서 같은 사건을 연 뒤 한쪽에서 배정·판정을 저장한다. 다른 쪽의 초안 보존, 저장 거절, 최신 이력 확인 후 재시도를 확인한다. 조회자 권한, 내 담당/미배정 필터, 비활성 담당 인수도 확인한다.
5. 새 스키마가 들어간 백업으로 격리 복원을 수행한다. 카탈로그 FK 수는 16개이며 `incident_assignments` 지문을 대조한다. 이전 백업에는 담당 열이 없으므로 새 복원 검사 전에 마이그레이션 적용 여부를 명시해야 한다.

되돌릴 때는 A/B·화면·CLI를 같은 이전 판으로 맞춘다. 추가 열·FK·배정 이력은 삭제하지 않는다. 이전 판에서는 배정 조작과 충돌 방지가 제공되지 않는다는 점을 운영 기록에 남긴다. 기존 측정 증거는 당시 판의 결과로 보존하고 새 판의 회귀시험과 구분한다.

## 검증 범위

개발 검증은 운영과 분리한 PostgreSQL의 실제 콘솔 역할로 수행한다. 서로 다른 연결의 동시 요청, 토큰 누락·불일치, 계정 상태·삭제, 필터와 반복 마이그레이션을 확인한다. 화면 시험은 초안 유지와 실시간/POST 응답 순서 역전을 포함한다. 운영 A/B 배포와 사람 계정의 실제 브라우저 재확인은 개발 시험과 별도다.
