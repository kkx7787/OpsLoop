# 웹 디코이 설계

작성일 2026-09-18 · WBS 2.7 · 구현 `decoy/` · 로그 `/opt/decoy/log/decoy.json*`

관문에 통로를 내고 관리자 계정을 살려 둔 미끼를 배치한다. 목적은 공격을 막는 것이 아니라,
**관제 콘솔과 같은 형식의 인증 로그를 공격만 있는 환경에서 얻는 것**이다.

---

## 1. 왜 만드는가

허니팟은 SSH 로그를, 관제 콘솔은 HTTP 로그를 남긴다. 종류가 다르므로 허니팟에서 뽑은 규칙을
콘솔 로그에 적용해 볼 수 없었다. 검증 설계의 구멍이 여기 있었다.

| 환경 | 정상 트래픽 | 측정 | 규칙의 흐름 |
|---|---|---|---|
| 웹 디코이 | 없음 (전부 공격) | **재현율** | 여기서 규칙 후보를 뽑는다 |
| 관제 콘솔 | 있음 (계획된 정상 사용) | **오탐률** | 뽑은 규칙을 여기에 리플레이한다 |

두 환경이 **같은 이벤트 형식**을 쓰는 것이 이 설계의 전제다. 그래서 디코이는 기존 웹 허니팟
제품을 쓰지 않고 콘솔과 같은 스택(FastAPI)으로 직접 만든다.

콘솔에는 아직 인증이 없다. 따라서 이 문서가 정하는 형식이 **콘솔 인증 로그의 형식이기도 하다.**

---

## 2. 이벤트 형식

### 2.1 이벤트 ID 체계

`<발생원>.<범주>.<동작>` 으로 둔다. Cowrie 의 표기법을 그대로 따른다.

| 발생원 | 예시 |
|---|---|
| `cowrie` | `cowrie.login.failed` · `cowrie.command.input` |
| `decoy` | `decoy.login.failed` · `decoy.action.upload` |
| `console` | `console.login.failed` (콘솔 인증 구현 시) |

**규칙은 발생원이 아니라 범주와 동작으로 매칭한다.** 탐지 엔진은 이미 `eventid_like` 를
지원하므로, `%.login.failed` 로 쓴 규칙은 디코이와 콘솔 양쪽에서 그대로 동작한다.
이것이 규칙을 옮겨 검증할 수 있게 하는 장치다.

### 2.2 디코이가 남기는 이벤트

| 이벤트 ID | 언제 | 주요 필드 |
|---|---|---|
| `decoy.session.connect` | 새 방문자의 첫 요청 | `src_ip` · `user_agent` · `url` |
| `decoy.request` | 모든 요청 | `http_method` · `url` · `http_status` |
| `decoy.login.failed` | 로그인 실패 | `username` · `password` |
| `decoy.login.success` | 약한 자격증명으로 통과 | `username` · `password` |
| `decoy.action.upload` | 파일 업로드 시도 | `shasum` · `input`(파일명 · 크기) |
| `decoy.action.command` | 진단 기능에 입력 | `input` |
| `decoy.action.view` | 로그인 후 화면 조회 | `url` |

### 2.3 공통 스키마 확장

`events` 테이블에 열 네 개를 추가한다. 기존 행에는 전부 비어 있어도 무방하다.

| 열 | 형 | 용도 |
|---|---|---|
| `http_method` | text | GET · POST |
| `http_status` | integer | 응답 코드. 404 연속은 경로 탐색의 신호 |
| `user_agent` | text | 클라이언트 지문. HASSH 와 같은 역할 |
| `sensor` | text | `cowrie` · `decoy` · `console`. 집계를 섞지 않기 위한 구분 |

기존 열은 그대로 쓴다. `url` 에 요청 경로, `input` 에 본문 요약, `shasum` 에 업로드 파일의
해시, `password` 에 시도된 비밀번호가 들어간다. `protocol` 은 `http`, `dst_port` 는 8080.

## 3. 디코이 동작

### 3.1 화면

| 경로 | 동작 |
|---|---|
| `/` | `/admin` 으로 이동 |
| `/admin` | 로그인 화면. 일반적인 관리 콘솔 모양이며 특정 제품을 흉내 내지 않는다 |
| `/admin/login` | 자격증명 판정. 약한 조합이면 통과시킨다 |
| `/admin/dashboard` | 로그인 후 화면. 가짜 수치만 표시한다 |
| `/admin/users` | 가짜 계정 목록. 실제 사람의 정보를 쓰지 않는다 |
| `/admin/files` | 업로드 화면. 받은 바이트는 해시만 계산하고 버린다 |
| `/admin/tools` | 진단 입력 화면. 입력을 기록하고 정해진 문구만 돌려준다 |
| 그 외 전부 | 404 를 돌려주되 **요청은 기록한다.** 알려진 제품 경로를 흉내 내지 않으면서도 탐색 행위는 관측된다 |

### 3.2 통과시키는 자격증명

Cowrie 가 대부분의 비밀번호를 통과시키는 것과 같은 이유다. 로그인에서 막으면 "문을 두드렸다"
까지만 관측된다. 관심사는 **들어온 뒤의 행위**이므로 흔한 약한 조합만 통과시킨다.

통과 조합은 코드 상단의 목록 하나로 관리한다. 목록을 바꾸면 통과율이 바뀌므로, 변경 시점을
기록한다. 관측값 해석에 영향을 준다.

### 3.3 하지 않는 것

- 실제 기능을 제공하지 않는다. 데이터베이스에 연결하지 않고, 파일을 저장하지 않는다
- 업로드된 바이트는 해시 계산 후 버린다. 검체를 모으는 것은 허니팟의 일이다
- 입력을 실행하지 않는다. 진단 화면은 정해진 문구만 돌려준다
- 외부로 연결하지 않는다. 경유지로 쓰이지 않기 위해서다

## 4. 안전 요구사항

Cowrie 는 셸을 흉내만 내지만 **디코이는 실제로 동작하는 웹 애플리케이션**이다. 공격자가
코드 실행을 시도할 수 있는 대상이므로 조건을 명시한다.

| 항목 | 조치 |
|---|---|
| 권한 | 컨테이너 내부에서 비특권 사용자로 실행 |
| 파일 시스템 | 로그 디렉터리를 제외하고 읽기 전용 |
| 외부 연결 | 방화벽에서 DMZ 의 아웃바운드를 차단 |
| 자원 | 메모리 256MB · CPU 0.5 코어 상한 |
| 업로드 | 10MB 까지만 읽고 버린다. 그 이상은 잘라내고 기록에 표시 |
| 의존성 | 프레임워크와 서버 외 추가 라이브러리를 두지 않는다 |
| 코드 크기 | 한 파일로 유지한다. 읽어서 전부 확인할 수 있어야 한다 |

### 출발지 주소의 신뢰 경계

현재는 방화벽이 포트를 그대로 전달하므로 연결의 출발지 주소가 공격자의 주소다.
앞에 역방향 프록시를 두게 되면 전달 헤더를 봐야 하는데, **그 헤더는 공격자가 임의로 넣을 수
있다.** 우리가 세운 프록시를 거친 경우에만 신뢰하고, 그 외에는 연결 주소를 쓴다.

## 5. 여기서 뽑을 규칙 후보

임계치는 비워 둔다. **관측 전에 정하면 근거 없는 값**이 되기 때문이며, 규칙 v1 에서 한 번
겪은 문제다. 최소 3일 수집 후 분포를 보고 정한다.

| 후보 | 조건 | 콘솔로 옮길 때의 관심사 |
|---|---|---|
| R101 웹 인증 대입 | `%.login.failed` 가 창 안에서 N회 | 정상 사용자의 오타 반복과 구분되는가 |
| R102 경로 탐색 | 404 응답이 창 안에서 N회 | 콘솔의 깨진 링크가 같이 걸리지 않는가 |
| R103 침해 후 행위 | `%.login.success` 뒤에 `%.action.*` | 정상 로그인 후 활동과 구분되는가 |
| R104 도구 반입 | `%.action.upload` | 콘솔에 업로드 기능이 있으면 반드시 걸린다 |

R104 가 특히 중요한 사례다. 디코이에서는 업로드가 곧 공격이지만 콘솔에서는 정상 기능일 수
있다. **같은 조건이 환경에 따라 정탐도 되고 오탐도 된다**는 것을 보여주는 재료가 된다.

---

## 6. 검증 절차 (폐루프 2회차)

1. 디코이 로그로 규칙 후보를 만든다. 디코이에는 정상이 없으므로 여기서의 누락이 곧 재현율이다
2. 같은 규칙을 콘솔 로그 구간에 리플레이한다
3. 정상 사용이 걸리면 오탐이다. 조건을 고치거나 임계치를 올린다
4. 고친 규칙을 디코이 로그에 다시 적용해 재현율이 떨어지지 않았는지 확인한다
5. 두 값이 동시에 허용 범위에 드는 지점을 규칙 v3 으로 확정한다

4번이 빠지면 오탐만 줄이다 탐지 범위가 조용히 좁아진다. 1회차에서 이미 지적한 위험이다.

## 7. 배치

| 시점 | 위치 | 노출 |
|---|---|---|
| 이번 주 (선행) | 현행 허니팟 노드에 컨테이너 추가 | 보안그룹에서 8080 개방 |
| 다음 주 | DMZ 서브넷의 별도 노드 | 관문 방화벽이 8080 을 전달 |

선행 노출의 이유는 데이터가 시간에 비례해 쌓이기 때문이다. 구조 전환을 기다리지 않는다.
전환 시 컨테이너를 그대로 옮기므로 로그 형식은 바뀌지 않는다.

| 통과시킬 자격증명 목록 | 초기값은 흔한 조합 네 개. 통과율을 보고 조정한다 |

| 콘솔 인증 구현 시점 | 디코이 형식을 그대로 쓴다. 판정 화면 구현과 함께 진행 |
