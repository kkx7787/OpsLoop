# 콘솔 전송·로그인·웹훅 보안 보완 (#103)

## 범위와 검증 상태

현재 IP를 유지한다. 적용 후 주소는 `https://192.168.70.254:8443`이다. 도메인 구매·DNS 등록·인터넷 공개는 필요 없다. 브라우저 → HAProxy, HAProxy → 콘솔 A/B 두 구간을 TLS로 보호한다. 서버 인증서의 `console-a.opsloop.internal`과 `console-b.opsloop.internal`은 HAProxy가 인증서 신원을 확인하는 이름이며 실제 연결은 기존 IP로 한다.

2026-10-03 개발 검증은 운영 DB와 분리한 Docker 네트워크·PostgreSQL 16·Python 3.12·HAProxy 2.8에서 했다. 이어서 앱 `38720bd`를 실제 VM에 배포하고 사용자 Mac의 CA 신뢰 등록을 완료했다. 운영 반영과 후속 시험은 [별도 증거](evidence/2026-10-03-final-tls-deployment/README.md)에 남긴다. 기존 HTTP 전환 시간/복원 기록은 당시 판의 증거로 보존하며 새 판의 측정값으로 바꾸어 적지 않는다.

TLS는 콘솔 접속 구간에 적용한다. DB·수집 관문·Loki까지 모두 암호화했다는 뜻은 아니다. 관리망/VPN 제한과 콘솔 호스트 가드는 유지한다.

## 로그인 계약

- DB 시계 기준 60초 창에서 출발지·계정 조합 5회, 계정 전체 10회, 출발지 전체 30회까지 비밀번호 확인을 허용한다. 성공/실패/없는 계정/비활성 계정 모두 같은 사전 제한을 소비한다.
- 제한을 넘으면 429와 `Retry-After`를 반환한다. 계정 존재 여부나 어느 제한에 걸렸는지는 알리지 않는다. 거절을 반복해도 창의 끝을 미루지 않는다. 영구 계정 잠금은 없다. 창 경계에서 두 창의 허용량이 짧은 시간에 이어질 수 있는 고정 창 방식이다.
- 콘솔 A/B는 같은 DB 함수와 `SESSION_SECRET`으로 제한을 공유한다. 카운터 확인과 소비는 짧은 DB 잠금 안에서 처리하고 해시 계산은 밖에서 한다. 콘솔 재시작은 제한을 초기화하지 않는다.
- 제한 확인이 3초를 넘거나 DB/마이그레이션에 문제가 있으면 503으로 거절하고 비밀번호 해시를 시작하지 않는다. 프로세스 안의 대기나 무제한 재시도를 만들지 않는다.
- 키는 HMAC 값이다. 테이블에 아이디/IP 원문을 넣지 않고, 10분 지난 행은 다음 호출에서 지운다. 이 제한은 정상 계정에 대한 일시적 로그인 방해를 완전히 없애지는 못한다.
- `OPSLOOP_HTTPS_ONLY=1`이면 Secure 쿠키와 HTTPS Origin을 요구한다. HAProxy는 들어온 X-Forwarded-For/Proto를 지우고 자신이 본 주소와 `https`만 넣는다. 콘솔은 방화벽 `192.168.50.1`만 신뢰한다.

`infra/migrations/20261003_login_limits.sql`을 새 앱보다 먼저 적용한다. 옛 앱은 새 함수를 부르지 않으므로 단계 적용과 앱 되돌리기가 가능하다. 새 테이블의 백업 역할 읽기 권한도 포함한다. 콘솔 역할에는 함수 실행 권한만 주며 카운터를 직접 지우거나 바꾸는 권한은 없다.

## 웹훅 계약

주소를 저장할 때 HTTPS·사용자 정보·IP 형식 등을 검사한다. 발송할 때마다 A/AAAA 결과 전체를 검사하고, 하나라도 사설·루프백·링크로컬·예약 등 비공인 주소이면 발송하지 않는다. 검증한 숫자 주소에 직접 연결하므로 연결 시 DNS를 다시 해석하지 않는다. TLS 검증과 SNI/Host에는 원래 호스트 이름을 사용한다.

리다이렉트를 따라가지 않고 환경변수 프록시도 사용하지 않는다. Teams/일반 웹훅의 JSON 형식은 유지하며, 주소·응답 본문·예외 메시지를 로그나 발송 이력에 넣지 않는다. 2xx만 성공이다. 조회 실패·비공인 목적지·인증서 오류 등은 예외 종류로 기록한다.

소켓 연산은 최대 10초, 호출 대기는 전체 15초다. 전체 기한에는 DNS도 포함한다. OS DNS 조회 자체는 취소할 수 없으므로 별도 작업자 4개와 대기열 없는 상한을 둔다. 시간이 지난 작업이 실제로 끝나기 전에는 자리를 돌려주지 않는다. 자리가 없으면 `SenderBusy`로 실패하고 기존 재시도 일정을 따른다. 늦게 끝난 DNS 작업은 연결/전송을 시작하지 않는다. DNS가 계속 멈추면 발송도 실패하므로 이것을 전송 성공으로 읽지 않는다.

## 인증서 발급·배포 준비

`infra/vmware/scripts/console-certificates.py`는 파일만 만든다. Mac 신뢰 저장소 등록·원격 설치·서비스 재기동을 하지 않는다.

```bash
# 새 CA는 최초 한 번. 이미 있는 폴더를 덮어쓰지 않는다.
python3 infra/vmware/scripts/console-certificates.py init --ca-dir "$HOME/.config/opsloop/authority"
# 갱신도 기존 CA로 새 출력 폴더에 발급한다.
python3 infra/vmware/scripts/console-certificates.py issue \
  --ca-dir "$HOME/.config/opsloop/authority" --out "$HOME/opsloop-work/tls/20261003"
python3 infra/vmware/scripts/console-certificates.py check --out "$HOME/opsloop-work/tls/20261003"
```

CA는 5년, 서버 인증서는 90일이다. 배포 때와 매주 `check`로 21일 이상 남았는지 확인한다. 만료 21일 전 갱신해 여유를 둔다. 자동 갱신은 하지 않는다. CA 개인키는 소유자만 읽는 Mac 경로에 보관하며 저장소·VM·영상에 넣지 않는다. CA 유출 시 새 CA로 교체하고 모든 기기에서 옛 신뢰를 제거해야 한다.

| 대상 | 설치 파일 | 권한/주의 |
|---|---|---|
| 허용된 Mac | `ca.crt` | 지문 대조 후 사용자가 신뢰 등록. 공개 인증서만 전달 |
| Mac 감시·계측 | `~/.config/opsloop/tls/ca.crt` | `OPSLOOP_CONSOLE_CA`로 변경 가능. 검증 해제 옵션은 쓰지 않음 |
| 방화벽 | `/etc/haproxy/tls/console.pem`, `ca.crt` | root 소유, 디렉터리 0700·PEM 0600. CA 개인키 금지 |
| 콘솔 A | `~/opsloop/tls/server.crt`, `server.key`, `ca.crt` | A 전용 인증서. 키 1001:1001/0400, 디렉터리는 app UID 1001이 통과 가능 |
| 콘솔 B | 같은 경로 | B 전용 인증서. A의 키를 복사하지 않음 |

Mac 신뢰 등록은 발급한 CA 지문과 파일을 검토한 뒤 사용자 확인을 거쳐 한다. 인증서 경고를 무시하거나 `curl -k`, `verify none`으로 진행하지 않는다. 루프백 복원 훈련은 별도의 격리 환경이며 운영 CA를 신뢰시킨 것만으로 새 운영 경로의 복원 시험이 되지는 않는다.

## 적용 순서와 되돌리기

**기존 앱만 교체하는 배포 명령을 이 변경에 그대로 쓰면 안 된다.** 새 compose는 백엔드 TLS 인증서가 필요하고 새 HAProxy는 백엔드에서 TLS 응답을 기대한다. 점검 창에서 앱/compose와 HAProxy 설정을 함께 전환한다. A만 켜 둔 상태에서는 짧은 접속 중단이 생긴다.

1. 현재 앱·실행 이미지·compose·`.env`·HAProxy 설정·기존 인증서를 각 호스트의 비공개 백업 폴더에 보존한다. DB 백업 성공도 확인한다. 콘솔 B가 켜져 있으면 분배에서 뺀다.
2. 새 DB 마이그레이션을 적용하고 콘솔 역할의 함수 실행/백업 역할 읽기를 확인한다. TLS 파일을 위 경로에 설치하되 현재 서비스를 아직 바꾸지 않는다. `openssl verify`, 인증서/키 일치와 잔여 일수를 확인한다.
3. 사용 기기 CA 신뢰와 Mac 감시용 CA 파일을 준비한다. 새 앱 이미지는 기동 전에 빌드한다. `.env`의 `OPSLOOP_CONSOLE_URL`이 남아 있다면 HTTPS 주소로 맞춘다(기본값보다 환경값이 우선).
4. 새 앱+compose로 콘솔 A를 기동하고, A 안에서 `curl --cacert ~/opsloop/tls/ca.crt https://127.0.0.1:8000/health`가 200인지 확인한다.
5. 방화벽에서 새 설정을 `sudo haproxy -c -f <새 설정>`으로 검사하고 설치·reload한다. reload 명령 반환만으로 master 소켓이 준비됐다고 판단하지 않는다. 서비스 active와 master 소켓 응답을 제한된 횟수로 확인한 뒤 B 분배 제외 등 런타임 명령을 적용한다. 외부 HTTPS 헬스체크, 정상/실패 로그인, Secure 쿠키, WSS, 로그아웃, 평문 Origin 거부를 확인한다.
6. Mac 감시 스크립트를 갱신한다. 인증서 없는 환경을 정상으로 처리하지 않는지 확인한다. B는 전용 인증서를 설치한 뒤 합류 절차로 새 이미지와 compose를 받는다. `up`은 B 인증서/신원/잔여 일수를 먼저 검사한다. #105를 함께 배포하면 data01의 CLI 판정 도구도 [별도 설치·해시 대조](2026-10-03-사건-담당과-동시-작업.md)가 필요하다. 앱 이미지 교체만으로 CLI가 갱신됐다고 보지 않는다.
7. A/B 장애 전환과 세션 유지, 새 백업에 대한 격리 복원을 확인한다. TLS 변경 후 실측 결과를 따로 기록한다.

실패하면 점검 창을 유지한 채 **앱 이미지·compose·`.env`와 HAProxy 설정을 같은 이전 판으로** 되돌린다. 한쪽만 HTTP로 되돌리면 헬스체크가 계속 실패한다. 새 로그인 제한 DB 함수/테이블은 남겨도 옛 앱에 영향을 주지 않는다. 감시 URL도 이전 판과 맞추고, 되돌린 동안은 전송 보안 보완이 적용되지 않았음을 기록한다. 백업본이나 CA를 임의 삭제하지 않는다.

기존 시점의 백업에는 로그인 제한 함수가 없다. 새 이미지를 이용한 복원 훈련은 마이그레이션 이후 새 백업으로 진행하거나, 옛 백업 복원 뒤 해당 마이그레이션을 명시적으로 적용한다. 누락하면 로그인은 503으로 막힌다.

- [ ] 새 판의 정기 백업 회차·간격 관찰 (수동 백업과 별개)
- [ ] 실제 Teams 수신(외부 메시지 전송은 별도 승인된 시험에서만)

첫 전환은 HAProxy reload 직후 master 소켓 연결 거절로 중단됐으며 준비한 이전 앱/설정으로 복구했다. 준비 완료 확인을 추가한 두 번째 전환에서 HTTPS 200을 확인했다. B 합류 도구는 root:0700 인증서 폴더 안의 CA를 읽을 수 있도록 `sudo -n curl`로 검사한다(#113). 개인키/폴더 권한을 완화하지 않았다.

6회 시험 뒤 failover-probe를 비활성화하고 기존 계측 쿠키의 401 거절을 확인한 뒤 쿠키를 지웠다. B는 drain·maint·컨테이너 정지·게스트 종료 순서로 평시 상태에 돌려놓았다. Mac 점검 창을 해제하고 설치된 감시의 HTTPS 200을 확인했다. 평시 B가 꺼져 있다는 운영 조건은 바뀌지 않았다.
