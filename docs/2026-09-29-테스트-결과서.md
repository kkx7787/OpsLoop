단위 시험 전체 판정은 **조건부**다. 컨테이너에서는 저장소 파이썬 시험 56파일이 모두 종료 0 · 실패 0 이었다. ### 4.4 판정

**조건부.** 허니팟 장악을 가정한 핵심 경로는 막혔다. 허니팟에서 내부망 · 관문 · 인터넷 443 · 공용 DNS 로 가는 시도는 모두 실패했다. example.com:443 만 errno 101 이고 나머지는 시간 초과다. 원장 · SSM 은 엔드포인트로만 닿았다. 원장 쓰기는 자기 host 경로의 한 번 쓰기만 허용됐고, 센서 17 · 관문 11 사례가 모두 기대대로였다. 1차에서 미충족이던 네 항목은 모두 풀렸다. 옛 DB 직접 경로는 노드 종료로 없어졌고, 허니팟 외부 HTTPS · 공용 DNS · 다른 sensor · host 쓰기는 거부로 바뀌었다. 내부망 거부 경로 · 입력 제한 4건 · data01 서비스의 비특권 실행은 1차와 같다. DB 는 1차의 소유자 역할 사용에서 역할 분리로 바뀌었고, 146항목이 모두 기대대로였다.

오늘 실측에서 남은 위험은 셋이다. 첫째, 허니팟이 VPC DNS(10.0.0.2)로 임의 이름을 해석한다. DNS 질의에 정보를 실어 내보내는 경로가 남는다. DMZ 설계 때 이미 인정한 잔여다(README 107행). 둘째, 관문 자신의 443 · 53 유출에 목적지 제한이 없다. 1차 때는 관문이 배포 전이었으므로 새로 생긴 잔여다. 셋째, console-a · data01 의 외부 HTTPS 는 포트만 제한하고 목적지는 제한하지 않는다. 1차와 같다. 셋 모두 운영 설정을 바꿔야 해서 이 회차에서는 고치지 않았다. 거부 로그 대조 · 관문 쓰기 양성 대조 · console-b 가 빠져 합격이 아니라 조건부로 둔다. 표 4-7 의 수집 VM 분리 · 시간 동기화 지표는 1차 권고 가운데 손대지 않은 설계 과제다.

### 4.5 한계

- 방화벽 거부 로그를 출발지 · 목적지 · 포트로 대조하지 않았다. 1차는 대조했다(1차 문서 58행 · results.json 기록 network_drop_logs). 관문 `gw-forward-drop` 기록 대조도 없다. 설계 기대값(네트워크 설계 123행 · README 210행)의 '기록이 남는다' 부분은 미시험이다.
- 내부 방화벽 설정 해시를 점검 전후로 비교하지 않았다. 1차는 비교했다. '운영 설정 변경 없음' 의 근거는 요약(a-summary.md 4행)뿐이다.
- 관문 역할 쓰기의 양성 대조가 없다. 자기 경로 · 자기 생존 신호 쓰기를 시험하지 않았다.
- console-b 격리는 1차 · 최종 모두 시험하지 않았다. a-summary.md 64행은 4.4 장애 주입 재측정으로 넘겼지만, 그 재측정에는 격리 항목이 없다.
- 탐침 대상 목록은 보관하지 않았다. probe.py 19행이 인자로 받은 대상은 각 *.out 의 머리 키로만 남았다. 옛 AWS DB · 옛 앱 탐침의 주소는 확인 못 함.
- 2차의 '허니팟 5432 차단' 은 기록이 없다(이슈 #31 완료 기준에 있으나 PR #32 검증 표에 없음). 오늘 실측으로 대신했다.
- DMZ 시험(09-23, PR #24)은 요약 한 줄뿐이다. 항목별 원자료가 로컬에 없어 항목 단위 비교를 못 했다.
- web01 → S3 는 이름 해석 실패만 있다. IP 직접 재검증은 하지 않았다.
- 1차에만 있고 오늘 재지 않은 항목이 있다. 내부 reader 권한 · 버킷 공개 차단 · 암호화 · 버저닝 · web01 IPv6 링크 로컬 · console-a → example.com:80 · 콘솔 `/health` · 파서 · 실행기 파일 소유 · 센서 업로더(opsloop-upload) 서비스 권한 · 관문 DB 역할(opsloop_gate)의 관리자 속성이다.
- 입력 제한 시험 뒤 정상 표식 요청이 도착했는지 확인한 기록이 없다. 1차는 확인했다(1차 문서 102행).
- 탐침 시간 초과 기준이 다르다(1차 약 3초 · 최종 4초).
- 노드마다 한 번씩 쟀다. 장시간 같은 상태였다는 보증이 아니다.
- 소유자 접속 0 은 pg_stat_activity 를 한 순간 본 값이다. 주기 실행 서비스(ingest · agents)가 그 순간 붙어 있지 않았을 수 있다.
- 서비스 권한 표는 원 출력 없이 요약(a-summary.md 50 ~ 57행)만 있다.
- 설계 문서 안에서도 기대값이 다르다. 콘솔은 3.2 절 96행 '지금은 443 전체 허용' 과 4장 129행 '등록 채널로만' 이 다르다. 데이터 노드는 3.2 절 106행 '그 외 거부' 와 내부 방화벽 86행(목적지 조건 없는 443 허용)이 다르다. 이 절은 격리 목표 쪽을 기대로 두고 잔여 위험으로 판정했다.
- 서비스 권한 · DB 점검 시각은 요약에 '15:5x' 로만 있다. 원본을 옮기기 전 파일 수정 시각이 15:49 였다는 검토 기록이 있어 두 값이 다르다. 정확한 분은 확인 못 함.

## 5. 통합 시험 (수집 → 탐지 → 판정 → 차단 → 해제)

### 5.1 목적 · 범위

단계마다 시각을 남기고, 걸린 시간을 기준과 견줬다(이슈 #70 '통합 시험' · WBS 4.3).

### 5.4 판정

이슈 #70 의 통합 시험 완료 조건과 이슈 #51 의 두 시간 기준은 합격이다. 공격 요청 8건이 50초 만에 사건 두 건이 됐다.
차단 요청 뒤 74초에 내부 방화벽과 관문이 모두 적용을 보고했다. 87초에 공격자의 새 연결이 시간 초과로 떨어졌다. 해제 뒤 86초에 다시 열렸고, 97초에 두 지점 모두에서 203.0.113.10 원소가 빠진 것을 직접 확인했다. 시험 사건은 규칙 품질 집계에서 빠졌고 탐지 · 판정 기록에는 남았다.

절 전체 판정은 조건부다. 판정값과 차단 시간이 시연 절차와 달랐다(까닭은 5.3). 거부 로그 · 정상 출발지 유지 · 맺어진 연결 · 동기화 중단 · 만료 경로 · 대시보드 집계는 하지 않았다. 관문의 실제 차단 효과는 이 구성에서 잴 수 없다.
50 · 74 · 86초는 한 회차의 한 점이다. 1분 타이머가 이어진 경로라 회차마다 위상에 따라 값이 달라진다.

### 5.5 한계

- **관문 차단 효과는 재지 않았다.** 관문은 AWS 허니팟 앞에 있어 공격자 VM 트래픽이 지나지 않는다. 관문은 fail2ban · nft 상태를 직접 조회해 적용 · 제거만 확인했다. 실제 차단 효과는 내부 방화벽 경로로만 확인했다. 관문 조회 시각은 '15:43 대' 로만 남았다. 이 구성은 허니팟 정보가 web-01 보호에 기여한다는 것까지 증명하지 않는다(이슈 #51).
- **시연 절차의 확인 항목을 다 하지 않았다.** 방화벽 거부 로그 fw-block-drop(README 924행), 차단 중 정상 출발지 유지(README 930행 · `verify.sh` 7장), 맺어진 연결과 새 연결(README 931행), 동기화 중단(README 941행)이다. 만료 경로와 대시보드 · 규칙 화면 집계도 보지 않았다.
- **판정 · 차단 · 해제는 운영자 화면 조작이다.** 자동 판정은 없다. 차단 근거는 반복 탐색 · 제품 식별 요청을 확인한 것이고, 침해 성공을 확인한 것이 아니다(README 919행). 두 판정의 decision_seconds · proposed 기록은 확인 못 함.
- **한 회차 · 한 점이다.** 차단 경로에 1분 타이머 둘(집행기 · 동기화)이 이어져 있다. 집행기 타이머 주석은 '요청에서 관문 반영 확인까지 약 2분' 을 목표로 적는다(`enforcer/opsloop-enforcer.timer`). 두 대기가 겹치는 최악 위상에서 2분 기준에 드는지는 재지 않았다.
- **만료 없는 차단 12건은 설계상 집행 제외다.** 목록에서 빠지므로 두 지점 어디에서도 막지 않는다(`block_enforcer.py` 292 ~ 304행). 9/26 덤프 blocklist 13(복원 results.json) · 9/28 집행기 'exclude 13' 과 1건 다르다. 덤프 값은 전체 행 수이고, exclude 는 만료 없음 밖에 대역 주소 · 금지 대역도 함께 센다. 셈 기준이 조금씩 달라 1건 차이의 까닭은 확인 못 함.
- **관측 시각과 실제 시각이 다를 수 있다.** 16 · 17단계는 조회 시각이다. unenforced 감사의 why 값, enforcement 가 실제로 비워진 시각, 15:45:15 회차 요약 전체 줄은 확인 못 함.
- **원자료가 요약이다.** 감사 줄 · enforcement 값 · block-sync 회차 로그 · nft · fail2ban 출력 · 규칙 품질 조회 결과 원문은 it-summary 요약으로만 있다. Teams 미발송은 시험 세션에서 확인했으나 원문은 증거 폴더에 없다. web-01 줄 10 가운데 nginx.request 8건 밖의 2줄은 확인 못 함.
- **시험 출발지 제외가 없는 조회에는 이번 판정이 섞인다.** 규칙 품질 뷰와 콘솔 집계는 시험 출발지를 뺀다. 9/28 판정 지표 조회(`docs/evidence/2026-09-28-verdict-batch/metrics.sql` 1 · 4 · 5절)는 빼지 않는다. 다시 돌리면 9/28 · 9/29 시험 판정이 함께 세어진다.

## 6. 장애 주입 시험 (콘솔 이중화)

### 6.1 목적 · 범위

콘솔 한 대가 죽었을 때 HAProxy 가 다른 콘솔로 넘기는 시간과, 넘어간 뒤에도 세션이 유지되는지를 잰다(이슈 #43 · WBS 4.4).
#43 측정 뒤 남은 한계 세 가지를 고치고, 같은 도구로 다시 쟀다(이슈 #56 · PR #57).
운영 콘솔과 운영 HAProxy 에 실제로 장애를 넣었다. 주입 · 복귀 명령은 사람이 승인하고 돌렸다. 측정 도구가 운영에서 하는 일은 읽기뿐이다(`infra/vmware/README.md` 292행).

기준은 세 가지다.

- 이슈 #43 합격선: 노드 중단 후 30초 이내 전환 · 전환 뒤 세션 유지 · 판정 유실 0. 공식 시나리오는 컨테이너 정지 · VM 강제 끔이고, 각각 3회 이상 돌린다.
- 도구 합격선(README 322행): 도구 전환값 30초 이하 · HTTP 401 + 웹소켓 1008 = 0 · 마지막 실패 뒤 20번 연속 성공. 대상은 `stop` · `kill` · `vm-off` 다. `net-cut` · `db-cut` · `drain` 은 관찰 시나리오라 참고로만 남긴다.
- 이슈 #56 완료 조건: VM 끔 뒤 3분 안에 그 콘솔의 옛 DB 연결 0 · VM 끔 전환 때 끊긴 요청과 최대 지연이 이전 측정보다 줄어듦 · DB 끊김 복구 뒤 통보 재연결 6초 안.

### 6.4 판정

합격선 대상 20회는 모두 30초 안에 다른 콘솔로 넘어갔다. 가장 늦은 전환 완료는 기준선 VM 끔의 11.50초다. 27회 모두 HTTP 401 · 웹소켓 1008 이 0 이어서 전환 뒤 세션도 유지됐다. 감지는 회차 최솟값 ~ 최댓값으로 연결 거부형 4.7 ~ 6.2초, VM 끔 10.8 ~ 11.8초, 망 단절 11.7 ~ 12.3초다.
도구 판정은 20회 가운데 19회가 합격이다. 불합격 1건은 #44 보강 뒤 정지 1회차 t01-stop-a 다. 이 회차의 전환 완료는 0.45초였다. 그러나 T0 뒤 94.9초에 보낸 me 줄기 요청 1건이 reset 으로 끊겼고, 이 때문에 도구 전환값이 94.9초가 됐다. PR #44 는 이 1건을 전환이 끝나고 95초 뒤 HAProxy 에 닿기 전에 끊긴 단발 연결로 설명한다. 전환 구간의 실패는 0건이라고 적었다. 로컬 fw-haproxy.log 에는 그 시각(09-26 00:51:46.594 KST)에 받은 `/api/me` 줄이 없어, PR 설명과 어긋나지 않는다. 다만 `option dontlognull` 설정 때문에 요청 없이 끊긴 연결은 로그에 남지 않는다. 그래서 원인을 확정하지 못했고, 정지 시나리오는 조건부로 둔다.

차수 순서로 보면 다음과 같다. #44 보강으로 전환 완료가 4.7 ~ 11.5초에서 0.2 ~ 0.5초로 줄었다. VM 끔 때 끊긴 요청도 105 ~ 112건에서 51 ~ 52건으로 줄었다. 그러나 성공한 요청의 최대 지연은 오히려 늘었다. 기준선의 약 0.35 ~ 0.5초가 #44 보강 뒤 약 5초가 됐다. 전에는 끊기던 요청이, 이제는 `timeout connect 5s` 동안 죽은 콘솔과의 연결을 기다린 뒤 다른 콘솔에서 성공했기 때문이다(haproxy.cfg 23 ~ 25행). #57 이 이 값을 1s 로 줄이자 끊긴 요청은 10 · 10건, 성공 최대 지연은 약 1초가 됐다. 이슈 #56 완료 조건 세 가지는 모두 충족했다.
종합 판정은 조건부다. 조건부로 두는 까닭은 세 가지다. 첫째, #43 의 판정 유실 0 · 두 콘솔 실시간 · DB 재시작 뒤 통보 유지는 운영에서 재지 않았고 DB 시험으로만 확인했다. 둘째, #57 설정으로는 정지 · 강제 종료를 다시 재지 않았고 VM 끔도 2회뿐이다. 셋째, console-b 는 평소 꺼 두므로, 이 결과는 B 를 켠 동안에만 성립한다.

### 6.5 한계

- (잔여 위험) 평시에는 이중화가 없다. console-b 는 평소 꺼 두고 시험 · 시연 때만 켠다(README 217행). 평시 콘솔은 A 한 대뿐이라, A 가 죽으면 넘길 곳이 없다.
- (잔여 위험) DOWN 판정 직전 1초 안에 들어온 요청 약 10건은 여전히 끊긴다. VM 끔에서 10 · 10건, 망 단절에서 11건이다. `on-marked-down shutdown-sessions` 가 연결을 기다리던 세션을 끊기 때문이다(README 335행 · PR #57).

## 7. 백업 · 복원 훈련

### 7.1 목적 · 범위

DB 를 잃었을 때 백업 한 벌(덤프 + 역할 목록)로 DB 를 다시 세운다. 조회 · 판정과 원장 재적재까지 되는 데 걸리는 시간(RTO)과 잃는 기록(RPO)을 잰다. 이슈 #45 · PR #46 · WBS 4.5 에 해당한다.

- **훈련 방식.** DB 인스턴스 손실 가정, data01 의 별도 컨테이너(`opsloop-drill-db`)에 복원. 운영 DB(`opsloop-db`)는 멈추지 않았고 읽기만 했다.
- **살아 있다고 본 것.** data01 호스트 · `/etc/opsloop` · 원장(S3 · Loki · 관문 · 관리 원장).
- **범위 밖.** data01 전손(VM 재구성 · 비밀 재발급 · Loki · 관문 · 관리 원장 사본 복원), 실제 장애 주입(탐지에 걸리는 시간).
- **하지 않은 것.** 사람의 복원 계정 비밀번호 로그인. 운영자 결정으로 훈련 전용 세션으로 대신했다(7.5).
- **회차.** 1회(r01). 2026-09-27 02:29:52 ~ 02:35:45 KST(2026-09-26 17:29:52 ~ 17:35:45 UTC).
- 계획은 6주차(10/7 ~ 10/13)였다(`docs/2026-09-18-계획-개정.md` 138줄). 실제로는 9/27 에 했다. WBS 4.5 는 '완료(09-27)' 다.
- WBS 4.5 문구('새 서버 복원')와 실제 훈련 방식이 다르다. 7.5 에 적는다.

### 7.4 판정

**조건부.** 훈련 시점(2026-09-27, 표 23 · 트리거 4 · 함수 7 구조)만 보면 도구 기준(RTO · 설계 RPO · 무결성 · 지문 · 재생성 대조 · 정리)은 모두 채웠다. 다만 사람 로그인(S6 · S7 기준)은 채우지 못했고, 보관 백업 간격은 목표를 넘었다. DB 인스턴스를 잃었다고 보고 백업 한 벌로 새 인스턴스를 세웠다. RTO 352.975초와 설계 RPO 8,477.671초가 목표 안이다. 무결성 · 지문 · 재생성 대조가 모두 맞았다. 운영 DB 는 읽기만 했고, 정리 뒤 운영 적재 · 탐지 · 알림이 그대로였다.

절 판정을 조건부로 두는 까닭은 셋이다. 첫째, 훈련 뒤 마이그레이션 다섯 개(20260927_block_enforce · 20260929_block_points · 20260930_status_board · 20261001_console_accounts · 20261002_console_accounts_manage)로 구조가 표 23 → 26 · 트리거 4 → 9 · 함수 7 → 18, 역할 7 → 8 로 바뀌었다. README 446줄은 20261002 적용 뒤 첫 백업 이후에 다시 훈련하라고 적는다. 증거에는 재훈련 기록이 없다. 지금 구조의 복원 근거는 백업마다 도는 복원 시험(pg_restore 와 네 표 건수)뿐이다. 2026-09-29 16:30 KST 회차도 표 26 · 역할 8 백업이 복원되고 네 건수가 운영과 같았다(backup.log). 역할 · 무결성 · 콘솔 · 재적재는 지금 구조로 확인하지 않았다. 둘째, 보관 백업 간격이 한 번 43,395초로 RPO 목표를 넘었고 원인이 미확정이다(잔여 위험). 셋째, 사람 로그인은 미시험이다. 재시험 때 지금 구조의 백업으로 다시 훈련해 `verify` 통과와 RTO 를 다시 재면 조건이 풀린다.

### 7.5 한계

- **WBS 문구와 다르다.** WBS 4.5 는 '백업 복원 훈련 (새 서버 복원 · …)' 이다. 실제는 DB 인스턴스 손실 가정, 같은 호스트 data01 의 별도 컨테이너(`opsloop-drill-db`) 복원이다. 새 서버(VM) 복원과 data01 전손 복원은 하지 않았다. WBS 비고 수정 여부는 사용자가 정한다.
- **data01 전손은 범위 밖이다.** VM 재구성 · compose `.env` 와 접속 파일 재발급 · 설치기 순서 · S3 키 재발급을 시험하지 않았다. Loki · 관문 · 관리 원장은 Mac 사본(`~/opsloop-backup/ledger`)뿐이다. 쓰는 중에 복사한 사본이라 되돌려 본 적이 없다(README 461 · 752 ~ 760줄).
- **훈련 뒤 구조가 바뀌었다.** 위 다섯 마이그레이션에 맞춰 도구 기대값도 바뀌었다(c06b7a6 · 738e9d9 · 0df8808 · 22e69c0 · c26900c). 지금 기대값은 표 26 · FK 15 · 트리거 9 · 함수 18 · 뷰 3 이다(`queries.py` 43줄). 역할 점검 스크립트(`verify-db-roles.sh`)도 훈련 뒤 다섯 번 바뀌었다. 그래서 훈련 때의 67줄은 지금 점검과 같은 단위가 아닐 수 있다. 도구 시험 45개는 PR #67 에서도 통과했지만, 가짜 ssh · docker 로 도는 시험이라 훈련을 대신하지 않는다. 20261002 의 운영 적용 시각은 이 절의 자료로 확인 못 함. 어느 백업부터 재훈련 대상인지도 확인 못 함.
- **보관 간격 초과 원인은 미확정이다.** PR #46 은 '관리 단말이 늦게 깨어난 회차' 라고 적었다. README 746줄은 '04:30 · 16:30 두 번이라 몇 초만 밀려도 43200초를 넘는다' 고 적었다. backup.log 에서 앞 회차(`opsloop-20260921-1941`)는 2026-09-22 04:41:39 KST(Mac 시계)에 시작했다. 일정보다 늦었다. 그런데 덤프 머리 시각(data01 시계)은 04:26:51 KST 로 Mac 시작보다 14분 48초 이르다. Mac 시계로 본 두 회차 시작 간격(04:41:39 → 16:30:02)은 12시간보다 짧다. README 467줄은 Mac 이 깬 직후 두 시각이 최대 49분 어긋났다고 적는다. 격리 1차 문서(`docs/2026-09-22-격리시험-결과.md` 129줄)는 그날 data01 chrony 비동기를 관측했다. 시계 어긋남일 가능성도 있으나 추정이다. 후속 이슈 · 설정 변경 흔적은 찾지 못했다.
- **설계 RPO 는 이 백업 한 벌의 값이다.** 훈련 백업은 정기 일정 밖(00:08 KST)에 받은 것이라 T_f 와 2시간 21분 떨어졌다. 정기 일정만으로는 최악이 보관 간격(실측 43,395초)에 가깝다.
- **DB 에만 있는 기록의 손실 0 은 조건 덕이다.** 운영 마지막 판정이 2026-09-25 12:58:42 KST(03:58:42 UTC)로 T_b 보다 앞섰다. (T_b, T_f] 에 새 판정 · 조치가 없었다. 손실이 생길 수 있는 조건에서 잰 값이 아니다.
- **콘솔 확인은 사람 로그인이 아니다.** 사람 대신 Claude 가 훈련 콘솔 전용 서명 키로 발급한 세션(operator)으로 조회 · 판정했다(`human_checked=false`). 결과 파일은 사용자가 이 방식을 지시했다고 적는다. 복원 계정의 비밀번호 로그인은 확인하지 않았다. README 721줄 · drill.py 머리말의 '사람이 로그인' 과 다르다.
- **RTO 에 빠진 것 · 든 것.** 실제 장애를 주입하지 않아 탐지 · 판단 시간이 빠졌다. S6 → S7 에는 도구 결함 수정 약 3분이 들었다. RTO 끝점도 두 정의가 있다. 훈련은 T0 → S9(재생성 대조 · 무결성 통과)다. README 453줄 운영 런북은 '8단계 검증 통과 + 10단계 콘솔 판정 확인' 이다.
- **재생성 대조 범위가 좁다.** S3 센서 대조에는 cowrie · gateway 만 있고 decoy 는 없다. 대조 문장이 센서별로 묶으므로 창 안에 양쪽 모두 decoy 행이 없던 것으로 보이나 확인 못 함. 관제 대상 로그의 센서 목록은 비어 있다. 일치 근거는 web-01 지표 177건뿐이다(세션 4건은 허니팟 세션이다). PR #46 의 'S3 센서 · 관제 대상 로그 손실 0' 보다 좁다.
