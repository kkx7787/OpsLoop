# OpsLoop 격리 시험 결과 — 2026-09-22

## 결론

**현재 운영 구성은 일부 격리 통제를 검증했지만, 허니팟 호스트 침해를 전제로 한 격리 목표는 미충족이다.** 내부 web-01의 DB·콘솔·관리 접근 제한과 S3 기존 원문 보호는 동작했다. 반면 허니팟에서 기존 AWS DB로 직접 연결할 수 있고, 외부 HTTPS·DNS 목적지 제한과 센서별 S3 쓰기 권한 분리가 부족하다. 내부 수집기는 PostgreSQL 관리자 역할을 사용한다.

이 결과는 실제 침해가 발생했다는 뜻이 아니다. 사용자 소유 장비에서 허용·금지 경로를 직접 시험한 결과다. 시험의 기대값은 강화하려는 격리 목표이며, 기존 설계가 의도적으로 허용한 통신도 그 목표를 만족하지 않으면 보완 대상으로 표시했다.

## 범위와 방법

- AWS 서울 리전의 기존 `opsloop-honeypot`, `opsloop-app`, 원장 S3 및 관련 IAM·보안 그룹·라우팅을 확인했다. 계정 안의 다른 인스턴스는 연결 시험 대상에서 제외했다.
- VMware에서 실제 켜져 있는 fw, console-a, data01, web01을 확인했다. console-b는 꺼져 있고 HAProxy에서도 DOWN이므로 이번 시험의 합격 대상에 포함하지 않았다.
- AWS 관문·DMZ 구성 파일은 작업본에 있지만 조회 시점에는 해당 VPC·EC2·S3 VPC 엔드포인트가 배포되지 않았다. Terraform 구문 검증은 오류·경고 0건이었다. 구문 통과는 배포 또는 격리 성공을 뜻하지 않는다.
- SSH 및 SSM으로 실행한 제한된 TCP 연결, 정상 DNS 질의, S3 시험 객체 API 요청, 수집 관문 거부 시험, 읽기 전용 SQL 및 기존 로컬 시험을 사용했다. TCP 연결 성공은 DB 인증 성공이나 데이터 유출을 뜻하지 않는다.
- 운영 설정·정책·서비스를 변경하거나 재시작하지 않았다. 원본 로그를 삭제하지 않았다. 재수집 회복은 기존 타이머의 자연 재시도로 확인했다.
- 접속 오류를 차단 성공으로 계산하지 않았다. 먼저 각 장비와 실제 리스너를 확인했다. web01에서 이름 해석이 실패한 외부 목적지는 IP 직접 연결로 재검증했다.

개별 측정 시각과 원문 출력은 [시험 근거 JSON](../docs/evidence/2026-09-22-isolation/results.json)에 보관한다. 장시간 전체가 같은 상태였음을 보증하는 시험은 아니며, 각 결과는 기록된 관측 시점에 해당한다.

## 2. S3 권한 실측

센서 시험은 실제 `opsloop-sensor-role` 인스턴스 역할, 내부 읽기 시험은 실제 `opsloop-archive-reader` 주체인지 확인한 뒤 수행했다. 관리자 자격으로 대신 시험하지 않았다.

| 시험 | 실측 | 평가 |
|---|---|---|
| 센서가 전용 시험 객체 새로 쓰기 | 200 | 정상 업로드 허용 |
| 센서가 raw 목록 조회·시험 객체 읽기 | 각각 403 AccessDenied | 읽기 제한 확인 |
| 센서가 조건 없이 시험 객체 덮어쓰기 | 403 AccessDenied | 보호 동작 |
| 센서가 `If-None-Match: *`로 기존 시험 객체 재작성 | 412 PreconditionFailed | 기존 객체 보호 동작 |
| 센서가 시험 객체 삭제 | 403 AccessDenied | 삭제 제한 확인 |
| 센서가 다른 sensor·host 경로에 새 시험 객체 쓰기 | **200** | **센서·호스트별 쓰기 분리 미충족** |
| 센서가 같은 버킷의 `cti/` 시험 경로에 쓰기 | 403 AccessDenied | 현재 허용 prefix 밖 쓰기 제한 확인 |
| 내부 reader가 시험 객체 읽기·시험 prefix 목록 조회 | 성공 | 읽기 경로 정상 |
| 내부 reader가 시험 객체 쓰기·삭제 | 각각 AccessDenied | 쓰기·삭제 제한 확인 |
| 내부 reader가 `cti/` 목록 조회 | AccessDenied | 현재 reader 범위 밖 |

각 시험 객체의 버전은 1개이며 삭제 표식도 없었다. 버킷 공개 차단 4종, 기본 SSE-S3 암호화, 버저닝 Enabled도 읽기 전용 조회로 확인했다. 이번 `cti/` 거부는 현재 버킷 정책의 시험이며, 아직 만들지 않은 CTI 서비스 전체가 격리됐다는 뜻은 아니다.

초기 조건부 쓰기 요청은 설치된 boto3가 `IfNoneMatch` 인자를 인식하지 못해 **AWS 요청 전에 실패**했다. 이를 정책 거부로 계산하지 않고, 기존 업로더와 같은 서명 전 헤더 삽입 방식으로 재시험한 결과가 위 표다. 운영 SDK나 업로더는 변경하지 않았다.

현재 역할은 `raw/*`, `hb/*` 전체를 쓸 수 있다. 원문 덮어쓰기 보호와 다른 센서로 가장한 새 원문 작성 방지는 서로 다른 문제다. 역할·host·sensor prefix를 묶는 권한 분리가 필요하다. 또한 센서 역할에는 SSM 관리 정책도 붙어 있으므로 전체 AWS 권한이 오직 S3 쓰기뿐이라고 설명해서는 안 된다.

관련 코드: [센서 IAM 권한](../infra/terraform/iam.tf:56).

## 3. 입력 제한과 프로세스 권한

### 운영 수집 관문

web01에서 4건만 보내 확인했다. 대용량 본문을 보내지 않고 크기 초과 헤더만 사용했다.

| 입력 | 결과 |
|---|---|
| 인증 토큰 없음 | 401, missing |
| 알 수 없는 시험 토큰 | 401, unknown |
| 정상 web01 토큰 + 미지원 본문 형식 | 415, content_type |
| 정상 web01 토큰 + JSON 상한 초과 Content-Length | 413, too_large |

시험 뒤 관문·Loki·에이전트 다리가 동작했고 정상 표식 요청도 DB에 도착했다. 거부 2건과 제한 2건은 관문 이력에 남았으며, 거부 시험은 R202 사건 1건으로 통합됐다. 이 사건을 실제 공격으로 판정하거나 운영자 대신 종결하지 않았다.

### 내부 권한 경계

- 운영 systemd에서 수집·관문 프로세스의 비특권 OS 사용자, `NoNewPrivileges`, `ProtectSystem=strict`, 메모리 제한을 확인했다. 파서·실행기는 root 소유 파일이다.
- **수집기의 `collector.env`가 사용하는 DB 역할은 `opsloop`이며, 실제 PostgreSQL에서 superuser·역할 생성·DB 생성 권한이 모두 켜져 있었다.** console-a의 DB 연결도 `opsloop`로 관측됐다.
- 관문 전용 `opsloop_gate`는 위 관리자 권한이 꺼져 있었다.
- 수집·파서·PostgreSQL은 여전히 data01 한 VM에 있다. OS 비특권 실행만으로 DB 권한까지 최소화되는 것은 아니다. 적재·탐지·콘솔·관리 역할을 나누고 필요한 테이블·함수 권한만 부여하는 작업이 필요하다. 파서 침해나 DB 권한 악용을 실제 실행한 시험은 아니다.

## 4. 정상 수집과 관측된 장애 회복

1. 점검 초기에는 업로드·내부 적재·탐지 타이머가 성공 상태였고, S3 생존 신호와 내부 metrics 수신이 갱신되고 있었다.
2. 이후 내부 풀러 로그에서 S3 `EndpointConnectionError`와 탐지 보류를 확인했다. 19:18 KST의 첫 병행 대조에서는 내부 DB 건수가 AWS DB보다 적었다. 이 장애는 의도적으로 주입하지 않았다. 연결 실패의 정확한 원인은 이번 시험에서 확정하지 않았다.
3. 19:19:28~19:19:31 KST의 기존 타이머 재시도에서 원문 8개, 13,947바이트를 가져왔고 cowrie 23건·decoy 10건이 신규 적재됐다. 구멍·일시 오류·파싱 실패는 0, v1 탐지도 재개됐다.
4. 동일한 기준 시각 **2026-09-22 18:38 KST 이전**으로 다시 대조하니 아래 결과가 일치했다.

| 대상 | 내부 / AWS 건수 | 정렬한 식별자 지문 비교 |
|---|---:|---|
| cowrie events | 12,524 / 12,524 | 일치 |
| decoy events | 435 / 435 | 일치 |
| cowrie sessions | 2,765 / 2,765 | 일치 |
| decoy sessions | 215 / 215 | 일치 |

events 지문은 `line_hash`, sessions 지문은 세션 식별자 집합을 비교한 값이다. 모든 DB 열의 바이트 단위 일치를 입증하는 비교는 아니다. v1·v2 사건 식별자 집합도 같은 기준 시각에서 일치했다. 판정 이력은 내부 35건·AWS 32건으로 달랐고, 판정은 두 경로에서 별도로 쌓이는 데이터이므로 원문 수집 동일성 시험의 합격 조건에서 제외했다.

19:18:15 KST에 web01의 `/opsloop-first-receipt/isolation-20260922T0844Z`로 보낸 정상 GET 요청은 204 응답을 받았고, 19:19:29 조회에서 `nginx.request`, `provenance=fixture`로 DB에 존재했다. 추가로 웹 디코이의 표식 요청을 S3 경유 경로에서 추적했다. 최종 도착 결과는 아래 최종 확인에 기록한다.

data01에서 일시적으로 `chronyc`의 Not synchronised 상태도 관측했다. 방화벽의 시간원은 이후 Normal로 확인됐다. 시간 동기화 상태와 장기간 수집 중단의 표시·통보도 운영 점검 항목에 포함해야 한다. 이번 회복 확인은 기존에 요구한 48시간 연속 병행 대조를 대체하지 않는다.

최초 실행에서는 S3 풀러 35건에 실패 24건·오류 1건이 보고됐다(서브테스트 포함). Mac의 실제 여유 공간이 풀러의 10% 하한보다 낮아 `EXIT_DISK=13` 보호 로직이 발동한 것이 공통 원인이었다. 당시 풀러 출력은 여유 약 3.2GiB, `df`는 약 4.2GiB/사용률 98%였다. 계산 방식과 관측 시점이 다른 수치를 같은 값으로 간주하지 않는다.

추가 실행에서는 **시험 프로세스 안에서만** 여유 공간 검사를 충분한 공간으로 모의해 나머지 동작을 확인했고 35건이 통과했다. 기존 디스크 부족 시험은 계속 부족 상태를 따로 모의해 보호 동작을 검증했다. 운영 코드·하한은 변경하지 않았다. 전체 323건 무조건 원본 환경 통과라고 보고하면 안 된다. 단위 시험 자체도 실제 Mac 디스크 상태에 의존하지 않도록 보완할 여지가 있다.

내부 data01의 가상 디스크는 당시 약 13GiB 여유가 있었다. 그래도 VM 파일이 위치한 Mac 저장 공간 부족은 별도의 운영 위험이므로 사용자 파일을 임의로 지우지 않고 정리 필요 사항으로 남긴다.

## 6. 우선 보완 순서

1. **병행 전환 조건을 충족한 뒤 허니팟→기존 AWS DB 직접 경로를 제거한다.** 지금 즉시 끊으면 기존 수집 경로에 영향을 줄 수 있다. 새 DMZ의 배포 여부와 전환 근거를 함께 관리한다.
2. **센서의 외부 목적지와 DNS를 제한한다.** HTTPS 443 포트만 허용하는 현재 구성을 허용 서비스·목적지 통제로 보강한다. SSM·S3·정상 관리 경로가 유지되는지도 재시험한다. 새 관문 코드도 임의 외부 443을 허용하는 설계이므로 관문 배포만으로 이 항목이 해결되지는 않는다.
3. **센서별 S3 쓰기 권한을 분리한다.** 다른 sensor·host에 쓸 수 없도록 하고, 신뢰할 CTI·규칙 작성 권한을 따로 둔다.
4. **DB 최소 권한과 비신뢰 파싱 경계를 보강한다.** 수집·콘솔의 관리자 역할 사용을 정리하고 별도 수집 VM 분리를 검토한다.
5. **수집 지연·시간 동기화·Mac 디스크 부족을 운영 지표로 드러낸다.** 이번에는 재수집으로 회복했지만 중단을 빠르게 발견하는 기능은 별도로 필요하다.
