# 폐루프 1회차 — 판정에서 규칙 v2 도출

실행일 2026-09-08 · 규칙 v1 → v2 · 판정 32건 · 기준 `docs/2026-09-08-판정-기준.md`

수집 → 탐지 → 압축 → 통보 → 조치 → 판정 → 환류의 마지막 고리를 처음 닫았다.
이 문서는 그 한 바퀴에서 나온 수치와 판단을 남긴다. 결론보다 **무엇을 근거로
무엇을 바꿨는가**가 이 기록의 목적이다.

---

## 1. 입력 — 판정

| 항목 | 값 |
|---|---|
| 판정한 인시던트 | 32 / 38 (84%) |
| 도구 제안 수락률 | 100% (10/10, 뒤집힘 0건) |
| 차단 목록 등재 | 위협 판정 중 실제 침해 행위가 있었던 출발지 |

제안 수락률 100% 는 판정 기준 문서가 관측된 현상을 잘 설명했다는 뜻이다.
이 값이 낮았다면 규칙이 아니라 기준 문서를 먼저 고쳐야 했다.

## 2. 진단 — v1 이 무엇을 잘못했나

| 규칙 | 오탐률 | 비조치율 | 판정이 말한 것 |
|---|---|---|---|
| R001 무차별 대입 | 0.0% | **100.0%** | 관측값 5~28 전 구간이 비위협 |
| R002 침해 후 행위 | 0.0% | 0.0% | 조건과 판정 근거가 같아 지표가 무의미 |
| R003 악성코드 투하 | **25.0%** | 25.0% | 위협도 신호 1건, 오탐도 1건 — 분포 겹침 |
| R004 프록시 남용 | 0.0% | 0.0% | 판정 1건, 근거 부족 |
| R005 기준선 이탈 | 0.0% | **100.0%** | 2건 모두 기존 규칙이 이미 잡은 IP |

세 규칙에서 **같은 성질의 결함**이 서로 다른 지표로 드러났다.

> v1 은 "이벤트가 있었다"와 "의미 있는 일이 일어났다"를 구분하지 않았다.

- R003 — 파일 이동 이벤트가 있었다 ≠ 악성코드가 들어왔다 (빈 파일 2건)
- R002 — 명령을 실행했다 ≠ 무언가를 했다 (`echo xsec` 111회)
- R005 — 이벤트가 급증했다 ≠ 새로운 패턴이 나타났다 (단일 IP가 216/220, 308/308)

## 3. 처방 — v2 에서 바꾼 것

| 규칙 | 변경 | 근거 |
|---|---|---|
| R001 | **임계치 유지**, 상위 심각도 흡수(억제) 도입 | 관측값 전 구간이 비위협이라 임계치로는 못 나눔 |
| R002 | 무의미한 명령만 있는 세션 제외 | `echo`·`true`·`exit` 는 침해 후 행위가 아님 |
| R003 | 빈 파일 해시 제외 | `e3b0c442…` 는 0바이트 입력의 SHA-256 |
| R004 | 변경 없음 | 판정 1건. 표본 없이 손대면 개선이 아니라 추측 |
| R005 | 알림 난 행위자를 뺀 잔여에서 기준선 계산 | 기존 규칙의 그림자를 자기가 다시 잡고 있었음 |

### R001 에서 임계치를 옮기지 않은 이유

비조치율 100% 를 보면 임계치를 올리는 것이 통상의 처방이다. 그러나 관측값이
임계치의 5배(28회)인 인시던트까지 전부 "무시 가능"이었다. 위협 판정이 하나도
없으므로 임계치를 어디로 옮겨도 분리되지 않고, 옮기면 근거 없이 탐지 범위만
줄어든다.

비조치 사유가 모두 같았다. **같은 행위자에 대해 같은 시간대에 더 심각한 알림이
이미 떠 있었다.** 값의 문제가 아니라 같은 사건을 여러 규칙이 각자 보고하는
구조의 문제였다. 그래서 규칙이 아니라 인시던트를 만드는 단계에 억제를 넣었다.

규칙을 지우지 않은 이유는 다음 절이 보여준다.

## 4. 결과 — 같은 로그 구간에 v2 재적용

```
규칙                        v1        v2      증감
R001 SSH 무차별 대입         10         8       -2
R002 침해 후 행위            16         6      -10
R003 악성코드 투하            8         6       -2
R004 프록시 남용 시도          2         2       ±0
R005 기준선 이탈              2         0       -2
────────────────────────────────────────────────
합계                        38        22      -16   (-42.1%)
```

R002 는 신호 단계에서 **277 → 37 (-86.6%)** 로 줄었다. 알림의 대부분이 봇의
자격증명 확인이었다는 뜻이다.

### 억제가 규칙 삭제와 다르다는 증거

v2 를 두 번 실행했고, 첫 실행에는 R002 의 정규식 오류가 있었다.

| 실행 | R002 인시던트 | R001 억제 | R001 인시던트 |
|---|---|---|---|
| 1차 (R002 필터 미동작) | 13 | 10 | **0** |
| 2차 (수정 후) | 6 | 2 | **8** |

R002 가 정확해지자 R001 을 가리고 있던 상위 알림이 사라졌고, 억제되어 있던
8건이 되살아났다. **R001 을 삭제했다면 이 8건은 영원히 보이지 않았을 것이다.**

이것이 규칙을 지우는 대신 억제를 택한 결정의 사후 검증이다. 지금 데이터에서
쓸모없어 보이는 규칙이 조건이 바뀌면 유일한 탐지가 된다. 허니팟은 대부분의
비밀번호를 통과시켜 무차별 대입이 거의 항상 로그인 성공으로 이어지지만,
실제 서버에서는 실패만 반복하는 쪽이 다수다.

### 압축률에 대하여

전체 압축률은 v1 88.9% 에서 v2 71.1% 로 내려갔다. 신호 자체가 316 → 76 으로
줄었기 때문이며, **압축률이 낮아진 것은 나빠진 것이 아니다.** 압축은 목적이
아니라 노이즈에 대한 대응이다. 노이즈를 조건 단계에서 걷어내면 압축할 것이
줄어드는 것이 정상이다. 압축률을 성과 지표로 쓰면 노이즈를 남겨두는 쪽이
유리해진다.

## 5. 이 회차에서 확인된 것

- 판정이 규칙을 바꾸는 경로가 **실제로 동작한다.** 임계치 조정, 조건 변경,
  구조 변경 세 종류의 처방이 각각 다른 근거에서 나왔다.
- 지표가 처방을 구분해준다. 오탐률이 높으면 조건, 비조치율만 높으면 임계치나
  중복. R003 과 R001 이 서로 다른 처방으로 간 것이 그 사례다.
- 관측값 분포가 "임계치로 해결 가능한가"를 판별한다. R003 의 분포 겹침과
  R001 의 위협 판정 부재가 둘 다 "임계치로는 안 된다"를 가리켰다.

## 6. 다음 회차로 넘기는 것

- **v2 인시던트 22건 미판정.** 2회차의 입력이 된다. 특히 되살아난 R001 8건이
  상위 알림에 가려지지 않은 상태에서 어떤 판정을 받는지가 핵심이다.
- **R004** 는 표본이 쌓일 때까지 보류.
- **R002 의 순환** 은 남아 있다. 조건과 판정 근거가 겹치는 한 이 규칙의 오탐률은
  해석되지 않는다. 중복률을 이 규칙의 실질 지표로 삼는다.
- **재현율** 은 아직 측정하지 않았다. v2 가 v1 대비 무엇을 놓쳤는지 확인하려면
  v1 에서 위협으로 판정된 인시던트가 v2 에서도 잡히는지 대조해야 한다.
