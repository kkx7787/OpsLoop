# 관제 콘솔 화면 설계

작성일 2026-09-18 · WBS 2.8 · 구현 대상 `app/` · 선행 문서 `docs/2026-09-08-판정-기준.md`

설계 목표는 기능을 늘리는 것이 아니라 **판정 비용을 낮추는 것**이다. 화면의 수가 아니라
"한 건을 판정하는 데 몇 번 옮겨 다녀야 하는가"로 평가한다.

2026-09-23 디자인 반영: 공통 화면 틀과 인시던트 목록·상세·판정 화면은 개선안을 채택했다.
새 화면의 시각 기준은 [콘솔 개발 안내](../console/README.md#채택한-디자인-기준--2026-09-23)와 공통 컴포넌트를 따른다.
아래 내용과 기존 와이어프레임은 기능·업무 흐름의 설계 자료이며, 각 항목의 구현 완료를 뜻하지 않는다.

의미가 있으므로 주 색상과 별개로 유지한다.

## 2. S-01 로그인

디코이와 **같은 형식의 인증 로그**를 남기는 것이 이 화면의 숨은 목적이다. 형식이 같아야
디코이에서 뽑은 규칙을 이 로그에 리플레이할 수 있다.

| 항목 | 내용 |
|---|---|
| 남기는 이벤트 | `console.login.failed` · `console.login.success` · `console.session.connect` |
| 필드 | 디코이와 동일 (`username` · `user_agent` · `http_status` · `src_ip` …) |
| 계정 | 초기에는 관제사 1, 관리자 1. 가입 화면은 두지 않는다 |
| 잠금 | 실패 누적 시 지연을 둔다. 다만 **차단하지 않는다.** 차단하면 그 시도가 로그에서 사라진다 |

## 3. S-02 대시보드 — 미판정 현황

첫 화면이다. 인시던트 수가 아니라 **판정되지 않은 채 흐른 시간**을 맨 위에 둔다.

```
┌──────────────────────────────────────────────────────────┐
│  가장 오래된 미판정        미판정 잔량      오늘 판정      │
│      6시간 12분               23건        9건 / 중앙 2분   │
├──────────────────────────────────────────────────────────┤
│  제안 뒤집힘 비율 12%   ·   규칙 v2 적용 중   ·   차단 7건 │
├──────────────────────────────────────────────────────────┤
│  미판정 인시던트 — 오래된 순                               │
│  6h12m  R003 악성코드 투하   critical   4.4.66.84         │
│  4h05m  R101 웹 인증 대입    medium     198.x.x.x         │
│  ...                                                      │
└──────────────────────────────────────────────────────────┘
```

| 지표 | 정의 | 왜 보이는가 |
|---|---|---|
| 가장 오래된 미판정 경과 시간 | `now - first_ts` 중 최댓값 (미판정 건) | 사람이 판정한다는 전제에서, 밀린 정도가 곧 위험이다 |
| 미판정 잔량 | 판정되지 않은 인시던트 수 | 다음 회차 폐루프의 입력량 |
| 오늘 판정 수 · 건당 중앙 소요 | 판정 시각 기록에서 산출 | **판정 비용의 직접 측정치** |
| 제안 뒤집힘 비율 | `verdicts.proposed <> verdict` 비율 | 높으면 규칙이 아니라 판정 기준을 고쳐야 한다 |

서비스는 24시간 가동되고 관제자는 교대로 근무한다. 그래서 하나의 고정 기준(4시간 또는 24시간) 대신
**심각도별 목표 시간**을 둔다. 시계는 발생 시각부터 세고 교대할 때 초기화하지 않는다.

| 심각도 | 확인 목표 | 판정 목표 | 근거 |
|---|---|---|---|
| critical · 콘솔 발생 건 | 15분 | 1시간 | AWS 보안 사고 대응팀 확인 목표 15분, Splunk SOAR High 기본값 60분 |
| high | 1시간 | 4시간 | 3교대 한 교대 안에 끝나는 값 (추정) |
| medium | 4시간 | 12시간 | Splunk SOAR Medium 기본값 720분, 2교대 한 교대 |
| low | — | 24시간 | Splunk SOAR Low 기본값 1440분 |

목표의 2/3 가 지나면 주황, 넘기면 빨강으로 표시한다. 콘솔 발생 건은 침해사고 신고 기한(인지 후 24시간)이
걸리므로 심각도와 관계없이 critical 목표를 따른다.
다만 **허니팟과 디코이에서 발생한 건은 신고 대상이 아니다.** 우리가 노출을 의도한 자산이다.
이 구분을 화면에 표시한다.

**모바일**: 이 화면만 모바일에서 읽을 수 있게 만든다. 상단 수치와 목록까지다.
상세 조사와 규칙 변경은 데스크톱에서 한다.

모바일은 별도 앱이 아니라 **반응형 웹**으로 한다 (2026-09-18 결정).

| 방향 | 방식 | 근거 |
|---|---|---|
| 알림 · 안에서 밖으로 | 협업 도구 수신 훅 | 콘솔이 먼저 연결을 열므로 내부망을 열 필요가 없다 |
| 조회 · 밖에서 안으로 | 관리망 VPN 접속 후 반응형 화면 | 콘솔을 인터넷에 열지 않는다는 원칙을 유지한다 |

앱을 만들지 않는 이유는 셋이다. 모바일에서 할 일이 현황 확인뿐이라 앱이 강한 영역을 쓸 일이
없고, 스택과 배포 절차가 하나 더 붙어 임계경로가 밀리며, 이 구성에서 모바일의 설계 문제는
화면이 아니라 내부망에 있는 콘솔에 바깥의 단말이 어떻게 닿느냐는 네트워크 문제이기 때문이다.
홈 화면 설치(PWA)는 시간이 남을 때 덧붙이는 선택 사항으로 둔다.

## 4. S-03 인시던트 목록

| 항목 | 내용 |
|---|---|
| 기본 정렬 | **미판정 경과 시간 내림차순** (심각도순이 아니다) |
| 열 | 경과 시간 · 심각도 · 규칙 · 관측값 · 출발지 · 발생원(허니팟/디코이/콘솔) · 상태 · 담당 |
| 담당 | "맡기"로 담당을 표시한다. 두 사람이 같은 건을 동시에 여는 판정 충돌을 미리 막는다 |
| 경과 색 | 심각도별 판정 목표 대비. 주황은 2/3 경과, 빨강은 위반 |
| 필터 | 상태 · 심각도 · 규칙 · 발생원 · 기간 |
| 실시간 | 새 인시던트는 웹소켓으로 상단에 추가. 화면을 새로 고치지 않는다 |

상위 심각도 알림에 흡수된 건은 기본으로 숨기되 "흡수된 건 포함"으로 볼 수 있게 한다. 숨기기만 하면 사라진 것으로 오해한다.

`sensor` 열을 두는 이유는 **정상이 없는 환경(허니팟·디코이)과 있는 환경(콘솔)의 수치를
섞어 보지 않기 위해서**다. 섞으면 오탐률이 의미를 잃는다.

## 5. S-04 인시던트 상세

판정에 필요한 것을 한 화면에 모은다. 다른 화면으로 이동하게 만들면 그만큼 판정 비용이 는다.

| 구역 | 내용 |
|---|---|
| ① 규칙이 본 것 | 규칙 조건, 관측값, 임계치, 통합된 신호 수 |
| ② 규칙이 보지 않은 증거 | 같은 구간·같은 출발지의 **실제 행위** (명령, 파일, 경유 시도, 요청 경로) |
| ③ 행위자 이력 | 최초 관측일, 누적 발생, 다른 규칙 탐지 여부, **허니팟·디코이 접속 이력**, 차단 이력 |
| ④ 원문 로그 | 판단 근거가 된 원본 줄. 요약이 아니라 원문 |
| ⑤ 조치와 판정 | 조치 버튼과 판정 패널 (S-05) |

②가 이 화면의 핵심이다. 규칙이 본 것만으로 판정하면 **규칙의 시야를 그대로 물려받는다.**

③의 허니팟·디코이 접속 이력은 결정적 근거다. 그 자산에 접근한 IP가 정상 사용자일 가능성은
사실상 없다.

기획안(2.4 M4)의 상세 화면 요구를 함께 반영한다.

| 구역 | 내용 |
|---|---|
| 이 규칙 | 최근 오탐률 · 비조치율 · 제안 뒤집힘, 같은 규칙 · 비슷한 관측값의 과거 판정 |
| 발생 전후 변경 | 앞 24시간의 배포 · 백업 · 규칙 변경. 외부 유입 때문인지 우리가 바꾼 것 때문인지 가른다 |
| 추천 조치 | 규칙별 런북. 확인 절차 · 1차 조치 · 넘기는 기준 |
| 대조군 | 약 10% 는 제안을 가리고, 판정 후에 공개한다 |
| 담당 · 목표 | 머리글에 담당자와 판정 목표 초과 시간을 보인다. 담당 해제도 여기서 한다 |
| 증거 고정 | ② 의 행을 근거로 고정하면 판정과 함께 저장된다. 판정이 어느 로그를 보고 내려졌는지 남는다 |
| 예외 제안 | 오탐 · 무시 가능을 고르면 "이 건으로 예외 제안"이 S-07 조정 제안에 초안으로 올라간다 |
| 런북 | 확인 · 1차 조치 · 넘기는 기준을 체크리스트로. 체크는 이력에 남는다 |

**순환 경고**: R002·R003·R004 처럼 판정 근거와 규칙 조건이 겹치는 규칙은 화면에 그 사실을
표시한다. 이 규칙들에서는 정탐률이 품질 지표가 되지 못하며, 중복률을 대신 본다.

## 6. S-05 판정 패널

### 6.1 판정값 — 세 개에서 다섯 개로

관측결과 7장에서 세 값으로 분류할 수 없는 사례가 확인되었고, 디코이 가동 첫날에도
같은 사례가 나왔다(자기 정체를 밝힌 조사 기관 스캐너).

| 값 | 뜻 | 처방 |
|---|---|---|
| `threat` | 실제 위협 | 조치 |
| `non_actionable` | 규칙은 맞았으나 조치 불필요 | 임계치 또는 중복 |
| `false_positive` | 규칙이 겨냥한 현상이 아님 | 조건 수정 |
| `benign_positive` **(신설)** | 정확히 탐지했고 악의도 없음 (조사 기관 스캐너 등) | 규칙 수정 없음. 오탐으로 세지 않는다 |
| `undetermined` **(신설)** | 근거 부족 | 판정하지 않는다. 지표에서 제외 |

신설 두 값은 **오탐률의 분자에 들어가지 않는다.** 조사 기관 스캔을 오탐으로 세면 규칙 정확도가
실제보다 낮게 집계되어 불필요한 규칙 수정을 부른다.

**화면 표기**는 판정 기준 문서를 따른다. 실제 위협 · 무시 가능 · 오탐 · 양성 정탐 · 미결. 화면마다 다른 말을 쓰지 않는다.
순환 규칙(R002 · R004)에는 "무시 가능 · 중복" 제안만 허용한다. 계산으로 확정되는 값이기 때문이다.

### 6.2 자동화 편향 완화

1회차에서 일괄 수락을 썼기 때문에 제안 수용률 100%가 기준이 타당해서인지 확인 없이
수용해서인지 구분되지 않았다. 화면에 세 장치를 넣는다.

| 장치 | 화면에서의 모습 |
|---|---|
| 제안 신뢰도 공시 | "이 유형 제안의 과거 수용률 87% (23건 중 20건)" |
| 일괄 수락 제한 | 계산으로 확정되는 중복 판정에만 허용. 행위 근거 제안은 개별 확인 |
| 대조군 | 일부 건은 제안을 가린 채 판정. 나중에 제안과 대조 |

`false_positive` 는 제안하지 않는다. 규칙이 틀렸다는 판단을 규칙을 만든 쪽이 스스로 내릴 수 없다.

### 6.3 기록

판정 시 함께 저장: 판정자 · 시각 · **판정 소요 시간** · 제안값 · 관측값 · 근거 메모.
소요 시간이 있어야 "판정 비용이 줄었다"를 수치로 말할 수 있다.

| 열 | 대상 · 사유 · 집행 방법 · 적용 결과 · 만료 시각 · 요청자 |
| 동작 | 해제, 만료 연장 |
| 주의 | **요청과 실제 차단은 다르다.** 집행 결과를 확인해 표시한다 |

차단은 판정이 아니다. 가역적 완화 조치이며 만료가 있다. 화면에서도 판정과 분리한다.

## 8. S-07 규칙과 리플레이 결과

| 구역 | 내용 |
|---|---|
| 규칙 목록 | 규칙별 오탐률 · 비조치율 · 중복률 · 활성 여부 |
| 버전 비교 | v2 → v3 의 인시던트 증감, 규칙별 변화, 변경 사유 |
| 재현율 | 디코이 구간에서 산출한 값 |
| 변경 이력 | 무엇을 왜 바꿨는지. `rule_versions.reason` |
| 규칙 상태 | 활성 · 시험 적용(인시던트는 내되 지표와 분리) · 후보 |
| 자기 탐지 | R201 권한 상승 · 대량 해제, R202 미등록 에이전트 접속 |
| 기법 태그 | 규칙마다 ATT&CK 기법 ID 하나 (1차 매핑, 검토 필요) |

**임계치 조정 제안**: 제안값과 함께 얻는 것(콘솔 오탐 감소)과 잃는 것(디코이 재현율 하락, 놓치는 건 목록)을
나란히 보인다. 오탐률만 보고 조이면 탐지 범위가 조용히 좁아진다. 승인은 admin 이 하고 v3 후보가 된다.

여기가 폐루프의 결과를 보이는 화면이다. 발표 시연의 마지막 장면이 된다.

## 9. S-08 수집 노드 · S-13 노드 추가

**파이프라인 상태**: 원문 수신 · 적재 · 탐지 · 통보 네 단계의 마지막 시각과 지연(목표 탐지 30초 · 통보 10초)을
나란히 둔다. 끝에서부터 거꾸로 짚으면 끊긴 구간이 보인다. 네 시각은 기준선 하향 이탈의 감시 대상이다.

**점검 모드**: 점검하는 노드의 **통보만 묶고 수집과 탐지는 계속한다.** 점검 시간은 공격자가 숨기 좋은 틈이라
인시던트는 그대로 쌓는다. 종료 시각은 필수이고 최대 4시간이다. 만료 10분 전에 알리고, 끝날 때 여전히 이상이면
그 자리에서 다시 통보한다. 시작과 해제는 admin 이 하며 감사 기록에 남는다.

**콘솔 분배**: 콘솔 A/B 를 부하분산에서 빼고 넣는다(admin). 빼기는 진행 중 요청을 마친 뒤, 넣기는 연속 정상
3회 뒤 가중치를 단계적으로 올린다. 무중단 배포와 장애 시연에 쓴다.

| 항목 | 내용 |
|---|---|
| 노드 상태 | 정상(10분 이내 수신) · 지연(10분 초과) · 대기(토큰 발급 · 첫 수신 전) · 폐기(토큰 회수) |
| 미등록 에이전트 | 등록되지 않은 토큰의 수집 시도는 거부하고 인시던트로 올린다 |
| 구성 카드 | 세그먼트와 수신 경로. 연결을 여는 방향만 화살표로 표시한다 |

노드 추가(S-13)는 네 단계다. **대상 정보 → 수집할 로그 → 토큰 발급 · 설치 → 첫 수신 확인.**

- 콘솔은 토큰만 발급하고, 설치는 관리망의 Ansible 플레이북이 한다. 수집 설정을 손으로 고치지 않는다.
- 노드 추가와 토큰 발급은 관리자만 한다.
- 토큰은 1시간 · 1회용이며 발급 시 한 번만 보여 주고 해시만 저장한다. 취소하면 발급한 토큰을 폐기한다.
- 명령에는 토큰 원문 대신 환경 변수를 쓴다. 셸 이력에 남지 않게 하기 위해서다.
- 첫 수신 확인은 에이전트 등록 · 첫 로그 · 형식 변환 · 규칙 적용을 차례로 검사한다. 전부 통과해야 완료다.
- 인증 · 웹 접근 로그는 이벤트 ID 형식이 같으므로 R101 · R102 를 그대로 적용한다. R002(로그인 성공 + 명령)는
  정상 사용자가 없는 허니팟 전제의 규칙이라 보호 자산에는 적용하지 않는다.

시연 대상은 서비스망에 새로 띄우는 **보호 대상 서버 web-01** 이다. 콘솔을 대상으로 등록할 수도
있으나, "새 서버를 관제에 붙인다"는 장면이 분명하지 않다.

## 10. S-10 연결 끊김

콘솔 한 대가 죽는 것은 이중화가 흡수하지만 데이터 계층은 단일 장애점이다.

| 표시 | 내용 |
|---|---|
| 상단 | 마지막 수신 시각. 화면 수치가 그 시점 기준이며 갱신되지 않음을 밝힌다 |
| 동작 | 다시 연결 · 수집 노드 보기. 작성 중이던 판정 근거는 임시 저장한다 |
| 구성 요소별 상태 | 콘솔 A/B · 데이터베이스 · 수집(S3 에 계속 적재) · 실시간 통보(보류) |

복구 완료는 응답 재개가 아니라 **재생성 대조**(끊긴 구간을 S3 원문에서 다시 적재한 결과와 일치)와
**참조 무결성**(판정 · 조치 · 차단 기록)의 통과로 판정한다.

현장실습에서 DB 연결 실패 시 오류 페이지로 전환하는 기능을 만든 경험을 옮겼다.

## 12. S-12 알림 설정

알림은 안에서 밖으로만 나가고, 확인은 VPN 으로 콘솔에 들어와서 한다.

| 항목 | 내용 |
|---|---|
| 채널 | Slack · 일반 웹훅(JSON). Teams(Workflows 웹훅)는 선택. 매일 08:55 도달 확인 |
| 등급 | 즉시 호출(재호출 · 에스컬레이션) · 근무자 알림(근무 중인 관제자에게 바로, 재호출 없음) · 일일 요약 |
| 외부 생존 신호 | 콘솔이 1분마다 외부 감시(Uptime Kuma push)에 신호를 보낸다. 3분 끊기면 외부 감시가 직접 알린다. 내부망 전체가 멈춰도 알 수 있다 |
| 확인 | 콘솔에서 열면 재호출을 멈춘다. 즉시 호출이 30분 동안 확인되지 않으면 admin 에게 넘긴다 |
| 끊김 경로 | 데이터 연결 끊김은 DB 를 거치지 않는 헬스체크가 웹훅을 직접 호출한다. DB 가 죽으면 DB 를 거치는 통보도 멈추기 때문이다 |
| 콘솔 발생 건 | 심각도와 무관하게 즉시 호출. 24시간 신고 판단 기한이 걸린다 |
| 사건 | 새 인시던트 · 미판정 경과 · 센서 수신 끊김 · 데이터 연결 끊김 · 미등록 에이전트 접속 · 보고서 생성 |
| 묶음 | 같은 사건은 묶음 시간 안에 한 번만 보낸다. 미판정은 1회 후 매일 09:00 요약 |
| 재시도 | 1분 · 5분 · 15분. 결과를 발송 이력에 남긴다 |
| 권한 | admin 만 수정. 웹훅 주소는 비밀값이라 끝 4자리만 보인다 |

등급은 심각도가 아니라 **받는 사람이 지금 할 일이 있는가**로 정한다(기획안 7.3).

**저장 전 확인**: 지난 7일에 이 설정이었다면 몇 건을 보냈고 그중 밤 호출이 몇 건인지 먼저 보여 준다.
리플레이 평가와 같은 엔진을 쓴다. 불필요한 호출이 반복되면 받는 사람이 채널을 끄고, 그때 관제가 멈춘다.

메시지에는 번호 · 심각도 · 규칙 · 건수 · 런북(확인 · 1차 조치 · 넘기는 기준) · 콘솔 링크만 넣는다. 원문 로그 · 입력된 비밀번호 ·
내부 주소는 외부 서비스로 보내지 않는다. 카카오톡은 사업자 채널 심사와 토큰 갱신 문제로 제외한다.

## 13. S-14 감사 기록 · S-15 계정

않아 측정할 수 없다. 인터넷에 열린 두 센서 사이(허니팟 → 디코이)로 정의를 바꾼다.

## 15. 상태와 권한

**상태 전이**: `신규 → 확인 → 조치중 → 종결`. 차단을 요청하면 조치중이 되고, 종결은 판정이 기록될 때만 일어난다. 판정은 종결 시점에 기록한다.
판정 없이 종결할 수 없다. 판정이 폐루프의 입력이기 때문이다.

**권한** (S-15 에서 부여하고 코드에서 검사)

| 역할 | 판정 · 차단 요청 | 차단 해제 · 연장 · 규칙 억제 · 승인 | 알림 · 노드 토큰 · 콘솔 분배 · 계정 | 감사 기록 열람 |
|---|---|---|---|---|
| 조회자 | 불가 | 불가 | 불가 | 불가 |
| 관제사 | 가능 | 불가 | 불가 | 불가 |
| 관리자 | 가능 | 가능 | 가능 | 가능 |

권한 밖의 동작은 숨기지 않고 흐리게 보인다. 무엇이 있는지는 알되 누를 수 없게 한다.
노드 토큰을 관리자에게 두는 이유는 토큰이 있으면 가짜 에이전트로 탐지 입력을 오염시킬 수 있기 때문이다.

되돌리는 행위와 기준을 바꾸는 행위를 분리한다.

와이어프레임을 독립 검토한 뒤 고친 것과, 같은 검토에서 드러난 **이미 구현된 코드의 결함**이다.

| 구분 | 내용 | 처리 |
|---|---|---|
| 코드 | 판정자 · 조치자를 요청 본문에서 받음. 남의 이름으로 판정 가능 | 세션 사용자로 고정 |
| 코드 | operator 가 차단 해제 · 규칙 억제 가능 | admin 만 |
| 코드 | 차단하면 판정 없이 종결 | 차단은 조치중, 종결은 판정 기록 시 |
| 코드 | 차단 만료 없음 | 기본 24시간, 최대 30일 |
| 코드 | 제안값 · 판정 소요 시간 미저장 | 판정과 함께 저장 |
| 코드 | 새 DB 에서 스키마 설치 실패 (`sessions` 변경이 생성보다 앞) | 순서 수정 |
| 화면 | 1회차 결과를 두 주 비교처럼 표시, 규칙별 수치 불일치 | 같은 구간 리플레이로 다시 작성 |
| 화면 | 판정값 한글 표기가 화면마다 다름 | 판정 기준 문서 표기로 통일 |
| 화면 | 구축 전 방화벽에서 "적용됨" | 집행 대기로 |
| 화면 | 보조 글자 대비 3.3~3.6:1 | `#6e6e73` 으로 4.7~5.1:1 |
| 화면 | 빈 상태 · 오류 상태 없음 | S-16 추가 |

**구현 때 스키마에 더해야 하는 것**: 감사 기록 · 알림 채널 · 발송 이력 · 보고서 스냅샷 · 운영 변경 이력 테이블,
인시던트의 발생원 · 흡수 관계 · 신고 대상 여부, 판정의 대조군 여부 · 고정 근거, 차단의 집행 상태 · 해제자,
규칙의 상태 · 런북 · 기법 태그, 노드 토큰의 만료 · 1회용 여부, 사용자의 활성 상태.
