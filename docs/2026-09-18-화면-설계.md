# 관제 콘솔 화면 설계

작성일 2026-09-18 · WBS 2.8 · 구현 대상 `app/` · 선행 문서 `docs/2026-09-08-판정-기준.md`

설계 목표는 기능을 늘리는 것이 아니라 **판정 비용을 낮추는 것**이다. 화면의 수가 아니라
"한 건을 판정하는 데 몇 번 옮겨 다녀야 하는가"로 평가한다.

2026-09-23 디자인 반영: 공통 화면 틀과 인시던트 목록·상세·판정 화면은 개선안을 채택했다.
새 화면의 시각 기준은 [콘솔 개발 안내](../console/README.md#채택한-디자인-기준--2026-09-23)와 공통 컴포넌트를 따른다.
아래 내용과 기존 와이어프레임은 기능·업무 흐름의 설계 자료이며, 각 항목의 구현 완료를 뜻하지 않는다.

## 2. S-01 로그인

디코이와 **같은 형식의 인증 로그**를 남기는 것이 이 화면의 숨은 목적이다. 형식이 같아야
디코이에서 뽑은 규칙을 이 로그에 리플레이할 수 있다.

| 항목 | 내용 |
|---|---|
| 남기는 이벤트 | `console.login.failed` · `console.login.success` · `console.session.connect` |
| 필드 | 디코이와 동일 (`username` · `user_agent` · `http_status` · `src_ip` …) |
| 계정 | 초기에는 관제사 1, 관리자 1. 가입 화면은 두지 않는다 |
| 잠금 | 실패 누적 시 지연을 둔다. 다만 **차단하지 않는다.** 차단하면 그 시도가 로그에서 사라진다 |

## 3. S-02 대시보드 — 미판정 현황

첫 화면이다. 인시던트 수가 아니라 **판정되지 않은 채 흐른 시간**을 맨 위에 둔다.

```
┌──────────────────────────────────────────────────────────┐
│  가장 오래된 미판정        미판정 잔량      오늘 판정      │
│      6시간 12분               23건        9건 / 중앙 2분   │
├──────────────────────────────────────────────────────────┤
│  제안 뒤집힘 비율 12%   ·   규칙 v2 적용 중   ·   차단 7건 │
├──────────────────────────────────────────────────────────┤
│  미판정 인시던트 — 오래된 순                               │
│  6h12m  R003 악성코드 투하   critical   4.4.66.84         │
│  4h05m  R101 웹 인증 대입    medium     198.x.x.x         │
│  ...                                                      │
└──────────────────────────────────────────────────────────┘
```

| 지표 | 정의 | 왜 보이는가 |
|---|---|---|
| 가장 오래된 미판정 경과 시간 | `now - first_ts` 중 최댓값 (미판정 건) | 사람이 판정한다는 전제에서, 밀린 정도가 곧 위험이다 |
| 미판정 잔량 | 판정되지 않은 인시던트 수 | 다음 회차 폐루프의 입력량 |
| 오늘 판정 수 · 건당 중앙 소요 | 판정 시각 기록에서 산출 | **판정 비용의 직접 측정치** |
| 제안 뒤집힘 비율 | `verdicts.proposed <> verdict` 비율 | 높으면 규칙이 아니라 판정 기준을 고쳐야 한다 |

서비스는 24시간 가동되고 관제자는 교대로 근무한다. 그래서 하나의 고정 기준(4시간 또는 24시간) 대신
**심각도별 목표 시간**을 둔다. 시계는 발생 시각부터 세고 교대할 때 초기화하지 않는다.

| 심각도 | 확인 목표 | 판정 목표 | 근거 |
|---|---|---|---|
| critical · 관제 자기 탐지(R2xx) | 15분 | 1시간 | AWS 보안 사고 대응팀 확인 목표 15분, Splunk SOAR High 기본값 60분 |
| high | 1시간 | 4시간 | 3교대 한 교대 안에 끝나는 값 (추정) |
| medium | 4시간 | 12시간 | Splunk SOAR Medium 기본값 720분, 2교대 한 교대 |
| low | — | 24시간 | Splunk SOAR Low 기본값 1440분 |

목표의 2/3 가 지나면 주황, 넘기면 빨강으로 표시한다. 관제 자기 탐지(R2xx: 콘솔 감사 · 수집 경로) 사건은 침해사고 신고 기한(인지 후 24시간)이
걸리므로 심각도와 관계없이 critical 목표를 따른다.
다만 **허니팟과 디코이에서 발생한 건은 신고 대상이 아니다.** 우리가 노출을 의도한 자산이다.
이 구분을 화면에 표시한다.

**모바일**: 이 화면만 모바일에서 읽을 수 있게 만든다. 상단 수치와 목록까지다.
상세 조사와 규칙 변경은 데스크톱에서 한다.

모바일은 별도 앱이 아니라 **반응형 웹**으로 한다 (2026-09-18 결정).

| 방향 | 방식 | 근거 |
|---|---|---|
| 알림 · 안에서 밖으로 | 협업 도구 수신 훅 | 콘솔이 먼저 연결을 열므로 내부망을 열 필요가 없다 |
| 조회 · 밖에서 안으로 | 관리망 VPN 접속 후 반응형 화면 | 콘솔을 인터넷에 열지 않는다는 원칙을 유지한다 |

앱을 만들지 않는 이유는 셋이다. 모바일에서 할 일이 현황 확인뿐이라 앱이 강한 영역을 쓸 일이
없고, 스택과 배포 절차가 하나 더 붙어 임계경로가 밀리며, 이 구성에서 모바일의 설계 문제는
화면이 아니라 내부망에 있는 콘솔에 바깥의 단말이 어떻게 닿느냐는 네트워크 문제이기 때문이다.
홈 화면 설치(PWA)는 시간이 남을 때 덧붙이는 선택 사항으로 둔다.

### 3.1 보호 대상 중심 관제 현황 (2026-09-28 보충 #52 · 2026-09-30 개정 #72)

화면 제목은 '관제 현황' 이다. 지키는 서버(보호 대상)를 맨 위에 두어 "지키는 서버에서 무슨 일이 생겼는가" 를 먼저 답하고, 먼저 처리할 사건이
"무엇부터 처리할 것인가" 로 잇는다. 관측 센서와 관제 시스템은 아래에 한 줄씩 접는다. 보안 사건을 시스템 상태와 함께 보아
장애인지 공격인지를 한 화면에서 가른다. 성능 도구(그래프 · 경보 설정)는 만들지 않는다. 장비의 최근 로그는 보조 화면(3.2)으로 본다
(실시간 흐름이 아니라 1분 적재분을 다시 받는다).

배치는 위에서부터 다음 순서다.

1. 관제 이상 띠: 이상이 있을 때만 보인다. 조회가 실패하면 이전 항목을 지우고 '관제 상태 확인 불가' 한 줄만 둔다.
2. 보호 대상 카드: web-01 · 등록 노드.
3. 수치 · 먼저 처리할 사건: 앞 묶음은 보호 대상 · 관제 시스템 · 장비 미확인 사건, 뒤 묶음은 허니팟 · 디코이 사건이다.
4. 관측 센서(AWS 센서) · 관제 시스템(관제 콘솔 · 데이터 노드): 대상마다 한 줄 요약(수집 상태 · 경고 배지 · 미판정)으로 접고, 누르면 카드를 펼친다.

서버가 주는 대상 순서(AWS 센서 · web-01 · 관제 콘솔 · 데이터 노드 → 등록 노드)는 보고서 · 출발지 분석이 쓰므로 그대로 두고, 묶음은 화면에서만 나눈다.

| 대상 | 수집 신호 | 로그 | 대응 지점 | 자산 |
|---|---|---|---|---|
| AWS 센서 (Cowrie · 웹 디코이 · AWS 관문) | 업로더 생존 신호(적재기가 기록) | Cowrie · 웹 디코이 · 관문 기록 | AWS 관문 | honeypot-dmz · gateway |
| web-01 | 노드 수신(S-08 과 같은 판정) | web-01 로그 | 내부 방화벽 | web-01 |
| 관제 콘솔 | 없음(지금 붙은 콘솔은 실시간 연결의 이름) | 로그인 기록 | 없음 | console-a · console-b |
| 데이터 노드 | 마지막 탐지 실행 · 적재기 · 집행기 확인 | 없음 | 없음 | data-01 |
| 등록 노드 (#64, 0..n) | 노드 수신(S-08 과 같은 판정) | 그 노드 발생원(nodes.sensor) | 없음 | node_id 와 같은 자산(없으면 연결된 자산 없음) |

- 수집 상태는 네 가지이며 늘 글자로 쓴다: **정상**(신호가 새롭고 최근 1시간 요청 로그 있음) · **요청 없음**(신호는 새롭지만 요청이 없음) ·
  **수신 없음**(신호가 끊김) · **생존 상태 미확인**(신호가 없는 대상 · 기록하는 쪽이 멈춤). 로그 시각만으로 정상이나 장애로 칠하지 않는다.
- 보안: 최근 1시간 신규 · 높음 이상 · 전체 미판정. 한 사건이 여러 대상에 걸칠 수 있어 카드 합은 전체와 다르다. 장비를 확인하지 못한 사건은
  보호 대상 카드 아래 '장비 미확인 미판정 N' 으로 따로 센다. 사건 → 대상은 규칙 버전 정의의 발생원으로 정하고, 발생원이 섞인 규칙은 탐지와 같은 범위의
  실제 이벤트로 고른다(계산 방식과 한계는 4.1). '미판정 N' 은 그 장비로 거른 미판정 목록으로 잇는다(0 이면 링크 없음).
- 최근 사건: 24시간 안 높음 이상 중 가장 최근 한 줄(없으면 아무 사건). 누르면 상세다. 서명 규칙 사건이면 CVE 배지를 붙인다.
- 시스템: CPU · 메모리 · 디스크 한 줄. web-01 만 수집하고 나머지는 '자원 지표 미수집' 이다.
- 대응: 숫자 0 을 그리지 않는다. 그 지점이 적용을 확인한 것만 '차단 적용 n', 거부한 것은 '차단 적용 실패 n', 확인 전은 '차단 적용 여부 미확인 n',
  차단 금지 대역 출발지는 '정책상 차단 제외 n'. 적용 결과를 수집하지 않는 대상은 '차단 적용 여부 미확인'(숫자 없음). 집행기 확인이 멈추면 적용 확인을
  믿지 않고 미확인으로 합쳐 그 까닭을 함께 보인다.
- 취약점: 자산마다 수정판 있음 · 재부팅 대기 · 수정 여부 미확인 · KEV 수와 조사 시각. 총수는 자산 화면에서 본다. 자산 정보 없음 · 대조 전 ·
  48시간 넘음은 0 으로 꾸미지 않는다.
- 데이터 노드: 탐지 실행이 새로워 수집 상태가 정상이어도 적재기나 집행기(한 지점이라도) 확인이 멈추면 머리 배지를 '주의' 로 보인다.
  수집 상태 값은 그대로라 보고서는 바뀌지 않는다.
- 활성 차단 요청: 칸 이름의 수는 그대로 두고 값을 지점별 두 줄(AWS 관문 · 내부 방화벽마다 적용 · 실패 · 미확인)로 보인다. 집행기가 멈춘 지점은
  대응과 같이 미확인으로 합치고 '집행기 멈춤' 을 붙인다. 집행 제외는 두 줄에 들지 않으므로 아래에 '집행 제외 n건' 으로 적는다.
- 먼저 처리할 사건: 규칙 번호가 아니라 장비로 가른다. 앞 묶음을 먼저, 묶음 안은 오래된 순으로 합계 최대 8건이다. 제목 옆에 앞 · 뒤 수를 두어
  뒤로 밀린 건수도 보인다. 줄마다 장비를 붙인다.
- 관제 이상 띠: 다음 네 가지를 본다. 띠와 사이드바는 같은 조회를 쓰고, 적재기 기록이 없거나 생존 신호 · 노드 표를 읽을 수 없으면 흐린 글로 따로 적는다.
  - 멈춤: 적재기 확인이 30분, 집행기 확인이 지점마다 10분 넘게 없다. 집행기 항목은 차단 목록(S-06)으로 잇는다.
  - 탐지 경로: 허니팟 탐지(5분)는 경로의 마지막 실행, 노드 · 관제 탐지(1분)는 규칙 버전마다 15분 넘게 실행이 없다. 24시간 안 기록이 없어도
    멈춤이다. 1분 쪽 버전을 은퇴시키면 그 경보가 최대 24시간 남는다.
  - 적용 실패 · 관문 불일치: 지점별 적용 실패나 관문 불일치가 1건 이상이다. 차단 목록(S-06)으로 잇는다.
  - 노드 수신: 활성 노드(등록 대기 · 폐기 제외)가 모두 10분 넘게 수신이 없다. 수집 노드(S-08)로 잇는다.
- 배치: 보호 대상 카드는 최소 22rem 으로 폭에 맞춘다. 1440 화면(본문 1184px)에서 한 줄 최대 3장이고, 더 넓으면 더 놓인다.
  **모바일은 대상마다 한 줄(이름 · 수집 상태 · 미판정)로 접어** 먼저 처리할 사건이 첫 화면에 남게 한다. 관측 센서 · 관제 시스템은 모든 폭에서 접어 둔다.
- 등록 노드 (2026-09-29 보충, 이슈 #64): S-08 에 등록한 노드 가운데 폐기가 아니고 고정 대상과 id 가 겹치지 않는 것을 보호 대상 묶음의 web-01 뒤(node_id 순)에
  web-01 과 같은 틀로 더한다(지표를 보내면 자원 지표, 아니면 미수집). 이름은 hostname(없으면 node_id)이라 비신뢰 문자열로 그리고 역할 옆에 node_id 를 붙인다.
  그 노드 발생원의 사건은 '장비 미확인' 에서 빠진다.
- 사이드바 · 상단바: 사이드바(모바일은 상단바 · 서랍)에 관제 이상 요약('관제 이상 n' · '관제 상태 일부 미확인' · '관제 이상 없음' · '관제 상태 확인 불가')을
  두고 누르면 이 화면으로 온다. 상단 '실시간 통보 연결' 은 웹소켓 연결만 뜻하며 수집 · 탐지가 정상이라는 뜻이 아니다.
- 새 사건 알림: 보호 대상 장비가 확인된 사건만 오른쪽 아래에 최대 3장 띄운다(규칙 범위 · 대체 추정은 띄우지 않는다). 같은 규칙 · 출발지는 처음 뜬 때부터
  60초 동안 한 장으로 묶어 건수를 늘리고, 재접속 · 재동기화 뒤에도 같은 사건을 다시 띄우지 않는다. 탭이 숨은 동안 띄운 수는 탭 제목에 붙인다.
- 규칙별 비조치율 표는 S-07 규칙 화면으로 옮긴다(대시보드에는 링크만).

**CVE 배지 (S-03 · S-04 공통)**: 서명 규칙 사건에 'CVE n · KEV m · 해당 | 비해당 | 미확인' 을 붙인다. 판정값 · 심각도와 섞이지 않게 정보 색 ·
둥근 테두리로 그린다. 공개 정보가 48시간 넘게 오래됐으면 비해당을 미확인으로 읽는다. 목록 · 카드 · 상세가 같은 서버 계산을 쓴다.

### 3.2 보호 대상 장비 최근 로그 (2026-09-30 보충, 이슈 #73)

- 경로 · 여는 곳: `/devices/:id/logs`(메뉴에는 없다). 보호 대상 카드 맨 아래 '사건 보기 · 최근 로그' 와 사건 상세의 확인된 보호 대상 배지에서 연다.
  상세에서는 판정 소요 시간이 다시 시작되지 않게 새 탭으로 연다.
- 범위: web-01 · 등록 노드만 본다(그 밖은 404). 발생원은 관문이 토큰으로 증명한 node_id(web-01 은 'web-01')이고 줄 속 호스트명은 믿지 않는다.
  웹 접근(nginx) · SSH 인증(sshd)의 실제 줄(real)만, 최근 7일 최신 100줄을 5초마다 다시 받아 줄 id 로 합친다. 필터는 로그 종류 · 출발지 IP · 응답 코드다.
  권한은 로그인한 모든 역할이다.
- 가림: API 응답에서 가린다. 비밀번호 열은 읽지 않고 있었는지만 보인다. 비밀 키의 값 · Bearer · Basic · URL 사용자 정보 · 토큰 모양(긴 16진 · base64 ·
  JWT)은 '…(가림)', URL 쿼리 값과 '=' 없는 조각 · 키 모양이 아닌 조각은 '…' 로 바꾼다. 경로와 SSH 사용자 이름은 보이되 그 안의 비밀 · 토큰 모양은 가린다. 쿼리 속 공격
  문자열도 가려진다. 사건 상세(5장 ① 근거 표본 · ② · ④)도 보호 대상 장비 줄은 서버에서 같은 규칙으로 가리고 허니팟 · 디코이 · 관문 줄은
  공격 증거라 원문 그대로 둔다(권한 · 비밀번호 열 처리도 같다).
- 시각 네 가지를 따로 둔다: 마지막 적재(nodes.last_loaded_at) · 로그 종류별 마지막 줄(nodes.receipt) · 마지막 탐지(이 장비의 1분 탐지 규칙 버전
  w2 · c1 · sg1 가운데 가장 오래된 값, 하나라도 15분 넘게 멈추면 '멈춤') · 화면 갱신(응답 as_of). 계산 기준은 ⓘ 에 둔다.
- 한계:
  - 로그는 1분 적재 회차로 들어오고 사건은 그 뒤 탐지 회차에서 생긴다. 5초는 화면이 다시 받는 주기이지 줄이 들어오는 주기가 아니다.
  - 한 회차에 100줄보다 많이 들어오면 사이 줄을 건너뛴다. 화면은 '이 사이 줄이 빠졌을 수 있음' 으로 알린다.
  - 늦게 도착한 줄은 최신 100줄 안에 들 때만 보인다. 시각이 5분 넘게 앞선 줄은 목록에서 빼고 건수만 본문에 적는다.
  - 로그 종류별 마지막 줄 시각에는 목록에 없는 줄(시험 · 형식 밖 · sshd 외)도 들어가 맨 윗줄보다 새로울 수 있다.
  - 숨은 문자 · 퍼센트 부호로 쪼갠 키, 이름 칸에 잘못 친 비밀번호, UUID, 40자 미만 base64 는 모양으로 잡지 않는다.
  - 24시간 넘게 멈춘 탐지 버전은 마지막 탐지 판정에서 보이지 않는다.

## 4. S-03 인시던트 목록

| 항목 | 내용 |
|---|---|
| 기본 정렬 | **미판정 경과 시간 내림차순** (심각도순이 아니다) |
| 열 | 경과 시간 · 심각도 · 규칙 · 관측값 · 출발지 · 상태 · 담당. '출발지 · 대상' 칸 아래 줄에 장비(장비 · 로그 종류, 여러 개면 보호 대상 먼저, 대체 추정은 장비 미확인)를 둔다 |
| 담당 | "맡기"로 담당을 표시한다. 두 사람이 같은 건을 동시에 여는 판정 충돌을 미리 막는다 |
| 경과 색 | 심각도별 판정 목표 대비. 주황은 2/3 경과, 빨강은 위반 |
| 필터 | 상태 · 심각도 · 규칙 · 장비 · 기간. 장비는 쪽을 나누기 전에 거르고 전체 수는 중복 없이 센다(여러 장비에 걸친 사건도 한 건). 선택지 끝에 '장비 미확인' 을 둔다 |
| 실시간 | 새 인시던트는 웹소켓으로 상단에 추가. 화면을 새로 고치지 않는다 |

상위 심각도 알림에 흡수된 건은 기본으로 숨기되 "흡수된 건 포함"으로 볼 수 있게 한다. 숨기기만 하면 사라진 것으로 오해한다.

규칙 번호로 가르는 발생원 분류(허니팟 · 디코이 · 콘솔)는 판정 목표 · 보고서 집계용으로 그대로 둔다(상세 머리 '발생원'). **정상이 없는
환경(허니팟·디코이)과 있는 환경(콘솔)의 수치를 섞어 보지 않기 위해서**다. 섞으면 오탐률이 의미를 잃는다. 장비는 이 분류와 별개로 사건마다
근거에서 계산한다(4.1).

### 4.1 장비 계산 방식과 한계 (2026-09-30 보충, 이슈 #72)

**기존 근거로 관련 장비를 계산해 제공한다(저장하지 않음).** 목록 · 상세 · 먼저 처리할 사건 · 대상 카드 수가 조회할 때마다 같은 계산을 쓰고,
붙인 장비마다 근거를 셋 가운데 하나로 단다.

| 근거 | 정하는 법 | 예 |
|---|---|---|
| 확인 | 사건이 직접 가리킨다. 대상 열(노드 · 사용자), 근거 발생원(evidence.sensors), 탐지와 같은 범위에서 찾은 이벤트 · 세션의 발생원 | R301 → 그 노드, R201 → 관제 콘솔, 이벤트로 고른 R101 |
| 규칙 범위 | 규칙 정의의 발생원이 한 장비뿐이다 | 허니팟 규칙(R001 · R003 · R004 · R006) → Cowrie, R103 → 웹 디코이, R202 → 데이터 노드 |
| 대체 추정 | 근거로 장비를 고르지 못해 규칙상 그럴 수 있는 장비로 돌린 값이다. 카드 수 · 장비 필터에 넣지 않는다 | 아래 세 경로 |

- 목록 · 카드 · 먼저 처리할 사건은 확인과 규칙 범위를 같은 배지로 보이고, 상세에서만 근거 글자를 붙인다. 대체 추정만 있거나 아무 장비도 고르지 못한
  사건은 '장비 미확인' 으로 보이고, 추정한 장비 이름은 상세 ⓘ 에만 적는다.
- 대체 추정 경로는 셋이다.
  1. 발생원이 섞인 규칙인데 이벤트를 고르지 못하면 등록 노드 없이 정한 web-01 로 돌린다. 등록 노드가 있을 때의 n1 R101 뿐이다
     (노드 에이전트 이벤트는 web-01 과 등록 노드가 함께 낸다).
  2. 세션 규칙(R002)인데 세션을 고르지 못하면 Cowrie 로 돌린다. AWS 센서는 규칙 범위로 남는다.
  3. 기준선 규칙(R005)은 Cowrie 로 돌린다. 탐지가 Cowrie · 디코이 · 콘솔을 함께 세므로 한 장비 규칙이 아니다.
- 카드 수 · 장비 필터는 확인 ∪ 규칙 범위로 센다. 그래서 카드 '미판정 N' 과 그 장비로 거른 미판정 목록의 전체 수가 같다. 매핑이 노드 카드 · 규칙 정의 ·
  이벤트에 기대므로 같은 기준 시각에서만 같다. 카드와 목록은 따로 조회하므로 그 사이 적재 · 판정이 있으면 다를 수 있다.
- 카드 수가 바뀌는 경우(#72 전과 비교):
  - R005 는 AWS 센서 · Cowrie 에서 빠져 '장비 미확인' 으로 간다.
  - 세션을 고르지 못한 R002 는 AWS 센서에는 남고 Cowrie 나눔에서만 빠진다.
  - 등록 노드가 있을 때 이벤트를 고르지 못한 n1 R101 은 web-01 에서 빠져 '장비 미확인' 으로 간다.
  - 대상별 대응의 '정책상 차단 제외' 도 같은 기준으로 세므로 대체 추정 사건의 출발지는 빠진다(등록 노드가 있을 때 이벤트를 고르지 못한
    n1 R101). 보고서의 대상별 대응도 같다.
- 로그 삭제 · 재적재, 규칙 정의 변경, 노드 등록 · 폐기가 있으면 같은 사건의 장비가 달라질 수 있다.
- evidence.sensors 는 요청 경로 서명(url_signature) 규칙만 남긴다. 그 밖의 섞인 규칙은 이벤트로 고른다.

## 5. S-04 인시던트 상세

판정에 필요한 것을 한 화면에 모은다. 다른 화면으로 이동하게 만들면 그만큼 판정 비용이 는다.

| 구역 | 내용 |
|---|---|
| ① 규칙이 본 것 | 규칙 조건, 관측값, 임계치, 통합된 신호 수 |
| ② 규칙이 보지 않은 증거 | 같은 구간·같은 출발지의 **실제 행위** (명령, 파일, 경유 시도, 요청 경로) |
| ③ 행위자 이력 | 최초 관측일, 누적 발생, 다른 규칙 탐지 여부, **허니팟·디코이 접속 이력**, 차단 이력 |
| ④ 원문 로그 | 판단 근거가 된 원본 줄. 요약이 아니라 원문(보호 대상 장비 줄은 3.2 규칙으로 가리고 허니팟 · 디코이 · 관문 줄은 그대로) |
| ⑤ 조치와 판정 | 조치 버튼과 판정 패널 (S-05) |

②가 이 화면의 핵심이다. 규칙이 본 것만으로 판정하면 **규칙의 시야를 그대로 물려받는다.**

③의 허니팟·디코이 접속 이력은 결정적 근거다. 그 자산에 접근한 IP가 정상 사용자일 가능성은
사실상 없다.

기획안(2.4 M4)의 상세 화면 요구를 함께 반영한다.

| 구역 | 내용 |
|---|---|
| 이 규칙 | 최근 오탐률 · 비조치율 · 제안 뒤집힘, 같은 규칙 · 비슷한 관측값의 과거 판정 |
| 발생 전후 변경 | 앞 24시간의 배포 · 백업 · 규칙 변경. 외부 유입 때문인지 우리가 바꾼 것 때문인지 가른다 |
| 추천 조치 | 규칙별 런북. 확인 절차 · 1차 조치 · 넘기는 기준 |
| 대조군 | 약 10% 는 제안을 가리고, 판정 후에 공개한다 |
| 담당 · 목표 | 머리글에 담당자와 판정 목표 초과 시간을 보인다. 담당 해제도 여기서 한다 |
| 증거 고정 | ② 의 행을 근거로 고정하면 판정과 함께 저장된다. 판정이 어느 로그를 보고 내려졌는지 남는다 |
| 예외 제안 | 오탐 · 무시 가능을 고르면 "이 건으로 예외 제안"이 S-07 조정 제안에 초안으로 올라간다 |
| 런북 | 확인 · 1차 조치 · 넘기는 기준을 체크리스트로. 체크는 이력에 남는다 |

**순환 경고**: R002·R003·R004 처럼 판정 근거와 규칙 조건이 겹치는 규칙은 화면에 그 사실을
표시한다. 이 규칙들에서는 정탐률이 품질 지표가 되지 못하며, 중복률을 대신 본다.

## 6. S-05 판정 패널

### 6.1 판정값 — 세 개에서 다섯 개로

관측결과 7장에서 세 값으로 분류할 수 없는 사례가 확인되었고, 디코이 가동 첫날에도
같은 사례가 나왔다(자기 정체를 밝힌 조사 기관 스캐너).

| 값 | 뜻 | 처방 |
|---|---|---|
| `threat` | 실제 위협 | 조치 |
| `non_actionable` | 규칙은 맞았으나 조치 불필요 | 임계치 또는 중복 |
| `false_positive` | 규칙이 겨냥한 현상이 아님 | 조건 수정 |
| `benign_positive` **(신설)** | 정확히 탐지했고 악의도 없음 (조사 기관 스캐너 등) | 규칙 수정 없음. 오탐으로 세지 않는다 |
| `undetermined` **(신설)** | 근거 부족 | 판정하지 않는다. 지표에서 제외 |

신설 두 값은 **오탐률의 분자에 들어가지 않는다.** 조사 기관 스캔을 오탐으로 세면 규칙 정확도가
실제보다 낮게 집계되어 불필요한 규칙 수정을 부른다.

**화면 표기**는 판정 기준 문서를 따른다. 실제 위협 · 무시 가능 · 오탐 · 양성 정탐 · 미결. 화면마다 다른 말을 쓰지 않는다.
순환 규칙(R002 · R004)에는 "무시 가능 · 중복" 제안만 허용한다. 계산으로 확정되는 값이기 때문이다.

### 6.2 자동화 편향 완화

1회차에서 일괄 수락을 썼기 때문에 제안 수용률 100%가 기준이 타당해서인지 확인 없이
수용해서인지 구분되지 않았다. 화면에 세 장치를 넣는다.

| 장치 | 화면에서의 모습 |
|---|---|
| 제안 신뢰도 공시 | "이 유형 제안의 과거 수용률 87% (23건 중 20건)" |
| 일괄 수락 제한 | 계산으로 확정되는 중복 판정에만 허용. 행위 근거 제안은 개별 확인 |
| 대조군 | 일부 건은 제안을 가린 채 판정. 나중에 제안과 대조 |

`false_positive` 는 제안하지 않는다. 규칙이 틀렸다는 판단을 규칙을 만든 쪽이 스스로 내릴 수 없다.

### 6.3 기록

판정 시 함께 저장: 판정자 · 시각 · **판정 소요 시간** · 제안값 · 관측값 · 근거 메모.
소요 시간이 있어야 "판정 비용이 줄었다"를 수치로 말할 수 있다.

## 9. S-08 수집 노드 · S-13 노드 추가

**파이프라인 상태**: 원문 수신 · 적재 · 탐지 · 통보 네 단계의 마지막 시각과 지연(목표 탐지 30초 · 통보 10초)을
나란히 둔다. 끝에서부터 거꾸로 짚으면 끊긴 구간이 보인다. 네 시각은 기준선 하향 이탈의 감시 대상이다.

**점검 모드**: 점검하는 노드의 **통보만 묶고 수집과 탐지는 계속한다.** 점검 시간은 공격자가 숨기 좋은 틈이라
인시던트는 그대로 쌓는다. 종료 시각은 필수이고 최대 4시간이다. 만료 10분 전에 알리고, 끝날 때 여전히 이상이면
그 자리에서 다시 통보한다. 시작과 해제는 admin 이 하며 감사 기록에 남는다.

**콘솔 분배**: 콘솔 A/B 를 부하분산에서 빼고 넣는다(admin). 빼기는 진행 중 요청을 마친 뒤, 넣기는 연속 정상
3회 뒤 가중치를 단계적으로 올린다. 무중단 배포와 장애 시연에 쓴다.

| 항목 | 내용 |
|---|---|
| 노드 상태 | 정상(10분 이내 수신) · 지연(10분 초과) · 대기(토큰 발급 · 첫 수신 전) · 폐기(토큰 회수) |
| 미등록 에이전트 | 등록되지 않은 토큰의 수집 시도는 거부하고 인시던트로 올린다 |
| 구성 카드 | 세그먼트와 수신 경로. 연결을 여는 방향만 화살표로 표시한다 |

노드 추가(S-13)는 네 단계다. **대상 정보 → 수집할 로그 → 토큰 발급 · 설치 → 첫 수신 확인.**

- 콘솔은 토큰만 발급하고, 설치는 관리망의 Ansible 플레이북이 한다. 수집 설정을 손으로 고치지 않는다.
- 노드 추가와 토큰 발급은 관리자만 한다.
- 토큰은 1시간 · 1회용이며 발급 시 한 번만 보여 주고 해시만 저장한다. 취소하면 발급한 토큰을 폐기한다.
- 명령에는 토큰 원문 대신 환경 변수를 쓴다. 셸 이력에 남지 않게 하기 위해서다.
- 첫 수신 확인은 에이전트 등록 · 첫 로그 · 형식 변환 · 규칙 적용을 차례로 검사한다. 전부 통과해야 완료다.
- 인증 · 웹 접근 로그는 이벤트 ID 형식이 같으므로 R101 · R102 를 그대로 적용한다. R002(로그인 성공 + 명령)는
  정상 사용자가 없는 허니팟 전제의 규칙이라 보호 자산에는 적용하지 않는다.

시연 대상은 서비스망에 새로 띄우는 **보호 대상 서버 web-01** 이다. 콘솔을 대상으로 등록할 수도
있으나, "새 서버를 관제에 붙인다"는 장면이 분명하지 않다.

| 끊김 경로 | 데이터 연결 끊김은 DB 를 거치지 않는 헬스체크가 웹훅을 직접 호출한다. DB 가 죽으면 DB 를 거치는 통보도 멈추기 때문이다 |
| 관제 자기 탐지(R2xx) | 심각도와 무관하게 즉시 호출. 24시간 신고 판단 기한이 걸린다 |
| 사건 | 새 인시던트 · 미판정 경과 · 센서 수신 끊김 · 데이터 연결 끊김 · 미등록 에이전트 접속 · 보고서 생성 |
| 묶음 | 같은 사건은 묶음 시간 안에 한 번만 보낸다. 미판정은 1회 후 매일 09:00 요약 |
| 재시도 | 1분 · 5분 · 15분. 결과를 발송 이력에 남긴다 |
| 권한 | admin 만 수정. 웹훅 주소는 비밀값이라 끝 4자리만 보인다 |

등급은 심각도가 아니라 **받는 사람이 지금 할 일이 있는가**로 정한다(기획안 7.3).

**저장 전 확인**: 지난 7일에 이 설정이었다면 몇 건을 보냈고 그중 밤 호출이 몇 건인지 먼저 보여 준다.
리플레이 평가와 같은 엔진을 쓴다. 불필요한 호출이 반복되면 받는 사람이 채널을 끄고, 그때 관제가 멈춘다.

메시지에는 번호 · 심각도 · 규칙 · 건수 · 런북(확인 · 1차 조치 · 넘기는 기준) · 콘솔 링크만 넣는다. 원문 로그 · 입력된 비밀번호 ·
내부 주소는 외부 서비스로 보내지 않는다. 카카오톡은 사업자 채널 심사와 토큰 갱신 문제로 제외한다.

### 13.1 계정 관리 (2026-09-29 보충, 이슈 #59)

관리자가 관제사 · 조회자 계정의 역할과 활성 상태를 화면에서 바꾼다. 화면은 "이 계정이 지금 무엇을 할 수 있는가" 를 답하고,
바꾸면 그 계정의 열린 세션이 끊겨 바뀐 권한으로 다시 로그인하게 한다. 관리자로 높이는 일 · 계정 추가 · 비밀번호 · 삭제는 만들지 않는다.
콘솔이 뚫려도 스스로 관리자가 될 수 없는 경계를 명령줄에 남기기 위해서다.

> 2026-09-29 이슈 #63 보충: 관제사 · 조회자의 추가(표 위 양식, 비밀번호 두 번) · 비밀번호 재설정 · 삭제(판정 · 조치 · 로그인 기록이 없는 계정만)를
> 화면에서도 한다(행의 줄 안 확인). 관리자 계정 · 관리자 부여 · 본인 변경은 그대로 명령줄이며, 비밀번호는 서버가 해시하고 화면 캐시 · 주소 · 감사에 남지 않는다.

| 일 | 화면 (관리자) | 명령줄 (`auth.py`) | 거부하는 곳 |
|---|---|---|---|
| 관제사 ↔ 조회자 역할 변경 | 가능 | 가능 | DB 함수가 관리자 대상 · 관리자로 올리기 · 본인을 거부 |
| 비활성 · 재활성 (관제사 · 조회자) | 가능 | 가능 | 같음 |
| 관리자 부여 · 해제, 관리자 계정 비활성 · 재활성 | 없음 | 가능 | 마지막 활성 관리자는 낮추거나 비활성할 수 없음 |
| 계정 추가 · 비밀번호 재설정 | 관제사 · 조회자만 (#63) | 가능 | 아이디 형식 검사, 비밀번호 12 ~ 256자. 관리자 추가 · 관리자 대상 · 본인은 DB 함수가 거부 |
| 삭제 | 이력 없는 관제사 · 조회자만 (#63) | 없음 | 판정 · 조치 · 로그인 기록이 있으면 거부(주체가 사라지므로 비활성으로 막는다) |

- **표**: 아이디 · 역할(관제사 · 조회자 · 관리자) · 상태(활성, 비활성이면 그 시각) · 마지막 로그인 · 변경 시각 · 동작. 변경 시각은 역할 · 활성 ·
  비밀번호가 마지막으로 바뀐 때이고 그보다 먼저 받은 세션은 쓸 수 없다. 아이디 순이며 30초마다 다시 조회한다. 모바일은 한 계정을 한 칸으로 쌓는다.
- **동작**: 행마다 '조회자로 낮추기' / '관제사로 바꾸기' 와 '비활성' / '재활성'. 누르면 행 아래에 확인 양식을 펼친다(모달 없음, S-06 차단 해제와 같다).
  양식은 무엇이 일어나는지 한 문장으로 적고, 할 수 있는 일을 줄이는 확정(낮추기 · 비활성)은 위험색, 늘리는 확정은 기본색이다.
- **세션**: 역할 변경 · 비활성은 그 계정의 열린 세션을 끊는다. 다음 요청부터 로그인 화면으로 가고 실시간 연결은 30초 안에 끊긴다. 확인 문장에 이 사실을 적는다.
  재활성해도 비활성 전 세션은 되살아나지 않는다.
- **잠금 표시**: 관리자 계정은 '명령줄에서만 변경', 로그인한 본인은 '본인 계정' 을 버튼 대신 보인다. 숨기지 않고 까닭을 보인다(15장 원칙).
  서버가 같은 규칙으로 다시 거부하므로 화면 잠금은 편의일 뿐이다.
- **결과**: 적용 · 이미 그 값(바뀐 것 없음) · 실패를 화면 위 띠로 알린다. 서버가 거부한 까닭은 서버 문장을 그대로 보인다. 응답을 받지 못하면(시간 초과 ·
  연결 끊김 · 5xx) 적용됐을 수 있다고 알리고 다시 받은 목록을 보게 한다. 처리 중에는 두 번 보내지 않고 다른 행의 버튼도 막는다.
- **감사**: 추가 · 역할 변경 · 비활성 · 재활성 · 비밀번호 변경(사실만) · 삭제가 감사 기록(S-14)에 한 줄씩 남고 대상 아이디로 찾는다. 화면 · 명령줄 ·
  DB 직접 변경을 같은 트리거가 남기며, 같은 값으로 다시 설정하면 남지 않는다.

**명령줄 안내 (S-15 아래 카드)**: 관리자 계정 추가 · 관리자 부여와 해제 · 비밀번호 재설정 · 관리자 비활성과 재활성 · 목록 명령의 모양을 보인다.
접속 주소 · 비밀번호는 싣지 않는다. `--by` 에 적은 이름이 감사 기록의 행위자(`cli:이름`)가 된다.

## 15. 상태와 권한

**상태 전이**: `신규 → 확인 → 조치중 → 종결`. 차단을 요청하면 조치중이 되고, 종결은 판정이 기록될 때만 일어난다. 판정은 종결 시점에 기록한다.
판정 없이 종결할 수 없다. 판정이 폐루프의 입력이기 때문이다.

**권한** (S-15 에서 부여하고 코드에서 검사)

| 역할 | 판정 · 차단 요청 | 차단 해제 · 연장 · 규칙 억제 · 승인 | 알림 · 노드 토큰 · 콘솔 분배 · 계정 | 감사 기록 열람 |
|---|---|---|---|---|
| 조회자 | 불가 | 불가 | 불가 | 불가 |
| 관제사 | 가능 | 불가 | 불가 | 불가 |
| 관리자 | 가능 | 가능 | 가능 | 가능 |

권한 밖의 동작은 숨기지 않고 흐리게 보인다. 무엇이 있는지는 알되 누를 수 없게 한다.
노드 토큰을 관리자에게 두는 이유는 토큰이 있으면 가짜 에이전트로 탐지 입력을 오염시킬 수 있기 때문이다.

되돌리는 행위와 기준을 바꾸는 행위를 분리한다.

## 19. S-09 출발지 분석 (2026-09-29 보충, 이슈 #58)

사건을 출발지 단위로 모아 "누가 얼마나 오래 무엇을 노렸고 지금 막혀 있는가" 를 답한다. 판정은 여전히 사건마다 하고, 이 화면은 조사 참고용이다.

| 탭 · 화면 | 내용 |
|---|---|
| 출발지 목록 | 사건 · 미판정 · 최고 심각도 · 규칙 · 노린 대상 · 판정 분포 · 차단 상태(관문 · 내부 방화벽) · 첫/마지막 시각. 시험 대역 · 차단 제외 대역 표시. 주소 앞부분 검색 · 정렬 세 가지 |
| 출발지 상세 | 요약, 사건 흐름(규칙 버전 포함), 이벤트 종류별 수, 이 주소가 쓴 도구 지문, 차단 상태, 차단 · 해제 조치 이력, 사건 목록으로 이동 |
| 도구 지문 | HASSH(`cowrie.client.kex`) · SSH 클라이언트 버전(`cowrie.client.version`) · 디코이 User-Agent 별 출발지 · 연결 · 사건 있는 출발지 수 |

- 도구 지문은 이벤트 메시지에서 꺼낸다(표 변경 없음). 흔한 라이브러리(Go · libssh · paramiko)는 지문이 겹치므로 같은 지문이 같은 행위자라는 뜻이 아니라는 안내를 늘 붙인다.
  지문 값 · User-Agent · SSH 버전은 공격자가 넣은 글자라 비신뢰 문자열로 그린다.
- 지문을 누르면 그 지문을 쓴 출발지 목록으로 간다. 지문 묶음은 시험 대역도 세므로 이때는 목록도 시험 대역을 넣어 수를 맞춘다.
- 차단 상태는 사건 상세와 같은 문구를 쓴다. 집행기 확인이 멈추면 '적용 확인' 을 '확인 지연' 으로 보인다.
- 감사 기록의 차단 이력(행위자 포함)은 admin 전용 정보라 싣지 않고 사건 조치 기록만 보인다. 선행 관측(13장 끝)은 이번 범위 밖이다.
- 운영 자료(2026-09-29 조회): HASSH 48종 가운데 한 값을 출발지 173곳이 같이 썼다(09-28 백업 기준 그중 171곳에 사건). 주소 단위로는 173개 행이지만 도구 단위로는 한 묶음이다.
