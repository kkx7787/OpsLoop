# 성공 백업 기록의 확인 불가 감시 (#111)

기존 진입점 감시는 마지막 성공 시각이 10시간 넘게 오래되면 알렸지만, 성공 줄이 처음부터 없거나 기록을 읽지 못하면 조용히 넘어갔다. 백업 실행기까지 돌지 않는 상황에서 놓치는 경고였다.

이제 매 회차에서 다음을 구분한다.

| 조건 | 동작 |
|---|---|
| 기록 파일 누락·읽기 실패·성공 줄 없음·시각 해석 실패 | `OpsLoop DB 백업 확인 불가` 한 번 |
| 성공 시각이 지금보다 5분 넘게 미래 | 같은 제목으로 시계 확인 사유를 알림 |
| 유효한 성공 시각이 10시간 초과 | 기존 `OpsLoop DB 백업 오래됨` 한 번 |
| 기록을 다시 정상적으로 읽음 | 확인 불가 상태를 풀고 그 시각의 오래됨 여부를 다시 판정 |
| 점검 창 | 알림을 미루고, 창이 끝나도 문제가 남아 있으면 발송 |

기록 누락과 미래 시각은 별도로 중복을 막는다. 확인 불가가 이어지는 동안 매분 같은 알림을 보내지 않는다. 미래 시각은 마지막 유효한 성공 시각을 덮어쓰지 않는다. 복구는 기록 파일에 남기며 별도 백업 복구 알림은 추가하지 않는다. `--status`는 조회만 하고 확인 불가 사유를 보여 준다. 예전 상태 파일에 새 `backup_problem` 항목이 없어도 읽을 수 있다.

## 반영

TLS 전환과 함께 새 `console-watch.sh`를 기존 `install-console-watch.sh`로 설치해야 한다. launchd는 저장소 파일이 아닌 설치 사본을 실행한다. 기존 URL/CA 파일을 확인하고, 점검 창에서 사본을 교체한 뒤 `--status`와 기록을 확인한다. 이 변경을 아직 운영 Mac에 설치하지 않았다.

백업 일정을 바꾸거나 백업을 지우는 작업은 없다. `caffeinate`는 이미 시작한 백업의 잠자기 중단을 줄이는 장치이며 예약 실행이나 꺼진 Mac에서의 알림을 보장하지 않는다. 같은 Mac 밖의 감시가 필요하다는 한계는 그대로다.

## 검증

`infra/vmware/scripts/test_console_watch.py`는 임시 HOME·가짜 알림 실행기·가짜 launchctl과 루프백 시험 서버를 쓴다. 외부 Teams나 실제 macOS 알림을 보내지 않는다. 누락/중복 억제/정상 기록 복귀/미래 시각/유효하지 않은 날짜/읽기 실패/점검 창/기존 오래됨을 검증한다. 증거는 `docs/evidence/2026-10-03-backup-observation/`에 둔다.

연계 문서인 README에도 #109의 구현 완료/운영 미설치와 #111 설치 이후의 알림 범위를 구분해 반영했다. 기존 시점의 측정 결과를 새 배포 결과로 바꾸지 않는다.
