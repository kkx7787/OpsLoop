# 계획 개정 — 2차 피드백 반영

작성일 2026-09-18 · 대상 `OpsLoop_WBS_v2.0.xlsx` · 선행 문서 `docs/OpsLoop 문서 정리/교수님 2차 피드백.txt`, `OpsLoop_허니팟_구성타당성.docx`

프로젝트의 목표와 폐루프 구조는 바뀌지 않는다. 바뀌는 것은 **공격 로그를 어디서 받는가**이며,
그 변경이 검증 설계와 남은 일정에 어떤 영향을 주는지를 이 문서에 남긴다.

---

## 1. 무엇을 지적받았나

| 지적 | 읽은 대로의 요지 |
|---|---|
| 허니팟을 클라우드에 단독으로 둔 구성은 처음 본다 | 센서가 내 방어 구조 **밖**에 떠 있다 |
| 내부 세그먼트 안에 있어야 한다 | 관문을 통과해 들어온 트래픽이어야 한다 |
| 디코이를 만들어서 파야 한다 | 관찰용 센서가 아니라 **내 자산처럼 보이는 미끼**가 필요하다 |
| 관문 방화벽에 별도 통로를 내고 8080 포트와 admin 계정을 살려 둔다 | 웹 계층의 디코이를 경계 뒤에 배치하라 |
| 수집된 것이 실효적인 공격 로그가 맞는가 | 배경 소음과 내 구조를 겨냥한 접근을 구분하라 |
| 굳이 클라우드가 필요한가 | 클라우드 사용 범위를 필수 요건으로 축소하라 |

## 2. 구조 변경

### 2.1 바뀌기 전

```
인터넷 ──▶ 허니팟(공인 IP, 단독 노출)
인터넷 ──▶ 앱 노드(관제 콘솔 + DB)          ← 같은 서브넷, 같은 기본 VPC
허니팟 ──5432──▶ 앱 노드 DB                  ← 센서가 DB 자격증명을 보유
```

### 2.2 바뀐 뒤

```
[AWS — DMZ 구간, 상시 가동]
인터넷 ──▶ 관문 방화벽(공인 IP)
              ├─ 22 · 23 ──▶ Cowrie (SSH 허니팟)
              ├─ 8080 ─────▶ 웹 디코이 (가짜 admin 로그인)
              └─ 그 외 차단 · 기록
                      │ 올리기만 가능
                      ▼
                     S3
                      │ 내부가 가져간다
[온프레미스 — VMware, 인터넷에서 도달 불가]
                      ▼
      내부 방화벽 ── 데이터 VM (수집 · 탐지 · PostgreSQL · Loki)
           └─ HAProxy ──▶ 콘솔 A · 콘솔 B ──▶ 담당자
```

### 2.3 변경의 근거

| 항목 | 근거 |
|---|---|
| 허니팟을 관문 뒤로 | 경계를 통과해 들어온 트래픽만 "내 구조를 겨냥한 접근"이라 부를 수 있다 |
| 웹 디코이 신설 | 허니팟은 SSH, 콘솔은 HTTP 라서 **규칙을 옮겨 검증할 수 없었다.** 디코이를 콘솔과 같은 인증 로그 형식으로 만들면 리플레이가 성립한다 |
| 클라우드는 DMZ만 | 클라우드가 필요한 조건은 공인 주소와 24시간 가동 두 가지뿐이다. 보호 대상인 내부망은 가상화로 옮긴다 |
| S3 단방향 유지 | 센서는 내부망의 주소를 알지 못한다. 현행 구성에서 센서가 DB 자격증명을 들고 있던 문제도 함께 해소된다 |
| 내부는 상시 가동하지 않아도 됨 | 수집은 DMZ와 S3에서 계속된다. 내부가 꺼져 있던 구간은 재가동 시 소급 적재한다 |

## 3. 검증 설계의 변경

기존 설계는 **허니팟에서 재현율, 콘솔에서 오탐률**을 측정하는 구성이었다. 그러나 두 로그의
종류가 달라 한쪽에서 만든 규칙을 다른 쪽에 적용할 수 없었다. 이 문제를 디코이가 해결한다.

| 환경 | 로그 성격 | 측정 대상 | 규칙 이동 |
|---|---|---|---|
| Cowrie 허니팟 | SSH · 전부 공격 | 침해 이후 행위, 배경 소음 기준선 | SSH 규칙군 |
| **웹 디코이 (신설)** | HTTP 인증 · 전부 공격 | **재현율** — 놓친 공격이 있는가 | 웹 규칙군을 여기서 도출 |
| 관제 콘솔 | HTTP 인증 · 정상 사용 | **오탐률** — 정상을 잡았는가 | 도출된 규칙을 여기에 리플레이 |

디코이와 콘솔이 **같은 인증 로그 형식**을 쓰는 것이 이 설계의 전제다. 그래서 디코이는 기존
웹 허니팟 제품을 쓰지 않고 콘솔과 같은 스택으로 직접 만든다.

## 4. 기능 범위

### 4.1 추가

| 기능 | 영역 | 비고 |
|---|---|---|
| 관문 방화벽 (포트 전달 · 차단 로그 수집) | A | 방화벽 로그가 새 로그 소스가 된다 |
| 웹 디코이 (가짜 admin 로그인 · 행위 기록) | B | 로그인 이후 단계를 관측한다. 실제 기능은 없다 |
| 온프레미스 내부망 (VM 4대 · 망 분리) | A | 서비스망 · 데이터망 · 관리망 |
| 내부 방화벽 (세그먼트 간 통제) | A | DMZ에서 내부로 오는 연결을 전면 차단 |
| S3 경유 단방향 로그 반출 | B | 센서는 내부 주소를 모른다 |
| 에이전트 자동 등록 (설치 후 토큰으로 자기 등록) | B | 미등록 에이전트는 알림 대상 |
| 미판정 경과 시간 대시보드 (모바일 대응) | C | 판정 비용을 보이게 하는 지표 |
| 웹 인증 로그 규칙군 (R101~) | B | 디코이에서 도출 |

### 4.2 유지

수집 파이프라인 · 공통 스키마 · 탐지 엔진 · 인시던트 통합 · 판정 도구와 판정 기준 ·
폐루프와 리플레이 평가 · 관제 콘솔 · 콘솔 이중화와 자동 전환 · 만료 있는 자동 차단 ·
통보 · Terraform 기반 인프라 코드화

### 4.3 축소

| 기능 | 조정 |
|---|---|
| 이중화 | 다중 가용영역 → **VM 2대 이중화**. HAProxy 능동 헬스체크는 그대로 |
| 무중단 배포 | 파이프라인 자동화 → **사전 풀 제외 후 순차 재기동 시연**으로 축소 |
| Sigma 규칙 | 전면 재작성 → 규칙 파일에 **필드 구조만 차용** |
| 관측성 | Prometheus · Node Exporter는 **선택 항목**으로 내린다 |
| 문서 산출물 | 18종 → **16종** |

### 4.4 삭제 · 연기

| 항목 | 사유 |
|---|---|
| CI/CD 파이프라인 (빌드 · 스캔 · 배포 · 롤백) | 단일 운영자 환경에서 남은 기간 대비 효용이 낮다. 테스트 실행만 유지 |
| 주간 보고서 자동 생성 · 발송 | 템플릿과 수동 생성 1회로 대체. 자동화는 향후 과제 |
| 내부망 디코이 노드 (3계층 중 내부 계층) | 웹 디코이로 먼저 성립시킨다. 향후 과제 |
| 부하 시험 | 관제 담당자 1인 환경에서 측정의 의미가 작다 |
| AWS 앱 노드 · 데이터 노드 | 온프레미스로 이전 후 정리 |

### 4.5 검토했으나 채택하지 않은 것

**에이전트 설치의 인공지능 자동화.** 에이전트 자동 배포 자체는 채택한다. 다만 이를 인공지능
기능으로 표현하지 않는다. 실체는 구성 관리 도구와 부트스트랩 스크립트이며, 멱등성과 실패
복구를 설명하지 못하면 기술 면접에서 되물릴 수 있다. 더욱이 **여러 서버에 대한 설치는 본
프로젝트가 "사람 승인"으로 규정한 비가역 조치**에 해당하므로, 자동 실행은 설계 원칙과
충돌한다. 인공지능을 넣는다면 사람이 검토할 초안을 만드는 자리(새 로그 소스의 스키마 매핑
제안)에 한정하며, 판정과 규칙 개정에는 두지 않는다.

## 6. 위험

| 위험 | 대응 |
|---|---|
| 구조 전환 중 수집 공백 | 기존 환경을 먼저 끄지 않는다. 새 경로 검증 후 전환하고, 1주일은 병행 수집한다 |
| 호스트 자원 부족 (메모리 16GB · 디스크 35GB) | VM 4대 약 6GB로 설계. 디스크는 씬 프로비저닝, 로그 보존 기간 단축 |
| 방화벽 배포판의 ARM 미지원 | 리눅스 + nftables 로 구성한다. 설정이 파일이라 형상 관리에 유리하다 |
| 콘솔 화면 미착수 | 임계경로 1순위로 둔다. 판정 화면과 대시보드가 없으면 시연이 성립하지 않는다 |
| 내부망 상시 가동 불가 | 실시간 통보는 운영 시간에 한정하고 문서에 명시한다. 수집은 중단되지 않는다 |
| 전환 중 데이터 유실 | 이전 전 전체 백업과 건수 대조. 전환 후에도 구 환경을 일정 기간 보존한다 |

## 8. 전개 방식 결정 (2026-09-18)

**클라우드에는 DMZ 구간만 두고, 내부망은 가상화 환경에 둔다.**

| 검토안 | 판단 |
|---|---|
| 전부 온프레미스 | 상시 가동과 공인 주소를 확보할 학교 자원을 사용하기 어렵다 |
| 전부 클라우드 | 센서가 경계 밖에 놓이는 기존 문제가 그대로 남는다. 망 분리를 구성도로 보이기도 어렵다 |
| **DMZ 만 클라우드 (채택)** | 필수 요건인 공인 주소와 24시간 가동을 충족하면서, 관문 방화벽 뒤에 센서를 두는 구조가 성립한다 |

근거는 두 가지 요건뿐이다. **공인 주소와 상시 가동.** 이 둘이 필요한 구간은 센서뿐이므로
클라우드 사용 범위를 그 구간으로 한정한다. 보호 대상인 콘솔과 데이터 계층은 가상화로 옮긴다.

수반되는 한계와 처리
- 내부망은 상시 가동하지 않는다. 실시간 통보는 운영 시간에 한정하고, 꺼져 있던 구간은
  재가동 시 소급 적재한다. 수집 자체는 DMZ 와 S3 에서 계속되므로 공백이 생기지 않는다.
- 발표 시연은 내부망이 켜진 상태를 전제로 하며, 전환 시연과 판정 화면은 사전 녹화로도 확보한다.
- 지원 크레딧이 확정되면 허니팟과 디코이를 별도 인스턴스로 분리하고, 사설 구간 관리 접근을
  세션 관리자 엔드포인트로 되돌린다.
