## 조사

### 1. 실패 순간 본문
- 원래 첫 실행: 화면 출력이 7,000자에서 잘렸다. 옆 메뉴까지만 남았다. 같은 화면의 전체 출력은 약 25,000자다(e 실패 기준). 그래서 **원래 실행의 본문은 확인할 수 없다.**
- 추가 e 실패 4회: `<main>` 안은 모두 같았다.
  - '로그인 정보를 확인하는 중입니다' h1 이 든 불러오는 중 카드(`role="status"` · `aria-busy="true"`)였다. `AppLayout.tsx:83-84` 의 `me.isPending` 분기다.
  - 404 제목은 DOM 에 없었다.
  - 가짜 fetch 는 `/api/me` 에 바로 답한다. 그런데 그 응답이 화면에 반영되기 전에 대기가 끝났다.
- testing-library 는 대기 시간이 끝날 때의 DOM 을 찍는다(`wait-for.js` `onTimeout` → `getElementError(…, container)`). 그래서 이 본문은 실패 시각의 상태다.

### 2. 파일 첫 시험의 냉시동
- 404 시험은 파일의 첫 시험이다. 404 경로는 정적 import 다(`router.tsx:9` · 58). 그래서 시험 안에서 모듈을 더 읽지 않는다. 모듈 적재는 파일 import 때 끝나고, 시험 시간에 들지 않는다.
- 냉시동 비용은 첫 렌더와 첫 역할 조회에 있다. 조사용 시험(`micro/micro.test.tsx`)으로 쟀다.
  - 원래 시험과 같은 렌더 · 같은 가짜 응답을 쓴다. `findByRole` 과 같은 `waitFor(getByRole)` 에 계측을 끼웠다.
  - 추가 부하 없이 10회 잰 값이다(중앙값).

| | 그리기 ms | 첫 확인 1회 ms | 404 제목이 DOM 에 생긴 시각 ms | 대기 ms |
|---|---|---|---|---|
| 파일 첫 시험 | 37 | 62 | 116 | 80 |
| 두 번째 · 세 번째 시험 | 12 ~ 16 | 6 | 25 ~ 28 | 17 ~ 18 |

- 그린 직후 본문 h1 은 늘 '로그인 정보를 확인하는 중입니다'다. 404 제목은 `/api/me` 응답을 반영한 다음 그려진다.
- 같은 파일 뒤 시험은 데워져 있다. e 에서 404 시험은 5회 중 4회 실패했지만, 같은 파일의 다른 15건은 모두 통과했다.

### 3. findByRole 비용
- `findByRole` 은 `waitFor(getByRole)` 이고 대기 창은 1,000ms 다.
  - 첫 확인은 대기를 시작하자마자 동기로 돈다.
  - 그동안 이벤트 루프가 막힌다. 그래서 `/api/me` 응답 반영과 404 화면 그리기가 그 뒤로 밀린다.
  - 계측 기록(`check_log`)에서 첫 확인 때와 둘째 확인 때 h1 은 '로그인 정보를 확인하는 중입니다'였다. 404 제목은 셋째 확인에서 잡혔다.
- 첫 확인 비용은 이름 계산 때문이 아니다. 파일 첫 시험에서 확인 방법만 바꿔 각 5회 쟀다(추가 부하 없음, 중앙값).

| 확인 방법 | 첫 확인 1회 ms | 데운 뒤 ms |
|---|---|---|
| `getByRole('heading', { level: 1, name })`(원래) | 59.7 | 6.5 |
| 이름 조건 없이 역할만(`getAllByRole('heading', { level: 1 })`) | 57.4 | 3.1 |
| 숨김 판정 생략(`hidden: true`) | 60.2 | 5.9 |
| `getByText(제목, { selector: 'h1' })` | 10.0 | 3.1 |

- 이름 조건을 빼도, 숨김 판정(계산된 스타일 조회)을 빼도 첫 확인 비용은 거의 같다. 비싼 것은 역할 조회의 첫 호출 자체다. 그 안에서 무엇이 비싼지는 재지 않았다.
- 틀 전체 DOM 은 요소 137개다. 크지 않다.

## 원인 판단

확인한 것:
1. 지정 조건 (a) ~ (d) 53회에서는 재현되지 않았다.
2. 인위 부하에서는 같은 오류가 났다(e 5회 중 4회). 실패 순간 본문은 로그인 확인 중이었다.
3. 파일 첫 시험은 첫 역할 조회가 비싸다. 추가 부하 없이 약 60ms 이고, 데운 뒤의 약 10배다. 이 비용은 1초 대기 창 안에서 치러지고, 부하에 따라 커진다.
4. 첫 실행 때 `tsc -b` 가 함께 돌았다. 전체도 느렸다. 파일 소요 합은 재실행의 약 4.1배다.
5. 같은 위험이 다른 파일 첫 시험에도 있다. f 에서 IncidentsPage 첫 시험이 같은 종류로 실패했다.

추정:
- 첫 실행의 실패도 같은 경로로 보인다. CPU 경쟁이 큰 상태에서 파일 첫 시험의 냉시동 비용(첫 렌더 + 첫 역할 조회)을 치르는 동안, 로그인 확인이 끝나기 전에 1초 대기가 끝났다는 것이다.
- 원래 실행의 본문은 잘려서 직접 확인하지 못했다. 첫 실행 때 부하의 전체 구성도 모른다. 그래서 **확정하지 않는다.**

404 기능에 대해:
- 단독 40회 · 전체 15회(e · f 제외 13회 + f 2회)에서 404 제목이 그려졌다.
- 실패는 모두 '대기 시간 안에 못 찾음'이었다. 다른 화면이 그려진 것이 아니라 로그인 확인 중 화면이 남아 있었다(e).

   - 근거: 조사용 시험에서 yes 64 기준 실패 2/5 → 0/5 였다. 다만 조사용 시험에서 잰 것이고, 실제 시험 파일로는 확인하지 않았다.
   - 대기 한도만 늘리는 것은 명세대로 단독 해결책으로 정하지 않는다.
   - 같은 위험이 다른 파일 첫 시험에도 있다(f 의 IncidentsPage). 한 시험만 고치면 남는다. 고친다면 범위부터 정해야 한다.
3. 조치를 검증하는 기준
   - 조건 e(router.test.tsx 단독 + yes 64개, 5회 중 4회 실패)를 같은 횟수 이상 반복해 실패 0을 본다.
   - 그다음 프런트 전체 시험이 통과하는지 본다(명세 회귀시험 표).

## 한계
- 지정 횟수는 명세(10 · 10 · 10)보다 적다. 이번 지시대로 5 · 5 · 3회다.
- 추가 부하는 `yes` 로 만든 인위 부하다. 첫 실행 때 부하와 종류가 다르다.
- 조사용 시험은 원래 시험을 흉내 낸 것이다. 계측(MutationObserver · querySelector)이 비용을 조금 더한다.
- 파일 순서는 첫 실행 순서로 고정했다. 첫 실행 직전의 결과 캐시는 남지 않아, 원래 순서는 시작 시각으로 거꾸로 만든 것이다.
- 같은 Mac 에서 다른 작업(다른 에이전트 · 가상 머신 5대 · 앱)이 함께 돌았다. 상위 5개 표본에 안 잡힌 짧은 프로세스는 알 수 없다.
- 23:35 ~ 23:45 에 yes 를 띄운 동안 이 Mac 의 다른 작업도 느려졌을 수 있다.

전체 실행 결과 JSON 15개(`raw/b-full-*` · `c-w4-*` · `d-build-*` · `f-build-burn12-*`, 각 약 414KB)는 저장소 크기 때문에 `raw-full-runs.tar.xz` 하나로 묶었다(손실 없음). 풀면 `raw-full-runs.SHA256SUMS` 로 원본과 대조된다. `results.tsv` 는 묶기 전 원본에서 뽑았다.

| `micro/` | 조사용 시험 `micro.test.tsx` · 설정 `vitest.micro.config.mts` · 실행기 `micro.sh` |
| `raw/env.txt` · `raw/review-timestamps.txt` | 실행 환경 · 검토 실행 파일 시각 |
| `raw/runs.tsv` | 실행마다 시작 · 끝 · 종료 코드 · 시작 전 부하 · 추가 부하 |
| `raw/*.build.log` · `*.build.time` | (d) · f 의 빌드 출력과 시작 · 끝 |
| `raw/micro-*.jsonl` · `micro-*.log` | 조사용 시험 결과(시험마다 한 줄, 확인마다 시각 · 비용 · 본문 h1) |
| `SHA256SUMS` | 이 폴더 파일의 sha256 |
| `raw-full-runs.tar.xz` · `raw-full-runs.SHA256SUMS` | 전체 실행 JSON 15개 묶음과 그 원본 sha256 |
