# 브랜치 전략 전환 기록

작성일 2026-09-18 · 적용 시점 `v0.2-decoy` 이후

## 결정

9/18 콘솔 구현부터 **main + 짧게 사는 기능 브랜치 + PR** 로 운영한다.
병합은 Rebase and merge 로 하고, 커밋 메시지는 한 줄로 쓴다.

## 그 전까지

9/2~9/18 은 main 에 직접 커밋했다. 이 구간은 허니팟을 띄우고 규칙 v1·v2 를 실험하던
단계로, 한 사람이 같은 파일을 연달아 고치는 흐름이라 브랜치를 나눌 대상이 없었다.
이 이력을 브랜치와 PR 로 소급해 다시 만들지 않는다. 시각이 맞지 않는 이력은 기록이
아니라 꾸밈이다.

## 전환한 이유

커밋 메시지를 한 줄로 줄이면서 **설계 근거를 남길 곳이 없어졌다.** 그 근거를
PR 본문에 남긴다. PR 템플릿의 "왜 이렇게" 칸이 그 자리다.

## 채택하지 않은 것

| 방식 | 판단 |
|---|---|
| GitFlow (develop · release · hotfix) | 1인 프로젝트에서 릴리스 브랜치는 관리 비용만 든다. 배포 대상도 하나다 |
| Squash and merge | 브랜치 안의 단계가 main 에서 사라진다. 커밋을 정리해서 올리는 편을 택했다 |
| Jira · 스프린트 · 별도 백로그 | WBS v2.0 이 이미 백로그다. 두 곳에 적으면 하나는 반드시 낡는다 |

## 운영 규칙

| 단계 | 내용 |
|---|---|
| 시작 | WBS 항목 단위로 이슈를 열고 브랜치를 판다 (`feat/` · `fix/` · `docs/` · `chore/`) |
| 작업 | 한 줄 커밋. main 이 앞서가면 merge 가 아니라 rebase 로 따라간다 |
| 완료 | PR 템플릿에 설계 근거와 검증을 적고 Rebase and merge |
| 단계 종료 | 태그 (`v0.3-console` 등) |
