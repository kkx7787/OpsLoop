# OpsLoop

허니팟에서 관측한 공격을 실서비스 방어까지 잇도록 설계한 관제 플랫폼이다. 사람이 사건을 판정하고, 그 판정이 탐지 규칙 개선과 차단 집행으로 다시 이어지는 폐루프를 운영한다.

Mac 한 대 위의 VMware 내부망(기본 리눅스 VM 여섯 대)과 AWS DMZ(인스턴스 두 대)에 직접 구축했다. 10/03 노드 편입 촬영에서 web-02 한 대를 추가했으며 현재 남겨 둔 상태다. 방화벽 · 부하분산 · DB · 로그 수집 · 백업 · 복원 · 장애 전환을 운영하고, 실제 장애를 넣어 시험했다. 운영 판단은 멈춘 곳 가르기 → 복구 → 정상 확인 순서로 한다.

## 구성

```
인터넷
  │  22 · 23 · 8080 만 닿는다
  ▼
[AWS DMZ]
  허니팟 관문 10.0.1.10 ─ DNAT · 거부 기록 · 차단 집행(fail2ban)
    └─ 허니팟 10.0.21.10 ─ Cowrie(SSH · Telnet) · 웹 디코이 · 원장 업로더
          │ 올리기만 (S3 게이트웨이 엔드포인트)
          ▼
        S3 원장 ─ raw(원문) · hb(생존 신호) · block(차단 목록) · cti(공개 정보)
          ▲ 가져오기 (내부에서 밖으로 시작하는 연결)
[VMware 내부망 · 인터넷에서 닿지 않는다]
  방화벽 VM ─ nftables · HAProxy :8443 · chrony · 관리 VPN · 내부 방화벽 차단 동기화
    ├─ 서비스망 192.168.50.0/24   콘솔 A .11 · 콘솔 B .12 · web-01 .21 · web-02 .22(촬영 추가)
    ├─ 데이터망 192.168.60.0/24   데이터 노드 .11
    ├─ 관리망   192.168.70.0/24   작업자 단말(Mac) .1
    └─ 외부 역할 203.0.113.0/24   공격자 VM .10 (web-01 80 에만 닿는다)
```

### VMware 내부망 (VMware Fusion · Ubuntu 24.04)

| 노드 | 주소 | 메모리 · CPU | 하는 일 |
|---|---|---|---|
| opsloop-fw | 서비스망 192.168.50.1 · 데이터망 192.168.60.1 · 관리망 192.168.70.254 · 외부 역할 203.0.113.1 | 1GB · 2 | 내부 방화벽(nftables) · 콘솔 진입점(HAProxy `:8443`) · 내부 시간 서버(chrony) · 관리 VPN(Tailscale 서브넷 라우터) · 차단 동기화(nft 집합 `opsloop_block`) |
| opsloop-console-a | 192.168.50.11 | 1GB · 1 | 관제 콘솔(FastAPI API · React 화면) · 알림 발송기 |
| opsloop-console-b | 192.168.50.12 | 1GB · 1 | 예비 콘솔. 평소 꺼 둔다. 시험 · 시연 때만 합류한다 |
| opsloop-data-01 | 192.168.60.11 | 2GB · 2 | PostgreSQL 16 · Loki(루프백에만) · 수집 관문 `:3101` · 5분 적재기 · 1분 다리 · 탐지 · 차단 집행기 · CTI 수집 |
| opsloop-web-01 | 192.168.50.21 | 768MB · 1 | 관제 대상 서버(nginx · sshd · Grafana Alloy 에이전트). DB 에는 닿지 않는다 |
| opsloop-attacker | 203.0.113.10 | 512MB · 1 | 시연용 공격자(문서용 대역). 평소 꺼 둔다 |
| opsloop-web-02 (10/03 촬영 추가) | 192.168.50.22 | 768MB · 1 | 등록 노드 편입·로그 수집 확인. #118에서 수집 관문 허용 줄·인벤토리·자산 조사 대상에 영속 반영 |

- 가상 네트워크는 DHCP 를 끄고 주소를 고정한다. 서비스망 · 데이터망은 Mac 에 연결하지 않는다. Mac 은 관리망으로만 들어간다.
- 세그먼트 사이 통신은 모두 방화벽 VM 을 지난다. 같은 서비스망 안의 web-01 → 콘솔은 콘솔 호스트 가드(nftables)가 막는다.
- 콘솔은 인터넷에 열지 않는다. 관리망 · VPN 에서 `https://192.168.70.254:8443` 으로 들어온다(10/03 #103 운영 반영). 허용 기기에는 프로젝트 CA 신뢰 등록이 필요하다. VPN 은 방화벽 VM 이 밖으로 연결을 여는 방식이라 바깥에서 들어오는 포트를 열지 않는다.
- 내부 노드는 인터넷 시간 서버에 닿지 않는다. 방화벽이 시각을 나눠 준다(`makestep 1 -1`).

### AWS DMZ

| 구성 | 위치 | 하는 일 |
|---|---|---|
| 허니팟 관문 | 공개 서브넷 10.0.1.10 · EIP | 인터넷 유입 22 · 23 · 8080 만 허니팟으로 DNAT 한다. 그 밖의 유입과 DMZ 에서 나가는 연결은 거부하고 기록한다. 차단 목록을 fail2ban 으로 집행한다 |
| 허니팟 | DMZ 서브넷 10.0.21.10 · 공인 주소 없음 | Cowrie(SSH 22 · Telnet 23) · 웹 디코이(8080) 한 대 · 원장 업로더(5분) |
| S3 원장 | 버전 관리 · 공개 차단 | 인스턴스별 쓰기 경계. 허니팟은 자기 경로에 한 번 쓰기만 한다 |
| 엔드포인트 | S3 게이트웨이 · SSM 인터페이스 3개 | 원장 업로드와 관리 접속이 인터넷 경로 없이 간다. 인바운드 관리 포트가 없다 |

- 허니팟은 원문을 올리기만 한다. DB 주소도 비밀번호도 모른다. 파싱 · 탐지는 내부망 데이터 노드가 가져가서 한다.

## 흐름

```
수집  허니팟 → S3 원장 → 5분 적재기(puller) → 파서 → events
      web-01 Alloy → 수집 관문 :3101 → Loki → 1분 다리(collector) → events
탐지  detect.py 규칙 → incidents → 콘솔 사건 목록 · 알림 채널
판정  사람이 콘솔에서 판정한다 (threat · non_actionable · false_positive · benign_positive · undetermined)
차단  차단 요청(지점 · 만료) → 집행기(1분) → S3 차단 목록 → 내부 방화벽 · 허니팟 관문 동기화(1분) → 적용 보고 → 콘솔 지점별 결과
해제  해제 · 만료 → 다음 목록에서 빠짐 → 두 지점이 뺐다고 보고 → 감사 기록
```

판정이 두 고리로 돌아간다.

- **대응 루프.** 사건 → 판정 → 차단 요청 → 두 지점 적용 확인 → 해제 · 만료. 판정은 사람이 한다(자동 판정 없음). 판정 보조 도구(`detector/triage.py`)는 규칙이 본 것 밖의 행위까지 증거로 보여 준다.
- **개선 루프.** 판정 → 규칙 품질 집계 → 같은 구간에 후보 규칙을 다시 돌려 견줌(리플레이) → 규칙 버전 승격. 판정 저장은 규칙·버전별 품질 집계에 바로 반영되지만, 후보 규칙 편집·리플레이·승격은 운영자가 직접 한다(자동 학습·자동 임계치 변경 아님). 화면은 저장된 결과를 조회·비교한다. 1회차는 판정 32건으로 v1 → v2, 2회차는 판정 69건으로 v2 → v3 · 웹 w1 → w2 를 만들었다. 3회차는 정상 트래픽 리플레이로 후보를 견주고 승격하지 않았다.

데이터 출처를 가른다.

- 구축 중 자체 접속은 `parser/exclusions.txt` 로 `provenance=fixture` 가 되어 실측 통계에서 빠진다.
- 시험 출발지(문서용 대역 `test_ranges`)의 사건은 탐지 · 판정 · 차단은 그대로 하고 규칙별 집계에서만 빠진다.

## 운영

### 감시 — 멈춘 곳 가르기

| 대상 | 방법 | 보는 곳 |
|---|---|---|
| 콘솔 진입점 | Mac launchd 가 60초마다 HTTPS `/health` 를 본다. 3번 모두 실패하면 DOWN, 돌아오면 복구를 알린다(macOS 알림 · 선택 웹훅). 콘솔 안의 발송기가 함께 죽어도 알릴 길을 따로 둔다. 마지막 성공 백업이 10시간 넘게 지나도 알린다(#91). 10/03 설치본은 기록 누락·읽기 실패·5분 초과 미래 시각도 확인 불가로 알린다(#111 · #113). 감시도 Mac 에서 돌아 Mac 이 잠들거나 꺼진 동안은 멈추고, 깨어난 뒤 알린다 | `infra/vmware/scripts/console-watch.sh --status` |
| 수집 · 관제 상태 | 대상별 카드(허니팟 센서 · web-01 · 관제 콘솔 · 데이터 노드 · 등록 노드). 생존 신호(업로더 5분 · 차단 보고 1분)는 신호 시각과 기록한 쪽의 확인 시각을 따로 둔다. 신호가 끊긴 것과 기록하는 쪽이 멈춘 것을 가른다 | 콘솔 '수집 · 관제 상태' · 관제 이상 띠 |
| 콘솔 DB 연결 | DB 연결 이름표로 콘솔 A · B 가 DB 에 붙어 있는지 본다 | 상태판 '관제 콘솔' 줄 |
| HAProxy | 서버별 UP · DOWN · MAINT | 방화벽 안 `127.0.0.1:8404`(SSH 터널로만) |
| 사건 · 수신 끊김 | 알림 채널(Teams Workflows · 일반 웹훅)로 보낸다. 채널마다 최소 심각도를 둔다 | 콘솔 알림 화면 |
| 시계 | 내부 노드는 방화벽만 시간원으로 쓴다. 시계가 어긋나면 S3 요청 거부 · 경과 시간 오류로 번진다 | `chronyc tracking` |

### 이중화 — 콘솔

- 방화벽 VM 의 HAProxy 가 `:8443` 에서 콘솔 A · B 로 나눈다. 상태 검사 `inter 2s · fall 3 · rise 3 · slowstart 30s` · `timeout connect 1s` · 재시도는 다른 서버로(`option redispatch`) · DOWN 이면 그 서버 연결을 끊는다.
- 두 콘솔은 상태를 갖지 않고 같은 DB · 같은 세션 서명 키를 쓴다. 넘어가도 로그인이 이어진다. 실시간 통보는 DB LISTEN 으로 두 콘솔 화면에 함께 간다.
- 콘솔 B 는 평소 꺼 둔다. 시험 · 시연 때만 `infra/vmware/scripts/console-join.sh` 로 합류 · 떼기를 한다. **평시에 A 가 멈추면 넘길 곳이 없어 서비스가 멈춘다.**
- DB · 방화벽 VM · Mac 한 대는 단일 장애점이다.

### 백업 · 복원

- Mac launchd 가 하루 3회(04:30 · 12:30 · 20:30) `infra/vmware/scripts/backup-db.sh` 로 DB 덤프와 역할 목록(비밀번호 없음)을 받는다. 매 회차 임시 DB 에 실제로 복원해 건수를 운영과 견준다. 21개(7일)를 보관한다.
- 덤프 전에 Mac 과 데이터 노드의 시계 차이를 재서 기록한다. 2초를 넘으면 데이터 노드 chrony 동기를 기다리고, 그래도 넘으면 덤프하지 않고 실패로 끝낸다.
- 실패하면 180초 쉬고 최대 2번 다시 돈다(제한 재시도, 한 회차 20분 안). 첫 실패 · 재시도 모두 실패 · 재시도 뒤 성공을 바로 macOS 알림으로 띄운다.
- 회차가 도는 동안 `caffeinate -i -s -w` 로 Mac 잠자기를 막고, 회차가 끝나면 푼다(#95). 시작된 뒤 잠드는 경우만 줄인다. 예약 시각에 이미 잠들어 있으면 Mac 을 깨우지 않고, 회차는 깨어날 때 돈다. 꺼져 있던 회차는 건너뛴다. `-s` 는 AC 전원일 때만 효과가 있다. 배터리 · 덮개 닫음에서의 동작은 확인하지 않았다.
- 한 회차를 통째로 놓치면 직전 성공부터 16시간이다. 목표 RPO 12시간을 넘는다. 상시 가동하지 않는 Mac 에 기대는 운영 조건이다.
- 콘솔 진입점 감시가 마지막 성공 백업이 10시간 넘게 지나면 따로 알린다(실행기가 아예 돌지 못해 스스로 알리지 못할 때). 감시도 같은 Mac 에서 돌아 Mac 이 깨어난 뒤 알린다.
- 목표는 RTO 2시간 · RPO 12시간이다. 런북은 `infra/vmware/README.md` 'DB 복원', 훈련 도구는 `infra/vmware/restore-drill/drill.py` 다. 훈련은 운영 DB 를 읽기만 하고 별도 컨테이너에 복원한다.
- 범위는 DB 인스턴스 손실이다. 데이터 노드 전손(VM 재구성 · 비밀 재발급 · Loki · 관문 원장 사본 복원)은 시험하지 않았다.
- **보관 백업 간격이 목표를 넘은 기록이 있다(9/29 ~ 30).** 후속 조치는 반영했다(#91 · #95). #91 반영 뒤 첫 정기 회차(10/02 20:30)는 Mac 이 잠든 채 시작돼 실패했다. #95 실행 중 잠자기 방지는 그 뒤인 10/03 00:10에 적용·확인했다. 정기 회차가 쌓인 간격은 아직 보지 못했다(아래 '시험 결과 · 복원').

### 격리

- 허니팟 장악을 가정한다. DMZ 에서 내부망 · 관문 · 인터넷으로 나가는 연결은 거부 · 기록한다. 원장 · SSM 만 엔드포인트로 닿는다.
- 내부망은 인터넷에서 닿지 않는다. 원장은 데이터 노드가 안에서 밖으로 가져온다.
- web-01 은 수집 관문 3101 밖에는 닿지 않는다. 에이전트는 등록 토큰으로 수집 관문에 붙고, Loki 는 루프백에만 둔다.

### 장애 전환 — 콘솔 이중화

증거: [docs/evidence/2026-10-02-retest-failover-stop/summary.md](docs/evidence/2026-10-02-retest-failover-stop/summary.md) · VM 끔 · 망 단절 · DB 끊김은 [docs/evidence/2026-09-29-failover/](docs/evidence/2026-09-29-failover/)(결과서 6장)

조건을 먼저 적는다.

- 시험 동안 콘솔 B 를 합류시킨 상태였다. 평시에는 B 를 꺼 두므로 평시 A 장애는 전환이 아니라 서비스 중단이다.
- 10/02 main `0d09fc7` 판으로는 컨테이너 정지 3회 · 강제 종료 3회(대상 A · B · A)만 다시 쟀다. VM 끔 · 망 단절 · DB 끊김은 9/29 값이다.
- 회차마다 1회 측정이다(회차 300초 · 기준 구간 30초 뒤 주입 · 주입 150초 뒤 복귀). 부하 시험이 아니다.
- 연결 재시도: HAProxy 배포본이 저장소와 같다(`timeout connect 1s` · `option redispatch 1` · `inter 2s fall 3 rise 3 slowstart 30s` · DOWN 때 그 서버 연결을 끊음). 정지 · 강제 종료에서는 대상 포트가 연결을 바로 거부해, 그 요청을 곧바로 다른 콘솔로 다시 보냈다. 전환은 DOWN 판정 전부터 요청 단위로 일어났다. '1초 넘게 기다린 요청을 다시 보낸다' 는 응답이 없는 장애(VM 끔 · 망 단절)의 동작이다. DOWN 판정 순간 그 서버로 가던 요청은 끊길 수 있다. 웹소켓은 화면이 다시 붙는다(아래 재연결 줄).
- console-b 를 대상으로 잰 것은 정지 1 · 강제 종료 1 뿐이다.

수치의 기준을 적는다. 모두 T0(주입 명령을 보내기 직전의 Mac 시각)부터 잰다. 명령이 닿아 대상이 멈추기까지 0.33 ~ 0.45초(대상 웹소켓 닫힘 기준)가 T0 뒤 모든 값에 들어 있다.

- 감지: HAProxy 통계(0.5초 표본)에 대상이 DOWN 으로 처음 보인 때다. HAProxy 로그의 DOWN 판정은 T0 뒤 4.97 ~ 5.67초다. 값은 '검사 2초 × 3회' 만으로 정해지지 않는다. 주입 전달 + 첫 검사까지의 위상(0 ~ 2초) + 남은 두 검사 4초 + 표본 지연(0.03 ~ 0.44초)이다. `haproxy.cfg` 머리 주석의 '실측 5.6 ~ 6.2초' 는 옛 값이다(배포 해시를 지키려고 설정 파일은 고치지 않았다).
- 도구 전환값: 감지와 마지막 실패 요청 가운데 늦은 시각이다. 30초 합격선은 이 값에 건다. 6회 모두 감지와 같았다.
- 연속 성공 구간 시작(기존 결과 표의 ‘전환 완료’): 다른 콘솔이 20번 연속 성공한 구간의 첫 요청을 보낸 시각이다(health · me 두 줄기 가운데 늦은 값). 0.36 ~ 0.49초에는 주입 명령 전달 시간이 포함된다. 요청 간격은 0.1초이며, HAProxy만의 전환 지연을 분리해서 측정한 값은 아니다. 20번째 성공 응답을 받아 확인한 시각은 T0 뒤 2.27 ~ 2.40초다.
- HTTP 실패: 주입 뒤 복귀 전까지 보낸 요청 가운데 2xx 가 아닌 것이다. 6회 합 1건(v03 me reset)은 주입 순간이 아니라 DOWN 판정 순간에 끊긴 요청이다. HAProxy 로그의 DOWN 11ms 앞에 보냈고, DOWN 때 그 서버로 배정된 연결이 끊겼다.

### 운영자 대응 시간 — 제한된 관찰

운영자가 공격 시각 · 종류를 모르는 별도 회차(블라인드 측정)는 하지 않았다. 10/02 통합 1회차의 사건 2건만 제한된 관찰로 적는다. 독립된 시험 2회가 아니고, 운영 효율이 나아졌다는 근거가 아니다.

| 구간 | R102 | R105 | 상태 |
|---|---|---|---|
| 사건 생성 → 판정 완료 | 138.3초 | 142.7초 | 관찰 (2건) |
| 사건 생성 → 최초 확인 | — | — | 측정 불가 |

- '판정 완료' 시각은 판정을 DB 에 넣은 트랜잭션이 시작된 DB 시각(`verdicts.created_at`)이다. 이번 두 건은 콘솔 판정이라 '판정 기록' 을 누른 직후다.
- DB 의 `decision_seconds`(판정 입력 시간, 도구 계측) 원자료는 R102 3초 · R105 2초다([g-decision-raw.txt](docs/evidence/2026-10-02-retest-integration/g-decision-raw.txt)). 원자료는 보존하되 검증된 측정값으로 쓰지 않는다.
  - 판정 입력 시간은 두 경로의 값이 한 칸에 섞인다. 콘솔은 운영자 브라우저가 사건 상세를 이번에 연 때부터 '판정 기록' 을 누를 때까지 잰다. 화면을 다시 열면 0부터 센다. triage 개별 판정은 근거를 보인 때부터 입력을 마칠 때까지 triage 실행 호스트의 단조 시계로 잰다. DB 에서 두 값을 가를 수 없다. 최초 확인 · 조사 시간이 아니다.
  - R102 는 차단 요청(09:27:33)이 판정(09:27:57)보다 24.5초 앞인데 3초로 남았다. 차단 확인은 같은 화면 안의 양식이라 시계를 다시 시작하지 않는다. 판정 3 ~ 4초 전에 상세 화면이 다시 열렸어야 하고, 무엇이 다시 열었는지는 기록이 없다.
- triage 로 한 판정은 판정 기록 시각이 사람이 입력을 마친 때가 아니라 근거를 모은 때다(코드 기준, 실측 미확인). 그 시각을 끝점으로 쓰는 값(보고서 '판정 대기' 등)은 사람 입력 시간만큼 짧게 나온다.
- 이 회차의 운영자는 공격을 보낸 사람이라 요청 시각을 알았다. 탐침 출력이 사건 생성 직후 터미널에 사건 키를 보여, 콘솔에서 사건을 스스로 발견한 시간이 아니다.
- 실제 운영의 발견 시간 · 시간 단축 효과 · 전체 탐지 정확도로 일반화하지 않는다.

### 가. 상시 운영 · 다른 사용자 접속 전 선행 조건

10/03에 다음 보완을 운영 반영했다. 반영한 기능과 남은 운영 조건을 구분한다. [배포·회귀시험 증거](docs/evidence/2026-10-03-final-tls-deployment/README.md).

- **콘솔 TLS와 Secure 쿠키를 적용했다(#103).** 브라우저 → HAProxy → 콘솔 A/B 두 구간이다. 다른 허용 기기의 CA 신뢰 등록과 인증서 갱신은 계속 관리해야 한다. DB·수집·Loki까지 모두 암호화했다는 뜻은 아니다. [발급·전환·되돌리기 절차](docs/2026-10-03-콘솔-보안-보완.md).
- **공유 로그인 제한을 적용했다(#103).** 60초 창에서 계정·출발지 조합 5회, 계정 10회, 출발지 30회까지 확인하고 이후 429/Retry-After를 돌려준다. A/B가 공유하며 영구 계정 잠금은 없다. 성공도 사전 제한에 포함한다. #95의 해시 스레드 분리와 별개의 보완이다. 운영에서는 정상 로그인과 실패 1회, 같은 배포 이미지의 격리 복원본에서는 5회 뒤 429를 확인했다.
- **데이터 노드 자원 감시를 설치했다(#109).** CPU·메모리·실제 루트/DB/Loki 디스크를 약 1분마다 최신 한 행으로 수집한다. 운영 카드에 새 측정과 저장소 여유가 표시되는 것을 확인했다. **Loki 보존 기간은 미결정이며 현재 무기한이다.** 7일·30일 후보는 설정 검증까지만 했고 원본 삭제는 적용하지 않았다. [판정·설치·보존 절차](docs/2026-10-03-데이터-노드-자원-감시.md).
- **웹훅 DNS/연결 검증 코드를 배포했다(#103).** 발송마다 A/AAAA 전체를 검증하고 숫자 IP로 고정해 연결한다. TLS 이름 검증을 유지하고 리다이렉트·환경 프록시를 사용하지 않는다. 발송 작업자는 4개로 제한한다. **새 판의 실제 Teams 수신 시험은 하지 않았다.**

### 나. 시연 범위에서 받아들인 한계

- **평시 이중화가 없다.** 콘솔 B 를 평소 꺼 두므로 평시 A 장애는 서비스 중단이다. DB · 방화벽 VM · Mac 한 대는 단일 장애점이다.
- **상시 가동하지 않는다.** 내부망은 Mac 한 대 위의 VM 이다. Mac 이 잠들거나 꺼지면 내부망의 적재 · 탐지 · 알림이 멈춘다. 깨어난 뒤 밀린 것을 적재하고 알림은 늦게 나간다. 기간 보고서에 그 구간의 공백 · 지연이 들어간다.
- **보관 백업 간격이 목표를 넘은 기록이 있다(9/29 ~ 30, 86,401초).** 후속 조치(하루 3회 · 제한 재시도 · 즉시 실패 알림 · 오래됨 알림 · 덤프 전 시계 확인 · 실행 중 잠자기 방지)는 반영했고(#91 · #95) 효과는 관찰 전이다. 복원 훈련 합격과 별개다. 데이터 노드 전손 복구는 시험하지 않았다.
  - 실행 중 잠자기 방지는 회차가 시작된 뒤 잠드는 경우만 줄인다. 예약 시각에 Mac 을 깨우지 않는다. 예약 시각 전에 이미 잠들어 있으면 회차는 깨어날 때 돈다.
  - 한 회차를 통째로 놓치면 직전 성공부터 16시간이다. 목표 12시간을 넘는다.
  - #91 반영 뒤 첫 정기 회차(10/02 20:30, #95 적용 전)가 이렇게 실패했다. Mac 이 잠든 채 2초 깸에 시작했고, 다시 잠든 사이 백업 창이 끝났다.
- **관문 차단의 실제 효과는 잴 수 없다.** 공격자 VM 은 같은 Mac 위의 VM 이고 트래픽이 관문을 지나지 않는다. 허니팟에서 본 공격자와 출발지도 다르다. 증명 범위는 '같은 차단 목록이 두 지점에 집행된다' 까지다. 허니팟 정보가 web-01 보호에 기여했다는 것까지 증명하지 않는다.
- **차단은 새 연결부터 막는다.** 두 지점 모두 맺어진 연결은 그대로 간다. 맺어진 연결은 시험하지 않았다. 기존 연결을 끊을지는 운영 정책으로 정한다.
- 만료 없는 차단은 설계상 두 지점 어디에서도 집행되지 않는다.
- **노드 편입은 수작업이다.** 현재 수집 플레이북과 내부 방화벽 허용 대상은 web-01 · web-02다. #118에서 web-02의 재부팅 후 수집 단절을 고쳤다. 다른 노드를 추가할 때는 인벤토리·방화벽 허용 목록·자산 조사 목록을 함께 반영해야 한다. 새 노드는 내부 방화벽에 그 노드 → 192.168.60.11:3101 허용 줄을 먼저 더해야 한다(`infra/vmware/README.md`). 토큰 발급만으로는 편입되지 않는다.
- R106 · R107 의 실제 탐지는 재지 않았다. 정상 표본이 작아 오탐률을 말하지 않는다.
- 운영자 대응 시간은 사건 2건의 제한된 관찰뿐이다. 블라인드 측정은 하지 않았다. 그 회차에서는 탐침 출력이 사건 생성 직후 운영자 터미널에 사건 키를 보였다. 판정 입력 시간(도구 계측)은 콘솔 · triage 값이 한 칸에 섞여 측정값으로 쓰지 않는다.
- 무응답형 장애 감지는 약 11 ~ 12초다. DOWN 직전 요청 약 10건이 끊기고, DB 끊김 때는 감지 전까지 5xx 가 난다.
- 격리 잔여 위험 셋(VPC DNS · 관문 외부 443 · 53 · 콘솔 · 데이터 노드 외부 HTTPS 목적지)이 남았다.
- 알림 발송기는 시험 출발지를 거르지 않는다. 시험 때는 채널을 잠시 끄는 절차로 막는다.
- 대부분 제한된 회차의 측정이고 부하 시험이 아니다. 결과서 12장의 통합 · 복원과 장애 전환 정지 · 강제 종료는 10/02 판(main `0d09fc7`) 값이다. VM 끔 · 망 단절 · DB 끊김은 9/29 값이다. 10/03 HTTPS 판의 개발 회귀시험과 컨테이너 정지·강제 종료 6회 및 새 백업 복원은 13.4에 별도로 기록한다. 통합 탐지·차단·해제 지연 전체를 새로 측정한 것은 아니다.
- 해제 뒤 화면 반영은 집행기 다음 회차를 기다려 한 회차에서 2분 기준을 2.8초 넘었다. 운영 문서는 집합에서 빠지는 시간(보통 2분 안)과 화면 지점 칸 반영(집행기 다음 회차라 더 늦을 수 있다)으로 기준 문구를 나눴다(#92). 집행기 반영 시점은 그대로다.
- 장비 방화벽 연동은 집행 실행기 자리만 두었다. 실제 장비 연동은 검증하지 않았다.
- 404 화면 시험은 시험 안정성 조사 항목이다. 최초 실행에서 비동기 화면 대기 실패 1건, 재실행 통과. 서비스의 404 기능 오류는 입증되지 않음. 원인은 확정하지 않았다(위 '화면 시험 404').

### 수정 판 확인과 시연 영상

10/03 최종 개발 판은 HTTPS 운영 반영과 영향 범위 재시험·정리까지 마쳤다. [기능 동결 기록](docs/2026-10-03-최종-개발-동결.md)과 [결과서 13.4](docs/2026-09-29-테스트-결과서.md#134-최종-개발-판의-https-배포와-재시험)를 최신 기준으로 삼는다. 아래는 그보다 앞선 수정 판과 촬영 기록이며, 영상의 주소·로고·담당 영역·자원 지표는 최종 판과 맞춰야 한다.

#94·#95가 포함된 main `4fb9949`의 회귀시험과 10/03 운영 화면 확인은 결과서 13장에 구분했다. 프런트엔드 1,079건·빌드, 백업 실행기 29건 통과 기록을 보존했다. 앱 729건은 Docker 저장 장치 오류 전 606건 관찰과 복구 뒤 123건 재실행의 합산이며, 단일 연속 전체 실행은 아니다. 첫 606건 전체 원문이 남아 있지 않은 한계도 적었다.

추가 촬영에서는 web-02 편입, 내부 방화벽 새 연결 차단·해제, 격리 복원 콘솔 조회·판정 저장을 확인했다. 새 RTO·지연·블라인드 운영자 시험은 아니다. 6분 50초 영상은 10/02 측정 장면과 10/03 촬영을 구분한다. 근거는 [수정 판 검토와 촬영 기능 확인](docs/evidence/2026-10-03-release-review/summary.md), 발표·WBS 반영 기준은 [문서 마감 확인](docs/2026-10-03-문서-마감-확인.md)에 있다.
